## 0. 一句话结论

**duoduo 是一个让大语言模型持续运行、随时可调用的程序。它只做模型自己做不到的事——保存状态、安排日程、管理并发、划定边界——所有需要判断的事都交给模型。**

这句话展开为三个设计决定：

1. **推理引擎来自外部。** duoduo 自己不写任何推理逻辑。它把 Claude Code、Codex、Grok、pi 这四个现成的 agent 引擎当作可替换的部件，同一份提示词传给任意一个。（第一部分）
2. **"自我"是一组文件。** 这个 agent 的人格、记忆、日程表、后台任务分工，全部是一个 git 仓库里的 Markdown 文件。模型改这些文件就是在改自己。每次改动是一个 commit，回滚就是 `git revert`。（第三部分）
3. **先记录，再执行。** 每条输入先写进只追加的事件日志，然后才排队、处理。队列消费进度和会话恢复所需的工作都可以从"日志 + 指针"重建。进程随时可以崩溃或被终止，未处理的工作不会丢。（第二部分）

三个决定背后是同一条规则，本文会反复用到它：

> **确定性的事交给代码：存储、排序、调度、并发、测量、校验。需要判断的事交给模型：推理、写作、决定记住什么、决定改什么。**

三个决定共同引出一个问题：一个无人值守、能改自己的程序，靠什么不做错事、不产生不必要的开销？这是第四部分。第五部分是总评。

| 部分 | 对应的设计决定 | 回答的问题 | 一句话答案 |
|---|---|---|---|
| 第一部分 · 推理引擎 | 决定 1 | 它怎么使用 Claude Code、Codex、Grok、pi？ | 一份提示词，四个可换的引擎；差异不隐藏，在命令层显式分支 |
| 第二部分 · 消息处理 | 决定 3 | 一条消息怎么被可靠地处理？ | 先写日志，再排队，再合并成一次引擎调用，最后写回执 |
| 第三部分 · 自我迭代 | 决定 2 | 它怎么变得更好？（本文核心） | 后台定时唤醒一次性的模型会话，读日志、改记忆文件、git 提交 |
| 第四部分 · 边界、成本与失败 | 三者共同的边界 | 什么阻止它做错事、产生不必要的开销？ | 少数硬边界写在代码里，其余约束写在提示词里；每个部件都定义了失败后怎么办 |
| 第五部分 · 总评 | — | 值得借鉴什么？局限在哪？ | 十二个可复用的设计，三个局限 |

**三种读法：**
- 15 分钟：第 0 节（含 0.1、0.4），第一至第四部分开头的"关键句"，第五部分。
- 1 小时：全文顺读。
- 深入：按附录 C 到 `AGENT_INTERNALS_ANALYSIS.md` 查逐行证据，或直接读还原源码。

## 0.1 起点：运行时补足模型的缺失

一个大语言模型是一个无状态函数：给它一段文本，它返回一段文本。它有五个天然限制。duoduo（本文叫"运行时"，定义见 0.3）的每个子系统都对应其中一个限制。

| 模型的限制 | 后果 | duoduo 的对策 | 在哪一部分 |
|---|---|---|---|
| 两次调用之间没有记忆 | 关掉对话，状态全部丢失 | 所有状态放文件：消息正文只在只追加的事件日志里保存一份，邮箱和索引只存指向它的指针；会话身份、任务定义、用量账本各有自己的持久文件；每次调用前重新装配上下文 | 第二部分 |
| 没有工具调用能力，不能读文件、跑命令 | 只能说，不能做 | 调用自带工具的 agent 引擎（Claude Code 等），duoduo 不写工具执行循环 | 第一部分 |
| 没人提问就不运行 | 没有人说话时什么都不会发生 | 一个定时器（"心跳"，约 37 分钟一拍），记忆有新变化时才唤醒一个一次性的分区会话 | 第三部分 |
| 感觉不到时间、不知道自己被打断过 | 隔了三天再聊，它以为是三秒前 | 每一轮把"距上次多久""刚才被打断"等信息作为文本写入输入 | 第二部分 |
| 不会自己变好 | 同样的错误反复犯 | 分区会话读日志、把经验写成记忆文件、git 提交；下一次对话自动加载 | 第三部分 |

"记忆有新变化"的精确含义：记忆目录里的碎片、实体档案、规则文件有改动，或事件日志里最新一条"外部来源事件"换成了新的一条。外部与内部按事件的来源种类划分：心跳、分区会话、系统维护、前台引擎的工具调用与回复、路由投递、网关写入这六类算内部，不计入；其余都算外部，包括渠道消息、定时任务的启动与完成事件、通过命令行写入的配置变更。因此一个定时任务到点运行并写下完成事件，即使没有任何人类消息，也会让下一拍心跳放行后台分区。只改记忆板本身不会触发（3.3 节）。

再加一条不是模型的限制，而是无人值守带来的风险：它可能做错事，也可能不停地花钱。对策是少数几个写在代码里的硬边界，加一组成本控制配置。这是第四部分。

## 0.2 预备知识：读本文需要的背景

本节只讲后文用到的概念。已经熟悉的读者可以跳过。

### 大语言模型相关

- **提示词（prompt）**：送进模型的那段输入文本。本文分两种：每次调用都放在最前面、讲身份和规则的"系统提示"；用户或运行时每一轮追加的"用户输入"。
- **上下文（context）**：这一次送进模型的全部文本。模型一次能读的最大长度叫"上下文窗口"。
- **token**：模型计费和计长度的单位，大约等于四分之三个英文单词或半个汉字。
- **输入缓存（prompt cache）**：引擎会把每次输入开头一模一样的那部分缓存起来。下一次输入只要开头相同，命中缓存的 token 按大幅折扣计费，且响应更快。缓存只保留几分钟。所以系统提示越稳定、越少变，成本越低。本文说"缓存前缀"，指的就是输入开头这段相同的文本。
- **流式（streaming）**：不等全部生成完，模型每生成一段就送回一段，连接保持打开。本文说"流式会话"，指一条一直开着的连接。
- **压缩历史（compact）**：对话太长时，让模型把前面的历史总结成一段短摘要替换掉，腾出上下文窗口，会话本身不换。
- **agent 引擎（agent harness）**：模型 + 一组工具（读写文件、跑命令等）+ 一个循环（模型决定调什么工具，引擎执行，把结果送回模型，直到任务完成）。Claude Code、Codex、Grok、pi 都是这种引擎。本文一律称"引擎"。
- **子代理（subagent）**：主会话临时开一个小会话去做一件事，做完收回结果。
- **hook（钩子）**：引擎提供的回调点，在工具调用之前或之后插入运行时自己的逻辑。
- **MCP（Model Context Protocol）**：给引擎追加额外工具的一种跨厂商通用接口。**dynamicTools** 是 Codex 自己的对应接口，让调用方在运行时动态注册工具。
- **思考过程（reasoning / thinking）**：模型在给出答案前生成的推理文本。引擎可以把它流式送出，也可以不送。

### Claude Code 与 Claude Agent SDK

本文里"Claude Code"指 Anthropic 的命令行工具（终端里的 `claude` 命令；命令行工具下文简称 CLI）。它和网页聊天的区别是：它会自己执行操作。你说"把这个 bug 修了"，它会读代码、改文件、跑测试、看结果、再改，循环到做完。

**Claude Agent SDK** 是把 Claude Code 封装成一个库，让别的程序能调用它。npm 包名 `@anthropic-ai/claude-agent-sdk`（npm 是 JavaScript 程序的包管理器；"npm 包"就是一份可安装的发布物，duoduo 也以此分发），核心函数是 `query()`。你的程序调一次 `query("帮我……")`，SDK 替你跑完一整轮，把结果流式返回。

| | Claude Code（CLI） | Claude Agent SDK（库） |
|---|---|---|
| 给谁用 | 人，坐在终端前 | 程序，自动调用 |
| 形态 | `claude` 命令 | 代码里的 `query()` 函数 |
| 关系 | 实际执行任务的程序 | 启动 Claude Code 并与之通信的接口 |

duoduo 用的是 SDK。对后台任务这类一次性会话，一轮对话就是一次 `query()` 调用；对前台聊天会话，duoduo 开一条长期保持（空闲 1 小时才释放）的 `query()` 连接，后面每一轮都送进同一条连接（2.2（c））。

SDK 会另起一个 Claude Code 程序（子进程）来执行，两者靠文本管道通信。这个程序随 SDK 一起安装，所以用户不必另装 `claude` 命令；想指定自己的 Claude Code 程序，用环境变量 `CLAUDE_CODE_EXECUTABLE`。用 `--omit=optional` 安装 duoduo 会缺掉这个程序，会话第一条消息时会报错并给出重装指引。这一层 duoduo 不涉及。

**其他三个引擎：**
- **Codex** 是 OpenAI 的 CLI agent。duoduo 启动一个常驻的 `codex app-server` 子进程，用 JSON-RPC 与它对话。JSON 是一种用花括号和引号书写结构化数据的文本格式；JSON-RPC 是一种约定：调用方发一条 JSON 文本写明"调哪个函数、参数是什么"，对方回一条 JSON 结果。本文说"RPC"，都指这种远程函数调用。
- **Grok** 是 xAI 的 CLI agent。duoduo 启动 `grok agent` 子进程，用 ACP（Agent Client Protocol，一个跨厂商的 agent 通信协议）与它对话。
- **pi** 是一个开源的 agent 库。它直接打包在 duoduo 的 npm 包里，不需要另外安装，运行在一个 duoduo 启动的 worker（工作进程）里。

### 软件工程相关

- **git**：给一个文件夹记版本的工具。本文只用到五个概念：commit = 存一个带说明的快照；revert = 生成一个撤销某次快照的新快照；diff = 逐行对比两个版本的差异；工作树 = 文件夹里现在实际的内容，可能比最新快照更新；`.gitignore` = 列出哪些文件不进版本记录的清单。
- **进程与子进程**：进程是一个正在运行的程序。子进程是由另一个进程启动的进程。
- **环境变量**：启动程序时传给它的一组"名字=值"设置，本文出现的 `ALADUO_*` 都是。
- **API key**：调用模型接口用的密钥。
- **哈希（sha256）**：把任意长的文本压成一串固定长度的字符，内容不同结果几乎必不同。用来判断"内容变没变"。
- **frontmatter**：Markdown 文件顶部用 `---` 包起来的配置块，格式是 YAML（一种"键: 值"逐行书写的配置写法，如 `runtime: claude`）。TOML 是 Codex 用的另一种配置文件格式。
- **JSONL**：每行一条 JSON 的纯文本文件。
- **unix socket**：本机进程之间通信用的一种文件形式的通道，权限由文件系统控制。TCP 端口则是网络端口，本机或远程程序都可能连上。WebSocket 是一种保持打开、双向推送的网络连接。
- **cron**：Linux 系统自带的定时器（macOS 上对应 launchd）。"cron 表达式"是它的五段式时间写法，如 `0 9 * * 1` 表示每周一 9 点。
- **GC（garbage collection）**：自动清理不再被引用的东西。本文里指自动清理孤儿记忆文件。

## 0.3 术语表

| 术语 | 含义 |
|---|---|
| **运行时** | 本文指 duoduo 这个常驻程序本身：调度、日志、心跳等确定性逻辑。它不做推理，也不执行引擎的内置工具（读写文件、跑命令）；它只实现附加给模型的自操作工具（见本表末尾） |
| **引擎（配置字段名 `runtime`）** | `claude`、`codex`、`grok`、`pi` 四选一的推理引擎，真正调用模型、执行工具的部件。注意：配置文件里的 `runtime` 字段指引擎，不指 duoduo |
| **daemon** | duoduo 的常驻进程。调度、会话、邮箱、日志、心跳等核心逻辑都在这个进程里；渠道适配器是独立进程，四个引擎各自跑在它启动的子进程里 |
| **host 模式** | daemon 直接在你的机器上运行、引擎能直接读写本机文件的模式。v0.8.1 只有这一种模式 |
| **Spine / WAL** | 只追加的事件日志，路径 `~/.aladuo/var/events/YYYY-MM-DD.jsonl`。WAL 是 write-ahead log，意思是"先写日志，再做事"。每条事件另有一行 by_id 索引，按事件 id 反查它在哪个文件的哪个位置 |
| **session / actor** | 一个对话（或一个后台任务）在内存中的执行体。一个会话键对应至多一个 actor |
| **session key（会话键）** | 会话的唯一名字，形如 `stdio:default:<工作目录哈希>`。前缀决定它是渠道会话、job 会话还是分区会话 |
| **渠道会话 / job 会话 / 分区会话** | 渠道会话是有人在聊天平台上对话的会话（下文的"前台会话"即渠道会话）；job 会话是执行一个后台任务的会话；分区会话是心跳唤醒的一次性后台模型会话。后两者合称"后台会话" |
| **mailbox（邮箱）** | 每个会话的待办文件，只存事件指针 `- [ ] @evt(id)`，不存正文 |
| **drain / turn** | drain 是"把邮箱清空"的一次处理；turn 是对模型的一次调用。多条消息可以合并成一个 turn |
| **outbox** | 出站回执的记录和投递状态 |
| **网关** | daemon 里接收所有入站消息、决定"要不要调用模型"的组件。注意：飞书渠道适配器的打包文件名叫 `feishu-gateway.js`，那是渠道适配器，不是这里的网关 |
| **kernel（内核，`~/aladuo`）** | git 管理的"自我"目录 |
| **身份提示（meta-prompt.md）** | 出厂的人格定义文件，从 npm 包内现读，不落内核 |
| **记忆板（memory/CLAUDE.md）** | 上游叫 broadcast board 或 intuition layer。每个新的渠道会话和 job 会话都会把它的正文注入系统提示（注入前去掉文件顶部的 frontmatter 和 HTML 注释，正文里用 `@路径` 引用的文件也一并读入展开）；分区会话只拿到它的路径，自己读 |
| **档案（dossier）** | `[[slug]]` 链接指向的深层文件：实体档案、`lesson-*`（纠错规则）、`groove-*`（重复任务的固定流程）。slug 是文件的简短标识名，如 `[[lesson-deploy-check]]` |
| **孤儿文件** | 从记忆板出发沿 `[[slug]]` 链接走不到的记忆文件，因此不会被前台读到 |
| **碎片（fragment）** | 后台从事件日志里提炼出的一条证据。大多数碎片回指记忆板的某一行，说明它"起作用了 / 该起作用却没起 / 没有相关证据"；另一类碎片不对应任何现有行，而是记录记忆板上还没有的新信号，供改记忆板时考虑是否新增一行 |
| **规则节点（node）** | 上游把 `memory/topics/` 下的一个 `lesson-*` 或 `groove-*` 文件叫一个节点 |
| **效果记录（effectiveness/）** | 由碎片折算出的、记忆板每一行"起作用了几次"的现状快照，一行一个文件。不进 git |
| **心跳（cadence）** | 默认约 37 分钟一次的后台定时器。每响一次叫"一拍" |
| **后台分区（subconscious partition）** | 上游叫 subconscious（潜意识）。每个分区是一个提示词目录，心跳会唤醒它跑一次分区会话。四个出厂分区在附录 B；下文用 distiller、weaver、tracker、committer 分别简称 gradient-distiller、intuition-weaver、pattern-tracker、memory-committer（weaver 不指已退休的 memory-weaver） |
| **playlist.md** | 分区的轮转表。checkbox（`- [ ]` 勾选框）格式，agent 自己可以改 |
| **只读检查（lint）** | 心跳里运行时对记忆文件做的检查：太长了？链接断了？有孤儿文件？只测量，不改内容；发现问题就写任务单 |
| **信号 / 任务单** | 只读检查发现问题时，产出一类"信号"（如 scan-gap、claude-compress，全部列在附录 B）；每个信号写成一份文本工单（`.pending` 文件）投进某个分区的收件箱，本文叫"任务单"。分区处理完就删掉它 |
| **contract（契约）** | 分区 frontmatter 里的机器声明："我接收哪几类信号" |
| **指令指纹** | 对"当前这套指令"算的哈希，用来发现"自我变了"（1.6 节）。另有两个同样用来判断"变没变"、但互不相关的机制：**配置签名**，把会话基本配置（工作目录、权限模式、工具集、附加目录等）序列化成一段 JSON 文本逐字比较，不同才重建流式会话，并能从差异里看出哪一项变了（2.2（c））；**活动指纹**，对记忆目录修改时间加最新外部事件 id 算的哈希，没变则心跳整拍跳过（3.3） |
| **job（后台任务）** | 由用户或前台会话布置的定时或一次性任务，一个 Markdown 文件定义；文件正文本文叫"任务书"。`keepalive` 类型的 job 跑完第一轮后不归档，保留会话进入休眠（空闲超过设定时间后资源被收回，会话记录保留），之后收到 Notify、`duoduo session notify` 或自己安排的下一次触发时在原会话上继续；要结束它必须显式归档 |
| **渠道（channel）** | 把 duoduo 接到某个聊天平台（飞书、终端、编辑器）的适配器进程，本文称"渠道适配器进程"。上游也叫渠道插件。IM 指即时通讯软件 |
| **渠道种类 / 渠道实例** | 种类指平台类型（飞书、终端）；实例指某一个具体接入点（某个飞书群）。种类配置在 `~/aladuo/config/<kind>.md`，实例配置在该实例的 `descriptor.md` |
| **自操作工具** | duoduo 追加给模型、用来操作 duoduo 自身的工具：Notify（给某个会话发通知）、ManageJob（创建、改期、归档后台任务）、ManageSession、QueueOutboundAttachment（本轮结束时给用户发文件）、Skip（本轮不输出任何文字） |
| **技能（skill）** | 一份给引擎读的操作手册文件，教它怎么完成某类运维任务，如刷新分区提示词、归档账本 |

## 第一部分 · 推理引擎：四个可替换的 agent

> **关键句**：duoduo 的代码里没有任何推理逻辑。它把 Claude Code 作为进程内库调用，把 Codex 和 Grok 作为常驻子进程调用，把 pi 作为内嵌进程调用。四个引擎接收同一个装配函数产出的提示词，只在两处分叉：怎么把这段文本交给引擎（1.3 后半），以及 `/compact`、`/model` 这类命令在各引擎上分别怎么实现（1.4）。引擎升级，系统就升级。

### 1.1 调用的是带工具的 agent，不是裸模型

这是整套架构成立的前提。duoduo 调用的不是 Anthropic 的裸 API（只负责"文本进、文本出"的最底层接口），而是完整的 agent 引擎。区别在于引擎自带工具调用能力：

| 调裸 API 时运行时必须自己写 | 使用现成引擎后直接得到 |
|---|---|
| 工具执行循环（读文件、跑命令、把结果送回模型、再循环） | 引擎内置全套工具和循环 |
| 子代理编排（把一个子任务交给独立上下文的模型实例、收回结果） | Claude Code 的 Agent 工具；Codex 有自己的 `spawn_agent`；pi 原生没有子代理工具，委派要走 job（2.6 节） |
| 会话持久化 | 引擎自己保存对话历史，duoduo 只保管一个会话 id |
| 干预正在进行的推理 | SDK 的两个 hook（工具调用之前 / 之后）就是控制接口，没有私有协议 |
| 工具扩展协议 | MCP、dynamicTools 现成可用 |

两个 hook 各管一件事：Skip 工具的调用被"工具调用之前"的 hook 拦截，直接以"本轮静默结束"终止这一轮；用户的插话在"工具调用之后"的 hook 里注入到下一个工具调用边界（2.2（b））。

所以 duoduo 代码量小，是因为最复杂的一层（工具执行与编排）由引擎承担。这也解释了第三部分：模型改自己，用的就是引擎自带的三个基本工具——Edit（改文件）、Write（写文件）、Bash（跑命令）——运行时只需把工作目录指向内核。

给 PM 的一句话：评估"自建 agent 运行时"时，第一个问题是"工具执行循环自己写还是用现成引擎"。这个选择决定运行时是几千行还是几十万行。

### 1.2 四个引擎接法各异，失败处置也刻意各异

四个引擎的接法不同，探测失败时的处置也不同：Claude 不可用时会话在收到消息时报错；Codex 不可用时，渠道会话和 job 会话静默换成 Claude，分区会话则跳过本轮，用 ManageJob 创建 Codex 任务时直接报错；Grok 不可用时明确报错；pi 从不"不可用"。这不是同一个策略的几份实现，而是 duoduo 对各引擎的接法做了不同取舍：Codex 的接法取"保证能用"，Grok 的接法取"不隐藏问题"，pi 把"能不能用"推迟到有没有配模型。下表逐项对比。

| | Claude | Codex | Grok | pi |
|---|---|---|---|---|
| 进程模型 | 进程内调用 SDK；SDK 自己启动 Claude Code 子进程 | 常驻 `codex app-server` 子进程，换行分隔的 JSON-RPC | 常驻 `grok agent` 子进程，ACP 协议 | duoduo 包内自带的 worker 子进程 |
| 需要用户另装什么 | 不用另装：SDK 随 duoduo 安装并自带程序；需要本机 Claude 登录态或 API key（1.7 节） | codex CLI 并登录 | grok CLI 并登录 | 什么都不用装；需要在 `~/.pi/agent` 里配好模型和凭据 |
| 对话历史怎么续 | SDK 的 resume：每轮成功后保存一个会话 id | thread（Codex 把一段对话历史叫一条线程）：新建、续接，或 fork——复制一份历史、换上新设定、在副本上继续 | ACP 的 session/load | pi 自己的会话 |
| 启动时怎么探测 | 检查 SDK 和程序文件存在，5 秒超时，不验证登录态 | `codex --version` + `codex login status`，看输出里有没有 "logged in" | `grok --version`，5 秒超时，不验证登录态 | **不探测**，永远列为可用 |
| 探测失败时 | daemon 照常启动；用 Claude 的会话在收到消息时报错 "Agent runtime 'claude' is unavailable"，并提示修复或切到 Codex | 渠道会话和 job 会话**静默改用 Claude**，只留一条警告日志（分区会话跳过本轮并记 runtime_unavailable 错误；ManageJob 创建 Codex 任务时在创建阶段就报错） | **不降级**。会话仍会创建，第一条消息报错："Install the grok CLI, run 'grok login'" | 不存在"不可用"。缺模型指针时在发消息时报错 |
| 权限 | 默认 `bypassPermissions`（不弹任何审批） | `approvalPolicy: never`；沙箱（限制程序能写哪些目录的隔离环境）默认 `workspace-write`，即只能写工作区，可调只读或全开 | 启动参数 `--always-approve` | 由 pi 自己的设置决定 |
| 自操作工具怎么接入 | 进程内 MCP | dynamicTools，并强制放在工具列表最外层，否则 Codex 会把它们收进子菜单、模型看不到 | 经 ACP 挂载 MCP | 在 pi worker 子进程内注册，调用时经 RPC 回连 daemon 执行 |
| 思考过程是否流给渠道 | 思考增量作为流事件转发 | 不流出：适配器握手时写死退订思考过程增量通知，无配置可开 | 与 Claude 相同 | 与 Claude 相同 |
| 特有限制 | 工具白名单（4.1 节） | 内置工具**不可禁用**，duoduo 传的禁用清单会被直接忽略，只在 debug 级日志留一条记录 | — | 原生没有子代理工具；委派靠 job |

四点补充：

- **探测结果的缓存规则**（Claude、Codex、Grok 共用）：daemon 启动时探测一次并记住结果，"哪些引擎可选"看的就是这份结果；渠道会话和 job 会话选引擎时用的探测结果也只跑一次、之后一直复用，失败了不会自动重试，只有重启 daemon 才重新探测。例外是用 ManageJob 创建 Codex 或 Grok 任务：创建阶段每次都重新执行探测命令。所以 daemon 运行中途才装好 Codex 时，ManageJob 能创建 Codex 任务，但这个任务真正运行时仍会因为缓存的失败结果被静默改用 Claude，直到重启 daemon。
- **Codex 的思考过程**：四个引擎里只有 Codex 不流出思考过程。原因是 duoduo 的 Codex 适配器在握手时固定退订了三种思考过程增量通知，这份退订清单写死在代码里，v0.8.1 没有任何配置项或环境变量可以打开。这不是提示词能解决的事，也不是用户能配置的事。
- **五个自操作工具里，QueueOutboundAttachment 和 Skip 只注册给渠道会话。**job 会话和分区会话拿不到这两个工具：它们不能静默跳过一轮，也不能直接给用户发文件，只能经 Notify 交给自己的 owner 会话（owner 即创建这个 job 的那个会话，见 2.6）。写 job 任务书时不要写"把报告作为附件发给用户"这类做不到的指令。
- **pi 的特殊之处。**它随 duoduo 的 npm 包一起分发（`dist/release/pi-worker.js`），不需要外部 CLI、不需要登录探测；它回连 daemon 的那条 RPC 带口令校验和方法白名单。代价是它没有出厂默认模型：一个 pi 会话必须有一个 `provider/modelId` 形式的模型指针（来自 job 的 frontmatter、渠道会话的 `/model`、分区的 frontmatter，或配置层的 `pi.model`，见 1.5 节），否则发消息时报错 "This pi session has no model yet"。凭据从用户自己的 `~/.pi/agent` 目录读取，duoduo 从不往里写。

### 1.3 装配面共用：一份提示词供四个引擎使用

系统提示由同一个装配函数产出，六层按固定顺序拼接：

1. 身份提示（`meta-prompt.md`，出厂人格定义，第三部分详述）
2. 渠道种类的人格（`~/aladuo/config/<kind>.md` 的正文）
3. 实例提示（该渠道实例 `descriptor.md` 的正文）
4. 记忆板（`memory/CLAUDE.md`，前面加一段"这些指令覆盖默认行为"的引导语；含 `[[slug]]` 链接时再附一段"链接是档案入口，只在需要时展开"的规则）
5. 运行上下文（会话键、渠道种类、引擎名；**不含任何时间戳**）
6. job 任务书（仅 job 会话有）

四个引擎拿到的是同一段文本，差别只在传入方式：
- **Claude**：默认以 `{preset: "claude_code", append: 文本}` 的形式追加在 Claude Code 内置系统提示之后。配置项 `prompt_mode`（渠道或 job 配置里的一个字段）设为 `override` 时不用内置提示，只用这段文本。
- **Codex**：同一段文本包进 `<aladuo:system-context>` 标签，作为 baseInstructions（Codex 对"系统提示"的叫法）。Codex 没有"内置预设"这个概念，所以 `prompt_mode` 对它无效。
- **Grok、pi**：同样消费这段文本，`prompt_mode` 有效。

还有两个针对 Codex 的适配，让它读到和 Claude 同一套定义：
- 工作目录里有 `CLAUDE.md` 而没有 `AGENTS.md` 时，duoduo 自动建一个符号链接（一个指向另一文件的快捷方式），因为 Codex 按自己的约定读 `AGENTS.md`。
- daemon 初始化时会把每个后台分区目录下 `.claude/agents/*.md` 的子代理定义编译成 `.codex/agents/<name>.toml`（内容未变时跳过，源文件删除时同步删除生成物）。v0.8 出厂的四个分区不再带任何子代理文件，所以默认安装下这一步不产生文件；只有用户自己给分区加了子代理时才用到。

### 1.4 命令层分叉：同名命令按引擎显式分支

同名操作在不同引擎上语义不同，运行时不隐藏差异，在命令层显式分支：

| 操作 | Claude | Codex | Grok | pi |
|---|---|---|---|---|
| 对话中插话（steer） | 在下一个工具调用边界经 hook 注入 | `turn/steer` RPC | `_x.ai/interject` 扩展方法 | pi worker 的插话接口 |
| `/compact` 压缩历史 | SDK 原生，会话 id 不变 | `thread/compact/start`，id 不变 | `_x.ai/compact_conversation`，id 不变 | pi 原生压缩，id 不变 |
| `/model` 换模型 | 立即生效 | 下一条消息起 fork 一条新线程生效，历史保留 | 经 ACP 切换活会话，立即生效 | 只接受 `provider/modelId` 格式，下一条消息起生效 |
| 输入 token 记账 | 分三类：新读入 / 写入缓存 / 命中缓存 | 两类：cached 已含在 input 里 | Grok 自己的口径 | pi 自己的口径 |

三条说明：不带参数的 `/model` 在 pi 上列出本机真能跑的模型，但选了跑不了的 id 不会当场拒绝，要到下一条消息才报错。`/undo`（撤销上一轮）v0.8.0 起四个引擎都不再支持，历史控制类命令只剩 `/compact`。`/clear`（别名 `/reset`）会开一个全新的引擎会话。

### 1.5 引擎、模型、推理力度分开选，逐层覆盖

引擎、模型、推理力度三样各自独立选择，都按"实例 > 种类 > 全局 > 兜底"逐层覆盖，最具体的一层生效。

**引擎选择链**，从高到低：
1. 显式声明：渠道实例的 `descriptor.runtime`、job 的 frontmatter `runtime`、分区的 frontmatter `runtime`
2. 渠道种类默认：`~/aladuo/config/<kind>.md`
3. 全局默认：环境变量 `ALADUO_DEFAULT_RUNTIME` 或 `~/.config/duoduo/config.json` 的 `defaultRuntime`
4. 兜底：`claude`

**模型与推理力度默认值**（v0.8.1 新增）。推理力度（effort）是让模型"想多久"的档位，越高越慢越贵。每个引擎各有自己的键，如 `claude.model`、`codex.effort`，可以写在三层：全局（`~/aladuo/config/runtime.md`）、渠道种类、渠道实例，越具体的层优先。合并是逐键的：在种类层只写了 `codex.model`，全局层的 `claude.model` 仍然有效。之所以每个引擎用各自的键名，是为了防止一个渠道从 Codex 切到 Claude 后，把 GPT 的模型 id 错误地带进 Claude。

两条校验规则不同：`effort` 只接受 `low`、`medium`、`high`、`xhigh` 四个值。通过 CLI、聊天里的 `/effort` 或 ManageJob 创建 job 时写错，当场拒绝并列出合法值；直接手改配置文件、job 文件或分区 frontmatter 写错，运行时只忽略这个值、记一条日志，然后按下一层默认值运行。`model` 只要求非空且不含空白，因为模型 id 是开放集合，错的 id 留到真正运行时报错。

一处上游文档与实现不完全一致的细节：job 会话里，Claude、Codex、Grok 三个引擎上 job frontmatter 的 `model` 覆盖会话自己的 `/model`；pi 引擎则相反，会话自己的 `/model` 覆盖 job frontmatter 的 `model`。推理力度方面，四个引擎都是会话自己的 `/effort` 覆盖 job frontmatter 的 `effort`。普通渠道会话没有 job frontmatter，观察不到这个差异。

用量账本记录的是**实际服务本轮的模型**，不是请求的模型（4.4 节）。

### 1.6 指令指纹比对：记忆变了只换内容，身份变了才重建会话

问题是这样的：后台会改记忆板（第三部分），而前台可能有好几个会话正开着，拿的还是旧版记忆。运行时必须发现"指令变了"，并让每个在跑的会话换上新版，又不能每次都重建会话。办法是给指令算指纹。

**答案先说：记忆板改动后，新开的会话直接装入新版；运行中的会话按各自引擎的方式得知有新版，日志里留有 `fp_old → fp_new`（fp 即 fingerprint，指纹）的记录。这是第三部分"自我迭代如何生效"的接口。**

每次处理前，运行时对"当前这套指令"算一个哈希：身份提示、渠道人格、实例提示、记忆板、job 任务书（连同其必填的验收标准）。与会话存档比对，分三种情况：

- **只有记忆板变了**（最常见）。做法是"换内容、不换会话"：
  - Claude：会话不重建。正在运行的流式连接继续沿用原来那份系统提示（旧的记忆板仍留在前缀里，所以缓存不会被打断），运行时只在下一轮输入前附一句"记忆板已变，需要的话去读这个文件"，由模型自己决定是否读取新版。新版记忆板真正写进系统提示，要等这条流式连接下次重建，例如空闲回收后重新恢复会话。
  - Codex：普通聊天会话沿用原线程（v0.7.1 修复项）；由 job 创建的会话则 fork 一条新线程。
- **身份、人格或任务书变了**：Claude 的流式会话作废重建（日志里记 `instructions_drift`）；Codex 的系统提示是随线程启动一起交给 app-server 的，运行时沿用已有线程时不会再传新指令，所以改为 fork 一条携带新指令、继承原有历史的新线程（父线程已被回收时退化为新建线程，历史不保留）。
- **什么都没变**：什么都不做。

v0.8.1 修正了两处与指令指纹相关的缺陷：
- Agent SDK 新版默认会把一个会话第一次请求时的系统提示记录下来、之后一直复用，直到下一次压缩历史。这样记忆板改了也送不进正在跑的会话。duoduo 显式关掉了这个默认。
- 运行时原来靠"文件修改时间变了"判断分区和 job 的提示词文件有没有改；用 `cp -p` 这类保留原时间戳的方式覆盖文件就会漏检。现在下一拍就能发现。

### 1.7 无人值守下的权限与认证

daemon 无人值守，任何审批弹窗都会让会话无限期阻塞。所以除 pi（权限由 pi 自己的设置决定，见 1.2 表）以外的三个引擎都被设成不弹审批：Claude 未显式配置时一律落到 `bypassPermissions`，Codex 固定 `approvalPolicy: never`，Grok 用 `--always-approve`。Claude 的这一项渠道和 job 配置里没有字段，只能用环境变量 `ALADUO_PERMISSION_MODE` 改。安全不靠逐次审批，靠结构性边界：工具白名单和控制面分层的完整定义在 4.1 节，Codex 沙箱见 1.2 表的"权限"行。

一个易错的配置项：渠道或 job 配置里仍接受两个旧键，但都不管内置工具。`allowedTools` 只影响权限自动批准，不会把内置工具加进白名单。`disallowedTools` 只能禁掉 `mcp__` 前缀的 MCP 工具，对内置工具无效。写了对内置工具无效的项，daemon 不会报错，只打一条警告并忽略这些项；这条警告没有去重，每次为会话构建引擎参数时都会再打印一次，不影响运行。要增加内置工具，唯一入口是 `claude.tools`。

**认证来源**（仅 Claude 侧，首次安装向导 `duoduo onboard` 时三选一）：
- `claude_code_local`：用本机 `claude login` 的登录态。不写任何模型相关的环境变量；启动时只删除一组固定的残留变量（API key、认证令牌、接入端点、opus/sonnet/haiku 三个默认模型名，以及 API 超时和关闭非必要网络请求两项开关），防止旧的 key 或端点覆盖本机登录态。其他 `ANTHROPIC_` 前缀的变量不会被清理，例如 `ANTHROPIC_MODEL` 会原样传给 daemon。
- `anthropic_api_key`：用 API key。同时把 API 超时设为 3,000,000 毫秒，并关闭 Claude Code 的非必要网络请求；若在向导里额外填了模型名，opus、sonnet、haiku 三个默认模型也一并指向它。
- `compatible_endpoint`：任何 Anthropic 兼容端点。duoduo 给 Claude Code 子进程注入 `ANTHROPIC_BASE_URL` 和令牌。向导里的模型名是可选项：填了，opus、sonnet、haiku 三个默认模型就全部指向你填的那一个第三方模型，此时 `/model` 切档位没有意义；留空则不写任何默认模型变量，Claude Code 按自己的档位名向端点请求，切档位是否有效由端点自己决定。超时和关闭非必要网络请求两项与 `anthropic_api_key` 模式相同。

> **给 PM 的三点**
> - 不要承诺"跨引擎统一体验"。把差异显式分叉写进命令层，比隐藏差异更可维护；一条提示词装配函数加几段简单的适配代码，能避免两套封装各自漂移。
> - 常驻 agent 的权限模型重心从"逐次审批"移到"结构性边界"，立项时先决定这一点。
> - 任何做会话续接且提示词会演化的产品，都需要一个指令指纹比对的等价物，且要区分"记忆变了"和"身份变了"两种情况。

## 第二部分 · 一条消息的处理流程

> **关键句**：duoduo 处理一条消息分六步——先写日志，再分流，再写邮箱指针，再唤醒会话，再合并成一次引擎调用，最后写回执。任何一步进程崩溃，都能从日志和指针恢复。消息从渠道适配器进程进来（2.5 节）；不由人触发的消息来自 job（2.6 节）。

### 2.1 六步：先落盘，再分流，再排队，最后回执

```
外部消息（渠道适配器进程转换成 channel.ingress 调用送进 daemon）
 ① 写日志     事件原子追加进 WAL（一行事件 + 一行 by_id 索引），运维命令也不例外；重复消息直接重放上次回执
 ② 网关分流   由网关识别的运维命令（/status /config /model /effort /cancel /compact 等）直接回复，不入邮箱、不调用模型；
              其余消息——包括网关不认识的斜杠输入，如 /loop、/setup——继续往下走，作为普通消息交给模型
 ③ 写指针     向目标会话的 mailbox 追加一行 "- [ ] @evt(<id>)"，只存指针不抄正文
 ④ 唤醒       进程内广播一条 session.wake 通知，唤醒（或新建）这个会话键对应的 actor
 ⑤ 处理       drain：合并消息 → 装配上下文 → 调一次引擎 → 工具调用和结果逐条写回 WAL
 ⑥ 回执       写 outbox 记录（含成本元数据）+ 追加 agent.result 事件；有订阅的渠道实时推送
```

每一步有一个理由：

- **①写日志先行**：模型调用又慢又可能失败。把"收到"和"处理"分开，崩溃恢复就变成"重读文件"。去重只认渠道给的显式消息 id（v0.8.0 起不再按内容去重，同样的文字发两次会得到两次回答）；命中重复就重放上次回执，不重复扣费。
- **②分流**：在入口就判定"要不要动用模型"。能不调模型就不调，这是成本最低的节省手段。
- **③指针化**：正文永远只有 WAL 一份，避免双写不一致。
- **④一个会话一个执行体**：每个会话键在内存里只对应一个 actor，同一时刻只有它在处理这个会话的消息，所以同一个会话不会被两份代码同时改状态。为了让后台任务占不完资源，运行时限制同时活跃的渠道会话最多 10 个、job 会话最多 6 个，两类分别计数。另有一把跨进程的 daemon 写锁，保证同一个数据目录同一时刻只有一个 daemon 在跑（机制见 4.1 节"写锁与归档屏障"）。
- **⑤一次处理合并多条消息**：见 2.2（a）。
- **⑥回执带成本元数据**：渠道能把这一轮花了多少钱渲染给用户，见 4.4。

一个细节：v0.8.0 起 by_id 索引是有上限的近期缓存（默认保留 7 天，`ALADUO_SPINE_INDEX_RETENTION_DAYS`），不再无限增长。索引里查不到时，运行时根据事件自带的时间戳定位到它发生那一天的日志文件，从这一天开始向更早的日期逐个文件扫描，直到找到为止，所以没有事件会变得不可读。

### 2.2 处理步骤的四个设计：合并、插话、常驻、保持输入通道

处理这一步有四个设计。前三个都是为了少调用、少重跑、少冷启动；三者都以"工具调用边界是唯一安全的干预点"为前提。第四个是为了让后台子代理跑完。

**（a）合并消息：一次 turn 不等于一条消息。**真人常连发短句。drain 每次从邮箱顶部切出一个可合并窗口：最多 5 条、相邻间隔不超过 3 分钟、同类型同目标、不含斜杠命令。合并后的提示词直接说明：*"Process these N closely timed events as one continuous update. … Reply once."* 后台通知类事件不限数量一次处理完。代价是单条消息多等一会儿，换来 token 成本和碎片回复的大幅下降。

一个相关约定：后台子代理完成时，只有引擎自己的续写会把结果写进回复；运行时只把子代理的完成通知记成 WAL 里的一条生命周期事件（子代理的开始只在内存里登记，用来判断何时可以关闭输入通道，不写入 WAL），不再另起一个回调 turn。所以一个 turn 里派出三个子代理，用户看到的仍是一次回复，账本上也只有一次 drain。

**（b）插话优先于打断。**模型正在跑时来了新消息，按顺序尝试三种处理：
1. **插话**：如果引擎支持，把新文本在模型下一次调用工具的间隙送进当前这一轮。Claude 靠 SDK 的"工具调用之后"回调做到；Codex、Grok 和 pi 各有对应的插话接口，运行时把新文本直接送进引擎子进程正在跑的这一轮，送不进去时再退回下一步。
2. **软抢占**：普通消息无法插话时，对当前轮做"软抢占"，具体行为取决于引擎。对 Codex、Grok、pi 这类由子进程适配器驱动的会话：模型正在流式输出，就等它下一次发起工具调用时中止；有工具正在执行，就等该工具返回后中止；两者都不是，就立即中止——这些会话里普通消息不会截断一个正在执行的工具调用，只会在工具边界上终止当前轮。对持有常驻流式连接的 Claude 渠道会话：普通消息通常经插话通道直接送入当前轮；只有插话不可用（例如另一条消息正在插话中）时才退到软抢占，此时运行时在当前轮被引擎接受后立即中断这条流式连接，不等工具边界。之后这条消息进入下一轮处理。
3. **强制抢占**：`/cancel` 不等工具返回、也不等流式收尾，直接中止当前轮。其他斜杠命令只排队，不抢占。后台通知（子代理完成、job 完成或失败、空闲压缩等）一律只排队，不打断前台。

一次只准入一个对话 turn，后到的消息走显式的插话通道。这修复了旧版"后到消息被并入正在跑的 turn，导致会话永久忙碌"的问题。v0.8.1 又补了一条：模型自己发起的一轮（例如后台任务触发的）正在跑时，用户发来的消息会得到自己独立的一轮，不再被并入。

**（c）常驻流式会话。**同一个渠道 Claude 会话复用同一条流式 `query()` 连接，只有会话的基本配置变了（本段的配置签名）或身份类指令变了（1.6 节的指令指纹漂移）才重建。基本配置指工作目录、权限模式、工具集等；运行时把它们序列化成一段 JSON 文本作为"配置签名"，逐字比较是否变化；它不是哈希，与 1.6 节的指令指纹是两回事。好处有二：省掉每次启动进程的时间；引擎侧的输入缓存能持续命中。会话空闲超过 1 小时（`ALADUO_SESSION_IDLE_MS`）时，运行时会主动释放它持有的引擎进程（Codex、Grok 的子进程关掉，Claude 的流式连接中止），下一条消息再冷启动。理由是输入缓存只保留几分钟，一小时后早已过期，留着进程没有价值。

**（d）后台会话答完不立刻关闭输入通道。**适用范围是 Claude 引擎上的 job 会话和分区会话，不含渠道会话。这些会话在模型给出最终回复后不立刻关闭输入通道，而是等它派出的后台子代理全部回调完成再结束本轮。运行时靠 SDK 的 task_started、task_notification 消息跟踪这些子代理。如果 10 分钟没有任何子代理消息（`ALADUO_HOLD_INPUT_IDLE_TIMEOUT_MS`），一个超时计时器强制释放输入通道并记一条警告。渠道会话不启用这一机制，所以前台对话不会因为子代理而拖长。

### 2.3 崩溃恢复就是重读文件

重启后运行时扫描会话目录重建 actor 集合，邮箱里没勾掉的待办就地续跑。第一个 turn 给模型注入一条 `daemon-restart-hint`："你在新的 daemon 进程下运行"，若重启时给了原因（`duoduo daemon restart -r "升级到 0.8.1"`），原因一并带上。这条提示只发给渠道会话，job 会话和分区会话都拿不到。`--wake <会话>` 可以让指定会话在重启后收到一条唤醒消息；它随重启本身传递，即使发起重启的进程死了也不会丢。

实测：重启后 daemon 状态里的 `runtime_id`（这份运行时数据的实例编号）不变，会话和 WAL 完整。这就是"文件系统即数据库"的实际效果。

### 2.4 上下文装配：稳定的进系统提示，易变的进每轮输入

送给模型的文本被分成互不重叠的两块，本文叫两个"注入面"。这是整个运行时最可复用的单点设计。

| 注入面 | 装什么 | 载体 | 为什么 |
|---|---|---|---|
| **系统提示面** | 身份、渠道人格、实例提示、记忆板、运行上下文、job 任务书（1.3 节的六层） | system prompt | 很少变。稳定的开头让引擎侧的输入缓存反复命中，直接降低成本 |
| **瞬时面** | 九类通知块按固定顺序排在用户原文之前，例如：重启提示、时间流逝、被打断时的上下文、job 完成回执、记忆板刚更新的提示 | 前置在用户消息之前的文本块 | 每轮都变，绝不写进系统提示 |

完整顺序：重启提示 → 自动压缩提示 → 网关带外结果（运维命令的执行结果，告诉模型"已生效、勿重复"）→ 时间流逝 → Skip 回卷（模型上一轮用 Skip 跳过的内容）→ 被打断的上下文 → job 完成回执 → job 触发信息 → 记忆板刚更新的提示 → 用户原文。每类通知注入一次就清掉标记，不会混入后续轮次。

**时间信息是以文本注入的。**模型本身没有时钟，两次调用隔 3 秒还是 3 天对它完全一样。duoduo 用三个块把时间送进模型：`<time-context>`（距上次交互超过阈值才注入，默认 60 分钟）、`<job-tick>`（这是第几次例行运行、上次是什么时候）、心跳给分区会话的当前时间。反向的规则同样重要：**系统提示里没有任何时间戳**，因为输入缓存只在开头逐字相同时才命中，一个分钟级时间戳就会让每次的开头都不一样。

用户输入以 `/` 开头时跳过全部注入，只发原文。命令不该混入时间和打断信息。

### 2.5 渠道：每个平台一个独立进程，只做格式转换

每个聊天平台一个独立的小进程，只做转换：把平台事件转成 duoduo 的通用渠道协议，把 agent 的回复转回平台格式。接一个新平台，daemon 一行代码都不用改。以飞书为例：

```
你在飞书群里 @机器人 说话
  │  飞书开放平台 ──WebSocket 长连接──▶ channel-feishu 进程
  │    （长连接由本机主动发起，不需要公网服务器或回调地址）
  │  进程先自己过滤：群里没 @ 机器人就不处理（默认开启）；私聊默认全部放行；剥掉 @ 前缀；下载图片附件
  ▼
channel-feishu ──调用 daemon 的 channel.ingress 接口（本机通道 + JSON-RPC）──▶ daemon（进入 2.1 的六步）
  ▼
channel-feishu ◀──WebSocket 订阅推送（回复 / 流式增量 / 工具动态）── daemon
  │  渲染：纯文本或飞书卡片；处理中给用户那条消息加表情回应表示进度，并随阶段更换（收到、
  │  思考、调用工具、开始输出各一个），回复完成后全部撤掉；流式回复是不断更新同一张卡片；
  │  音频附件发成飞书原生语音消息
  ▼
飞书 API 发回群里
```

五个要点，按架构、配置、运维的顺序：

- **一个群 = 一个会话。**进程把"飞书群 ID（私聊再加用户 ID）+ 工作目录路径的哈希"编成会话键，同一个群固定对应一段连续记忆。所有群共享同一个 agent 人格和内核记忆。首次在群里 `/setup` 绑定工作目录，就是把这条映射写进 daemon 侧的实例配置。
- **协议是通用解耦点。**接钉钉或 Telegram 等于写一个新的独立进程包：入站调 `channel.ingress`，出站开 WebSocket 订阅，首次绑定写 descriptor。协议内置能力协商：进程声明自己能收什么（哪些文件类型、哪些流结束原因等），daemon 对不认识的新语义自动降级，老进程与新版 daemon 保持兼容。
- **配置分两处。**行为配置走三层 Markdown，合并顺序从低到高：`~/aladuo/config/runtime.md`（全局）→ `~/aladuo/config/feishu.md`（种类）→ `~/.aladuo/var/channels/<id>/descriptor.md`（实例）；三层 Markdown 里目前唯一的渠道行为开关是进度卡（"群里要 @ 才响应"的开关另存于实例配置，见下一条）：v0.8.0 起可按渠道开启（`feishu.process_card: replace`），同一张卡片先显示处理进度和正在调用的工具，完成后答案原地替换，不再出现第二张卡片，默认关闭。凭据和过滤策略则是渠道适配器进程自己的环境变量，一起写在 `~/.config/duoduo/.env`，永不进任何 Markdown：飞书 app_id、app_secret；私聊默认全放行（`FEISHU_DM_POLICY=open`），可设为 `allowlist`（只接收 `FEISHU_ALLOW_FROM` 白名单里的人的消息）；群消息另有 `FEISHU_GROUP_POLICY`（open / allowlist / disabled）。当前版本还接受 `FEISHU_DM_POLICY=pairing` 这个取值，但它的行为与 open 完全相同，并没有实现配对流程。
- **"群里要 @ 才响应"是渠道适配器进程执行的**，daemon 只存储开关。平台侧还有一个限制：想让机器人不 @ 也能收到群消息，要在飞书开放平台申请敏感权限。
- **渠道适配器进程崩溃后没有自动重启。**它由 CLI 启动、脱离终端运行，daemon 不知道它的存在。要靠 `duoduo channel feishu status` 发现，手动 `start`。`duoduo upgrade` 会在升级时重装并重启渠道适配器进程，但日常崩溃仍需人工处理。这是当前版本明确的运维负担。

### 2.6 job：由前台委派、结果回到前台的定时任务

job 是用户（或前台会话）主动布置的定时或一次性任务。它虽然在没人说话时运行，但属于"替用户做事"这一侧；第三部分的后台分区是"替自己做事"（自我维护）。两者是两套独立调度：job 由 60 秒扫描器驱动、任务书由人或前台会话写；分区由 37 分钟心跳驱动、提示词由 agent 自己维护。

- **定义是一个 Markdown 文件**，放在 `~/.aladuo/var/jobs/active/<id>.md`。frontmatter 里最需要关心的是五个字段：`cron`（定时规则）、`owner_session`（谁创建的）、`runtime`、`model`（必填）、`acceptance`（必填：怎样算做完，用可以检查的条件写）。此外还有创建时由 daemon 自动写入的 `type`、`created_at`（扫描器用它判断是否到期）和 `cwd_rel`（job 的工作目录，参与生成 job 的会话键），以及可选的 `effort` 和 `prompt_mode` 等配置字段。正文就是任务书。旁边一个 `.state.json` 记录运行历史。`cron` 支持 `@every 2h`、`@in 30m`、`once` 只跑一次、`keepalive` 休眠等待唤醒，以及标准的 cron 表达式；时长可以复合写，如 `1d6h4m`，单位 s/m/h/d/w；写错的规则在创建时就被拒绝。
- **扫描器每 60 秒跑一次**，与 37 分钟的心跳互不相关。到期就为它开一个 job 会话；上一次会话还没结束或正在归档就跳过，不重复启动。
- **谁能创建 job：**前台会话，或者一个 `keepalive` 类型的 job。普通 job 是执行者，它调用 ManageJob 创建新 job 会被拒绝；需要新会话时通过 Notify 告诉自己的 owner。keepalive 也不能创建另一个 keepalive。
- **job 可以给自己改期。**任何 job（包括不能创建新 job 的执行者）都能调用 ManageJob 的 reschedule 给自己设定下一次触发时间，例如 `@in 20m`。这不创建任何东西，是一次性 job 等待某个条件的标准写法。`/loop` 自定节奏的任务也这样实现：每次运行结束前根据本次观察选下一段时长，不再改期就结束。
- **结果回到 owner，没有别的配置项。**失败会唤醒 owner 一轮；成功不唤醒，而是作为 job 完成回执随 owner 的下一轮一起送达（v0.8.1）。理由：失败需要有人处理，成功只需要 owner 下次运行时知道，为一句"做完了"冷启动一整轮不值。在启动前就被取消、或整个运行没有送入任何事件的运行，什么都不投递，由扫描器直接重试；但在启动阶段就报错的运行（例如引擎不可用）仍会向 owner 投递一条失败通知并唤醒它。
- **`/loop` 把一句话变成 job。**在任何前台对话里输入 `/loop 每 20 分钟检查一次 staging 部署，坏了立刻告诉我`，agent 从文字里读出节奏、引擎、模型，以及任务书里是否要在有信号时调用 Notify（投递本身没有可配置项，结果固定回到创建它的会话）；先给出计划——每个 job 的调度规则、引擎、模型，心跳间隔，停止和暂停方式，首次触发时间——等用户确认后才创建。计划里不含成本估算，一个 job 花了多少只能事后在用量账本里查。
- **零模型成本的监控模式：**一个普通脚本（用系统自带的定时器，如 Linux 的 cron 或 macOS 的 launchd）轮询数据源，只在有新数据时调 `duoduo session notify` 唤醒一个 keepalive job；job 判断是否需要上报，需要才 Notify 主会话。空闲期间不花一个 token。

> **给 PM 的三点**
> - "消息、合并窗口、turn"三层解耦是对话式 agent 的成本控制手段：合并省调用次数，插话省打断重跑，常驻流式省冷启动。
> - 可靠性没有用任何额外的服务（没有消息队列、没有数据库）：队列是 Markdown 文件，账本是 JSONL，锁是带存活时间戳的 JSON 文件。定位是单机个人 agent，可审计性最高（人和模型都能直接 `cat`），吞吐上限也在这里。
> - 渠道适配器进程在 daemon 的可靠性体系之外：做产品要么补一个进程守护，要么把手动重启写进运维手册。

## 第三部分 · 自我迭代：它怎么变得更好（本文核心）

> **关键句**：duoduo 的"自我编程"不是改代码，是改文件。运行时把 agent 的人格、记忆、后台分工做成一个 git 仓库里的 Markdown；心跳按 agent 自己可改的轮转表，唤醒一个个一次性、无状态的分区会话去读经验、改这些文件。运行时自己只做确定性的事，其中与自我迭代直接相关的四件是：**发现记忆有问题时写任务单、把任务单只送给声明能处理它的分区、用 git 做可撤销的删除（默认关闭）、用指令指纹通知运行中的会话"指令已变"**（此外还有勾选与重建轮转表、清理过期任务单等维护动作，见 3.3）。每一次记忆或提示词改动都是一个 commit。

### 3.1 自我是一个 git 仓库

"自我"的机器定义就是内核 `.gitignore` 的第一行注释：`# Runtime state (not part of cognitive evolution)`。进 git 的是"认知演化"（人格、记忆、分区提示词）。被忽略的有三类：一是可以从日志重建的运行态（memory 下的 fragments、effectiveness、state，以及 subconscious/inbox）；二是与认知无关的工具杂项（引擎自己的工作目录 `.claude/`、临时文件 `*.tmp`、本地覆盖说明 `CLAUDE.local.md`）；三是因为可能含凭据而单独排除的 `config/runtime.md`。注意 `.claude/` 这条匹配任意层级，所以用户给分区目录加的 `.claude/agents/*.md` 子代理定义也不进 git，不受 git 撤销保护。内核目录 `~/aladuo`（可用 `ALADUO_KERNEL_DIR` 改）的内容：

```
~/aladuo/                          ← git 仓库；首次启动时 git init + 首提交 "memory: genesis"
├── CLAUDE.md                      ← 内核根提示词 "My Inner World"：在这里工作的会话是在修改自己
├── claude-runtime.md / codex-runtime.md / grok-runtime.md / pi-runtime.md   ← 四个引擎的使用说明
├── config/
│   ├── runtime.md                 ← 全局配置层（模型档案、模型/力度默认值）；可能含凭据，被 .gitignore 排除
│   └── stdio.md feishu.md acp.md job.md   ← 各渠道种类的默认配置与人格
├── memory/
│   ├── CLAUDE.md                  ← 记忆板（注入每个渠道会话和 job 会话；出厂 0 字节）
│   ├── entities/<slug>.md         ← 实体档案：人、工具、项目
│   ├── topics/lesson-*.md         ← 纠错规则：一次人类纠正 = 一条"何时触发 → 怎么做"
│   │        groove-*.md          ← 固定流程：重复做过多次的任务收敛出的步骤
│   ├── fragments/<日期>/          ← 证据碎片            ┐
│   ├── effectiveness/<slug>.md    ← 每行记忆的效果记录    ├ 这三个被 .gitignore 忽略
│   └── state/                     ← 运行态              ┘
└── subconscious/
    ├── CLAUDE.md                  ← 后台分区总纲（上游出厂文件，运行时启动时不再覆盖，只有人工触发的刷新流程（3.8）会整文件换新；写着"我能改什么、不能改什么"）
    ├── playlist.md                ← 轮转表（agent 可改）
    ├── inbox/                     ← 出厂带的空目录，列在 .gitignore 里；运行时并不往这里投任务单，实际收件箱在 ~/.aladuo/var/subconscious/<分区>/inbox/（3.4 节）
    └── <分区名>/CLAUDE.md          ← 各分区自己的提示词（agent 可改）
```

git 操作与你的机器隔离：固定作者 `aladuo <aladuo@local>`，`GIT_CONFIG_GLOBAL=/dev/null`，`GIT_CONFIG_NOSYSTEM=1`。它不会用你的签名提交。

提示词层的自我定义在身份提示里，它是全系统的设计前提，值得引用原文：

> *"My continuity is in files, not in any single inference. … My body is this filesystem — tools are my hands, files are my memory, the event log is the trace of everything I've ever experienced."*
>
> *"I don't cite my memory files to the user. I just know things."*

v0.8.x 的身份提示（v0.7.1 尚无）还有一段写作规则，与本文的写法一致：*"a metaphor or flourish in place of a direct statement displays me instead of conveying the idea, and drags in connotations I did not choose. When a literal phrase exists, I use it."*

### 3.2 出厂文件只初始化一次：只补缺失，三类例外

npm 包里的 `bootstrap/` 目录是出厂人格和初始材料。daemon 每次启动都会跑一遍初始化（跑多少遍结果都一样，所以重复跑无害）。首次安装向导 `duoduo onboard` 只写 `~/.config/duoduo/` 下的配置和认证信息，不修改内核。初始化的规则只有一条：**内核为空就全量复制；内核已存在就只补缺失文件，不覆盖。**这一条就是"npm 升级永远不覆盖 agent 已演化的文件"的实现。例外恰好三类，都是上游所有的文件：

1. **身份提示 `meta-prompt.md` 和仪表盘页面 `dashboard.html` 都不落内核。**这两个文件永远不会复制进内核。身份提示在每次装配系统提示时从包内现读；仪表盘页面在每次访问 `GET /dashboard` 时从包内现读。效果：升级 npm 包，身份提示和仪表盘立刻升级；agent 自己写的文件不做任何修改。上游提供的与 agent 自写的在文件层就分开了。
2. **`~/.aladuo/var/` 各子目录里的 `DUODUO.md` 每次启动重新复制。**它们是运行时目录的使用说明。身份提示只教 agent "去运行时目录找 DUODUO.md"，而不把内容写死。
3. **内核 `.gitignore` 每次启动追加缺失的上游忽略项**（只追加，不删除用户自己加的行）。

初始材料里与产品设计最相关的三件：
- `memory/CLAUDE.md` 出厂是 0 字节：记忆从零积累。
- 四个出厂分区的提示词：后台的初始行为，合计约 47 KB（gradient-distiller 约 17 KB、intuition-weaver 约 18 KB、pattern-tracker 约 8 KB、memory-committer 约 4 KB），每次分区会话都先读完自己的那一份。身份提示约 16 KB。
- 各 `DUODUO.md`：按需发现而非硬编码。

**旧分区退休而不是删除。**v0.8.0 把 `memory-weaver` 拆成两个分区、去掉了 `cadence-executor`。老内核升级后这两个目录还在。运行时启动时做三件事：
1. 先确认目录确实是官方那份而不是用户挪作他用的同名目录（判据：`memory-weaver` 仍带有效的 `contract:`，`cadence-executor` 仍没有 `contract:`）；
2. 把分区 frontmatter 里的 `schedule.enabled` 改成 `false`，让心跳不再唤醒它；
3. 在 `~/.aladuo/var/meta/partitions/<分区名>.retired` 留一个标记。分区目录本身和 git 历史都不动。

想继续跑，手工改回 `enabled: true` 即可，运行时不会改第二次。

### 3.3 心跳不调模型；四个条件和轮转表决定谁被唤醒

心跳本身不调用模型。一拍里只有四个条件都放行、且轮转表轮到的分区（最多两个，见第 4 条），才会得到分区会话。

- **心跳**：一个定时器，默认 2,220,000 毫秒（约 37 分钟，`ALADUO_CADENCE_INTERVAL_MS` 可改）。每一拍先广播 `cadence.tick`，再跑一轮不调模型的确定性维护：先做只读检查（lint）——它只测量、不改任何记忆内容，但发现问题时会把结果写成任务单投进相应分区的收件箱，同时清掉运行时先前投递、而本拍检查已不再产生的旧任务单（问题已消失，或该分区已不再消费这类信号；分区自己写进收件箱的文件不动）；若同时开启 `ALADUO_EXP_MEMORY_CHECK` 和 `ALADUO_EXP_MEMORY_FORGET` 两个实验开关，还会用 git 删除已被判定为陈旧孤儿的记忆文件（条件见 4.1）。然后清理已归档会话的残留，最后写一条 `system.cadence_tick` 事件。
- **四个防止空转的条件**（后台引擎侧）：
  1. 重入与停机：上一拍还没跑完就跳过。
  2. **活动指纹**（与 1.6 节的指令指纹无关，只是同样用哈希判断"有没有变"）：对 memory 下 fragments、entities、topics 三个目录的最新修改时间，加上最新一条外部来源事件的 id 算指纹（定时任务的启动与完成事件也算外部来源，见 0.1），没变化整拍跳过。只改记忆板本身不会改变指纹。无外部活动时后台不产生模型开销。
  3. 每个分区有 `cooldown_ticks` 冷却。失败后还会退避，但只有超时和报错两类失败会推迟下次运行：每出现一次，就把下次允许运行的时间往后推一段，推的量随连续失败次数线性增加。上限是超时推到 2 小时、报错推到 4 小时；超时的前两次、报错的第一次不推。分区跑完但输出为空或不合格也算一次失败、会累加连续失败次数，但它本身不推迟下次运行。
  4. 前台优先：只有活跃会话不超过 1 个时才在同一拍多跑分区，每拍最多 2 个。
- **轮转表 `playlist.md`**：`## Current Round` 下的 checkbox，每拍取下一个未勾选的分区；整轮勾完，用所有启用的分区重建新一轮。它是纯文本状态机，且 agent 被明确授权改写它。后台分区总纲原文："Anyone can edit the playlist — including the partitions themselves."
- **一次分区会话**：开一个一次性的引擎会话（不保存历史），工作目录是该分区的目录。送给它的提示词由四段拼成：
  1. 分区自己的 CLAUDE.md 正文；
  2. 分区信息：名字、工作目录、收件箱路径、引擎；
  3. 运行上下文：现在几点、当前有几个会话活跃、内核目录与各类运行时数据（共享记忆、注册表、事件日志、job、收件箱）的绝对路径，以及一行 `duoduo spine` 命令的调用前缀（只给前缀，不带用法；怎么用它读日志写在后台分区总纲和各分区自己的提示词里）；
  4. 收件箱里的任务单（有才附）。

  超时即中止本次执行，迟到的结果只记一条日志后丢弃。结果写成一条 `agent.result` 事件（`tick_type: "subconscious"`）和一条用量记录，所以后台每次执行的成本都记到具体分区。分区可以在 frontmatter 里指定引擎、模型、推理力度；指定的引擎不可用就记一条 `runtime_unavailable` 错误并退避，不静默换引擎。
- 后台分区总纲的自述："Stateless. No memory of last time except what's written to files." 跨拍协作全靠文件，任何一拍崩溃都可以整段重跑。

### 3.4 经验变成记忆：完整流水线

这是全框架最核心的一段。**运行时负责发现问题，模型负责处理问题。**

```
经验（WAL 里的外部事件：用户说的话、任务的结果）
  │
  │ ① 只读检查并写任务单（代码，不调模型）
  │   心跳里的只读检查扫描记忆目录，产出带完整上下文的任务单（.pending 文件），信号名与附录 B 一致：
  │   某天的经验还没处理 → scan-gap；碎片积累了 → fold-gap；
  │   记忆板超 100 行或某行超 200 字符 → claude-compress；链接断了 → claude-lint；
  │   记忆板里有标题行 → claude-flatten；实体档案该收敛了 → entity-converge；
  │   同一个 slug 既是实体又是主题 → merge；规则节点格式过时 → node-converge；
  │   行为类规则节点已有效果记录、但仍是旧的 "# Pattern:" 写法 → revise（要求重写成 Lesson/Groove 格式；
  │     效果趋势只决定先处理哪一条，变弱的排在前面；已被裁定为应删除的变弱规则不发）；
  │   文件不可达 → orphan-newborn / orphan-islands；哪些记忆真的被读过 → activation-report
  │   每类每拍最多发一条（例外：新生孤儿文件每个各发一条）；同名任务单没被处理掉之前不重复投递
  │   只投给契约声明消费该信号的分区（契约过滤，定义见 4.1）
  ▼
分区收件箱（~/.aladuo/var/subconscious/<分区>/inbox/*.pending）
  │
  ├─▶ gradient-distiller（提炼证据）
  │     用 duoduo spine cat --interval … --kind external 读某一天某个时间段的外部事件，
  │     对每条事件逐行对照记忆板：这一行起作用了？该起作用没起？没有相关证据？
  │     写成 fragment 文件（memory/fragments/<日期>/），每条回指记忆板具体某一行，
  │     标记 STRENGTHENING（增强）/ WEAKENING（削弱）/ NEUTRAL（中性）/ NEW_SIGNAL（新信号）。它不改记忆板。
  ▼
  ├─▶ intuition-weaver（改记忆板）
  │     记忆板、效果记录、entities/ 的唯一写者。
  │     把碎片折算成每行的效果记录（现状快照），然后决定：
  │     保留 / 改写触发条件或方向 / 移出记忆板 / 新增 / 调整顺序 / 修指针。
  │     规则："每一处改动都要有行级证据；没有证据就不改，只报告缺口。"
  ▼
  ├─▶ pattern-tracker（提炼规则）
  │     把"人纠正过我一次"写成 lesson-*，把"同一任务做了 N 遍"写成 groove-*。
  │     新节点必须同拍从一个可达的档案里链接过来，不许产生没人引用的知识。
  ▼
  └─▶ memory-committer（git 提交）
        每次运行把允许提交的文件范围（memory、subconscious、config 三个目录，不含后台分区总纲）内的全部改动合成至多一个 commit。
        跳过本拍内还在被写的文件（下一拍再提交）；剩下的改动如果全是空白或行序调整，本拍不提交。
        它不审内容："Version history is the safety mechanism — a bad line that lands in a commit
        is one revert away from gone."
        提交信息格式：<scope>(<facet>): <what evolved>，scope 是 memory / subconscious / config 之一，
        facet 是一个简短的自由标签，说明改了什么（上游示例：memory(dossier): …、subconscious(self-program): …）；
        像 "update files" 这种只说做了事、不说演化了什么的提交信息不被接受
  │
  ▼
记忆板已被改写 → 下一次前台处理时指令指纹比对发现"记忆板变了"（1.6 节）→ 新会话装入新版，在跑的会话收到更新提示
```

注意生效顺序：前台会话读的是磁盘上现在的 `memory/CLAUDE.md`（git 术语叫"工作树"），不是 git 最近一次 commit 里的版本。所以 weaver 改完记忆板，新开的会话立刻用上，在跑的会话下一轮收到提示；committer 的提交是为了留下可回滚的历史，不是生效的前提。

distiller 与 weaver 按写权限切开——"算该往哪改"和"真的去改"由两个分区分别负责，各自只写自己的目录（碎片目录 / 记忆板与 entities）（v0.8.0 起，此前是一个分区内部的三个子代理，见附录 D）。同一版本新增的 **activation report** 是运行时统计的一份报告："最近若干个有人交互的日子里，记忆板每一行指向的档案被前台真正读过几次"，投给 weaver。一行记忆的指针从来没人打开，说明这行没起作用。窗口按"有人交互的天数"算，无人交互的一周不会让记忆过期。

上游把这条流水线叫 "text gradient"，借用机器学习里"梯度 = 该往哪个方向改"的说法：碎片告诉 weaver 每一行该往哪改，activation report 告诉它哪些行根本没人用。weaver 能做的只有五种动作：新增、改写、调序、把一行移出记忆板（上游也叫 retire，与 3.2 的分区退休无关）、修指针。这只是一种说法，真正执行的仍然是模型。

### 3.5 三个防止正反馈回路的设计

自治系统最常见的失败是正反馈回路：自己产生的信号被自己当成新证据，越放越大。duoduo 在三处阻断了这种回路。

**1. 证据链可复算。**distiller 的碎片必须写明它检验的是记忆板哪一行；weaver 要改一行的内容（改写方向、移出、新增）之前，必须先拿到这一行的行级证据——通常就是读这一行的效果记录，也可以是任务单附带的轨迹证据，或"双来源冷"：activation report 测得这行指向的档案在整个窗口内没人读过，并且没有更新的碎片引用这一行（两项必须同时成立）；没有证据就不改，只在报告里写明缺口。只有两类纯形式修复不需要效果证据：删除记忆板里的标题行（标题行没有指针，按构造就没有效果记录），以及把一行里多写的细节下沉回它指向的档案（内容只是挪位置，行为和指针都不变）。"事件 → 证据 → 效果 → 改写"每一环都是文件，模型不能无依据地声称"这条经验很有效"。

**2. 系统噪声进不了记忆。**只有外部事件（用户消息、任务结果）能成为证据；运行时自己产生的事件（来源为 `cadence`、`meta`、`system`、`runner`、`route`、`gateway`，即心跳、后台会话、系统维护、执行器、路由、网关）一律不算。这条规则在两处落实：
- distiller 读日志用的命令 `--kind external` 按回合过滤：它保留所有来自外部的事件；其中由用户消息打开的那一回合，还会把回合内模型的工具调用和回复一并印出来，但只是让 distiller 看清当时发生了什么，提示词规定不能拿它们本身当证据。job 会话的外部事件只输出事件本身，不展开回合，其结果摘要就是全部证据。
- weaver 的提示词明写"只有外部事件能成为记忆证据"。

**3. 信息只能单向流动。**

```
外部世界 ──WAL──▶ 后台分区      只有外部事件能变成记忆证据
后台分区 ──▶ 前台               只有三条窄通道：记忆板（新会话直接注入；在跑的会话下一轮收到更新提示）、
                                档案文件（前台按 [[slug]] 指针按需读）、
                                Notify 通知（从不打断前台）；碎片、效果记录、事件日志前台从不直接读
前台 ──▶ 后台分区               前台会话不能直接给后台分区下指令；前台的经验只能经 WAL 被后台读到
运行时 ──▶ 模型                 只发带上下文的任务单，不改记忆板、档案和分区提示词正文。运行时自己直接写的内核文件只有
                                三类辅助状态：轮转表的勾选与重建（3.3）、退休分区的启用开关（3.2）、忽略清单的上游条目（3.2）；
                                此外只有默认关闭的遗忘 GC 会动记忆文件（4.1）
分区 ──▶ 分区                   禁止改对方的提示词；跨分区的需求写进自己的最终报告
运行时 ──▶ 收件箱               收件箱由运行时填充；分区唯一能做的写操作是删掉自己的任务单表示已处理
```

给自治 agent 画这张信息流图，逐条问"这条边会不会形成正反馈"，比增加功能更重要。

### 3.6 记忆分层：上下文窗口是稀缺资源

自我迭代的产出要进入模型上下文才有用，而上下文窗口有限。duoduo 建了三层记忆，分层结构与 CPU 的缓存层级类似：

| 层 | 载体 | 进入方式 | 预算与规则 |
|---|---|---|---|
| **L1 记忆板** | `memory/CLAUDE.md` | **每个新的渠道会话和 job 会话自动注入**系统提示，模型不用主动读（为空时跳过这一层；分区会话只拿到路径，自己读） | 预算 100 行、每行 200 字符，超了就发 claude-compress 任务单 |
| **L2 档案** | `[[slug]]` 指向的 entities、lesson、groove 文件 | **默认不读**，模型按需 Read | 身份提示规定做高风险动作前必须先打开档案 |
| **L3 原始日志** | WAL 事件日志 + fragments | 只有分区会话批量读，经 `duoduo spine cat` 命令 | 前台从不直接读；经提炼才能进入上层 |

L1 的细节：每行 = 触发条件 + 一句方向 + 一个 `[[slug]]` 指针，不许有标题；不需要展开步骤的简短规则可以不带指针。计数不计空白，一个 `[[slug]]` 指针算 1 个字符，两个上限可用 `ALADUO_MEMORY_MAX_LINES`、`ALADUO_MEMORY_MAX_LINE_CHARS` 改。行的顺序本身也有意义：模型对一段文本开头和结尾的内容采用率最高，所以最重要的放头尾。

L2 的硬检查点：对一个有档案的实体或流程做破坏性操作、写文件、通知人、或给出确定性建议之前，必须先打开那份档案。简单问答不展开。

**一个记忆文件会不会被运行时自动清理，不看访问次数（访问次数由 activation report 统计、交给 weaver 裁决），只看它能否从记忆板出发沿 `[[slug]]` 链接走到**（从记忆板做一次广度优先遍历得到可达集合）。走不到的文件是孤儿，再分三态：被别的文件引用的叫 ISLAND，只是没接到板上；剩下的按文件最后修改时间分——距今不到 48 小时的叫 NEWBORN，先给它的写者发一条 orphan-newborn 警告；超过 48 小时的叫 STALE。时间只在这一处起作用，而且看的是修改时间：改动过一个 STALE 文件，它就重新回到 NEWBORN。只有 STALE 可能被遗忘，而且它的写者分区必须已声明能接收 orphan-newborn 警告（收不到警告的分区，其孤儿永远不删）；运行时并不记录某个文件是否真的收到过警告，三态每次都按修改时间和是否被引用现算。遗忘是 `git rm`，历史还在（完整条件见 4.1）。

档案里每条主张都标明它是哪一类知识：`[observation]` 记录的事实、`[inference]` 推断、`[instruction]` 承诺的规则、`[conditional: 事件]` 仅在某事件发生时有效、`[hypothesis (unratified)]` 未验证的假设、`[superseded 日期: 新结论]` 已过时。冲突时的规则：本轮观察到的新事实可以推翻档案里的 observation 和 inference；但不能推翻 instruction，只能判断"这条规则的前提还成立吗"。例如档案说"部署前必须跑测试"，今天测试跑得很快也不能因此跳过。

一行能否留在板上由 3.4 的证据决定：WEAKENING 的行是改写或删除候选，窗口内无人读且无新碎片的行移出记忆板。

> **给 PM 的一点**：这套"L1 硬预算 + L2 指针按需展开 + L3 提炼进入上层"是对"RAG（每次检索相关文档放进输入）还是长上下文（把所有资料一次全放进去）"之争的第三种回答：用预算限制系统把知识压缩成短规则，把细节留在指针后面。做 agent 记忆的产品都会遇到"记得越多、上下文越糟"的问题，duoduo 的答案是为记忆设预算和分层。

### 3.7 自改的边界：授权写在提示词里，硬边界在代码里，所有权按文件分

**授权清单**（后台分区总纲 `subconscious/CLAUDE.md` 原文，后台分区的授权规则）：

> 可改：自己分区的 CLAUDE.md（改进工作方式）；新建分区目录（增加新能力）；playlist.md（调整节奏）；memory/CLAUDE.md（"to shape how all of me thinks"）。
>
> 不可碰：Spine 事件数据（"不可更改的历史"）；锁文件；收件箱目录（运行时填充，分区只能删掉自己的任务单表示已处理）；job 调度（重复性需求写进最终报告，不自己建 job）；其他分区的 CLAUDE.md；任何分区的 `contract:` frontmatter（机器读的声明，归运行时所有）。

这份清单是提示词层的约束，模型理论上可以违反。真正硬执行的边界见 4.1。

**怎么改**：没有任何"SelfEdit"专用工具。每个分区会话以自己的分区目录（`~/aladuo/subconscious/<分区名>/`）为工作目录启动，改自己 = 在这个目录里用普通的 Edit、Write、Bash。对默认的 Claude 引擎来说，工作目录只是起点，不是沙箱：用绝对路径照样能读写内核的其他文件（授权清单里的 playlist.md、memory/CLAUDE.md 都在分区目录之外，Claude 分区就是这样改它们的）。分区若在 frontmatter 里配置为 Codex 引擎则不同：Codex 会话在沙箱里启动，默认级别 workspace-write（可用环境变量 `ALADUO_CODEX_SANDBOX` 改为 read-only 或 danger-full-access），读任何文件不受限，但只能写自己的分区目录；默认配置下它写不了 playlist.md 和 memory/CLAUDE.md，授权清单里这两项对 Codex 分区实际上不成立。

**内容质量由谁检查？**v0.7.1 及之前，memory-committer 提交前会对每一行做五道内容审查：这一行是否写清了触发条件、下一步行动方向和要调用的技能或指针；是否只是在描述记忆系统自身而不指导对外行为；否定式规则是否给出了可识别的触发场景和具体替代做法；是否只是事件回顾、变更记录或运行状态；来源是否仅来自运行时内部而没有外部佐证。任何一行不过关整个文件就不提交。v0.8.0 把审查全部删掉了。理由：前台会话读的是磁盘上的文件，不是 git 里的版本（3.4 节流水线图之后的"生效顺序"说明），所以拦住提交并不能拦住坏内容生效；反而因为没进 git，那行坏内容连 revert 都没法用。既然拦不住，不如全部提交、靠历史回滚。现在的检查点移到了三处：写者自己的证据规则（weaver "没有证据就不改"）、来源边界（内部噪声不能成为证据）、以及 git 历史（任何一行都可用一次 revert 撤销）。

**文件所有权清单**是理解这套治理的关键。duoduo 里的文件是人、模型、运行时三方共同书写的，但每一份有明确的所有者：

| 文件 | 所有者 | 其他方的权限 |
|---|---|---|
| WAL 事件日志 | 代码（只追加） | 人和模型只读 |
| 会话 mailbox | 代码 | 代码写指针、代码处理、代码删除已完成条目；人和模型都不该改 |
| playlist.md | 三方共同书写（代码勾选并重建轮次；分区和人都可直接改写） | checkbox 是三方共用的协议：每拍由代码把 `- [ ]` 改成 `- [x]`，整轮勾完由代码重建新一轮 |
| 记忆板、entities | 模型（出厂分工下 intuition-weaver 是唯一写者；后台分区总纲本身允许任何分区改记忆板） | 代码只测量，唯一例外是默认关闭的遗忘 GC（4.1）；人可改（git 留痕） |
| 效果记录 | 模型（intuition-weaver 唯一写者） | 不进 git；由 weaver 从碎片整文件重新生成，人改了下次会被覆盖 |
| lesson-*、groove-* | 模型（pattern-tracker 唯一写者） | 代码只测量；人可改（git 留痕） |
| fragments | 模型（gradient-distiller） | 不进 git，可从日志重建 |
| 各分区 CLAUDE.md 正文 | 该分区自己 | 别的分区禁改；升级经显式流程 |
| `contract:` frontmatter | 上游（经人工触发的刷新流程更新，3.8） | 运行时只读它；提示词明令模型不得修改 |
| 后台分区总纲（`subconscious/CLAUDE.md`） | 上游 npm 包 | committer 不提交它；升级刷新时整文件覆盖 |
| 身份提示 meta-prompt.md、`var/**/DUODUO.md` | 上游 npm 包 | 随升级换新；前者不落内核，后者每次启动重新复制 |
| `schedule:` frontmatter | 人（成本调参） | 升级合并时刻意保留 |
| 锁文件、索引、state.json | 代码 | 任何一方都不应手改 |

这张表回答了 PM 必问的一个问题："它会不会把自己改坏？"能改坏的范围被所有权划得很小，且全部在 git 里。

### 3.8 升级与演化互不干扰

agent 的"自我"有两条独立的演化线：上游发版，和 agent 自己的演化。四个机制把它们分开：

| 机制 | 效果 |
|---|---|
| 只补缺失文件（3.2） | 内核已存在时，代码升级只补缺失文件，不覆盖 memory、subconscious、config 里 agent 自己写的任何文件。例外只有 3.2 列出的三类上游所有的文件，以及退休分区的 `schedule.enabled`（改一次） |
| 身份提示留在包内现读（3.2） | 身份提示随 npm 升级即时更新，不动内核 |
| 分区提示词升级是人工触发的流程 | `duoduo-runtime-admin` 技能的 subconscious-refresh：拉取 → 对比 → 合并 → 提交一个回滚点 commit |
| 契约过滤（4.1） | 能力开关与提示词版本写在同一个文件里，分区刷新到带声明的版本后就不会出现"旧分区误解析新信号" |

刷新流程的合并规则：正文和 `contract:` 用上游的；`schedule:`、`runtime:`、`model:`、`effort:` 保留本地的，因为它们是用户调成本的设置。技能原文："This commit is the rollback point. The user can always `git revert` it if the refreshed prompts misbehave."

**"回滚点"要说清楚**：运行时没有任何自动回滚代码。所谓回滚点，是"每次认知演化都留下一个可 `git revert` 的提交"。回滚动作永远由人（或模型经 Bash）执行。这是刻意的：自动回滚需要"判断坏了没有"，而判断属于模型和人，不属于运行时。

> **给 PM 的三点**
> - **duoduo 重新定义了"自我迭代"的安全形态：迭代的是提示词的结构与分工（哪些分区、各自做什么、按什么顺序）和知识，不是代码。**迭代能力很完整（能新建分区、能改轮转表、能改记忆板），但全部发生在 git 管理的文本里，每一步可 diff、可 revert、可审计。对比另外两个框架（详见 [`AGENT_FRAMEWORKS_COMPARISON.md`](./AGENT_FRAMEWORKS_COMPARISON.md)）：hermes 只允许 agent 改知识、不允许改自己的行为设定（更保守）；pi 框架允许 agent 给自己写代码扩展、但不会自己主动发起（更激进：pi 自身没有内置权限系统，安全边界交给外层的容器或微虚拟机，自我扩展改完也没有验证步骤）。duoduo 取中间态并配了最完整的安全约束。
> - **自我迭代被做成一条有明确失败语义的流水线**：只读检查发现问题 → 任务单 → 分区处理 → git 入库 → 指令指纹生效。任务单积压可见、分区超时退避、每步都有文件。想给自家 agent 加"学习能力"的团队，可以照搬这个流水线结构，把"记忆"换成任何领域资产。
> - **敢让它改自己，靠四层安全机制**：git 历史（一切可回滚）、写者的证据规则与来源边界（无效证据进不了记忆）、契约过滤和工具白名单（硬边界）、指令指纹比对（变更显式生效，不静默漂移）。缺任何一层，"自我编程"都会从优点变成风险。

## 第四部分 · 边界、成本与失败

> **关键句**：自治 agent 的约束分两层：**软约束写在提示词里（模型可能违反），硬边界写在代码里（绕不过）。**duoduo 的硬边界刻意很少，只覆盖"不可逆伤害"和"持续消耗成本"两类风险；其余交给提示词、证据规则和 git。知道哪些是软、哪些是硬，才能正确评估风险。

### 4.1 硬边界清单（代码强制，模型绕不过）

| 边界 | 防什么 | 机制 |
|---|---|---|
| **工具白名单** | 无人值守时会话被审批弹窗阻塞、逃逸、能力失控扩张 | Claude 会话默认只拿到 16 个核心工具，联网类默认关闭；分区会话默认只有 6 个。要加工具只能在配置里显式追加 |
| **契约过滤（contract）** | 检查信号误投、版本错配 | 任务单只投给 `contract:` 里 `consumes` 列表（"我接收哪几类信号"）声明消费该信号的分区 |
| **写锁与归档屏障** | 并发写坏状态 | 同一个数据目录只允许一个 daemon；同一会话的状态改动在进程内串行；正在归档的会话拒绝一切唤醒 |
| **遗忘 GC（孤儿文件自动清理）** | 误删记忆 | 运行时唯一会主动删记忆文件的地方，默认关闭；删除走 `git rm`，可恢复 |
| **指令指纹比对** | 自我改了却不生效，或静默生效 | 指令指纹变了就按 1.6 节的规则显式处理：只有记忆板变了则通知在跑的会话读新版（Claude）或 fork 线程（job 创建的 Codex 会话）；身份、人格、任务书变了则重建或 fork 会话。日志留痕 |
| **WAL 只追加** | 篡改历史 | 事件日志没有更新或删除的代码路径 |
| **控制面分层** | 本机其他程序或网页驱动你的 agent | 默认只有两个入口：本机 unix socket（文件权限 0600，即只有本系统用户可读写，全功能）和 `127.0.0.1:20233`（只读 6 个方法）；远程完整控制需同时设三项环境变量 |

各条的细则：

- **工具白名单。**16 个核心工具是 Bash、Read、Write、Edit、Grep、Glob、Agent、TaskOutput、TaskStop、Skill、ToolSearch、TaskCreate/Get/Update/List、SendMessage；WebSearch、WebFetch 等联网类工具默认关闭。三处追加入口（渠道、job、后台分区各自的 `claude.tools`）的结果取并集，只增不减。分区会话默认只有 Bash、Read、Write、Edit、Grep、Glob 六个。"不在白名单里"即"关闭"，比逐项禁用更难绕过。Codex 的内置工具无法禁用，这道边界只对 Claude 完整生效；Codex 靠沙箱（默认只能写工作区，见 1.2 表）。
- **契约过滤。**分区 frontmatter 声明了 `contract:` 但其 `consumes` 列表里没有某类信号，这类信号的任务单就不投给它；没有声明 `contract:` 的分区（未刷新的旧分区、用户自建分区）退回到环境变量 `ALADUO_EXP_MEMORY_CHECK`，开着才投，默认关；目录名与声明的分区名不一致不投递（防提示词被复制冒名）；分区被禁用不投递；四个内置分区都不消费任何信号、且遗忘开关没有打开时，整轮检查直接跳过（遗忘开关打开时这一轮只做孤儿文件状态扫描和遗忘删除；用户自建分区是否消费信号不参与这个整轮判断，只在逐条投递时生效）。
- **写锁与归档屏障。**跨进程的 daemon 写锁记录进程 id、开机 id、存活时间戳；持有者已死或时间戳过期可被接管。进程内另有按会话键的互斥。
- **遗忘 GC 的删除条件。**要真的删掉一个文件，必须同时满足：两个实验开关（`ALADUO_EXP_MEMORY_CHECK` 与 `ALADUO_EXP_MEMORY_FORGET`）都打开；文件最后修改距今 48 小时以上（状态为 STALE，三态定义见 3.6）；没有任何别的文件引用它；该文件所属的分区已声明能收到孤儿警告（收不到警告的分区其孤儿永远不删）。删除走 `git rm`（仍在历史里、可恢复），中途失败自动回滚；发现 git 正被别的程序占用（`.git/index.lock` 存在）就放弃。
- **控制面分层。**控制面是外部程序指挥 daemon 的入口。unix socket 只有同一个系统用户能打开，可以做任何操作。TCP 端口只放行 6 个只读方法，其余返回 "Method not available on read-only endpoint"，并检查请求声称的目标域名，防止恶意网页借浏览器绕过"仅本机"限制。想从别的机器完整控制，需要同时设置 `ALADUO_DAEMON_HOST`（一个别的机器能访问到的地址）、`ALADUO_DAEMON_TOKEN`（请求里附带的一串口令，用 `duoduo daemon token new` 生成）和 `ALADUO_REMOTE_PORT`（必须与只读端口不同）三项。规则是：三项同时设置时，daemon 就在指定地址上开一个带口令的完整控制监听（即使地址是 127.0.0.1 也会开，只是别的机器访问不到）；三项没有同时设置时，daemon 正常启动、不开远程监听，但有两种配置会被拒绝启动：把 `ALADUO_DAEMON_HOST` 设成非本机地址却没有口令，或有口令却没有远程端口。

**软约束**即 3.7 的授权清单，全部在提示词层，靠模型自律 + 证据规则 + git 兜底。

评估风险的正确问法是："如果模型违反了 X，会发生什么？"对 duoduo：违反软约束 → 改动都在 git 里，人能看到 diff 并回滚，下一拍的只读检查能发现坏链接和超长；想突破硬边界 → 代码路径不存在。

### 4.2 成本控制

常驻加后台自治，意味着没人说话也在花钱。duoduo 的成本控制措施有多项，效果叠加：

- **入口分流**：运维命令不调模型（2.1）。
- **合并消息**：最多 5 条并成 1 次调用（2.2（a））。
- **缓存优化**：稳定的系统提示、系统提示里没有时间戳（2.4）、记忆板变了不重建会话（1.6）、常驻流式会话（2.2（c））。
- **空闲自动压缩**：两个键都在渠道配置里：`auto_compact_idle_minutes`（空闲多少分钟后触发）和 `auto_compact_min_context_tokens`（上下文至少多大才值得压）；两个都大于 0 才启用，默认都不设。触发时趁引擎的输入缓存还没过期，自动执行一次 `/compact`。对 Claude、Grok、pi 三种引擎的会话都生效，只有 Codex 会话被跳过；Grok 和 pi 的压缩结果不带压缩后的 token 数，阈值不会自校准，需要按 `smart-compaction` 技能里的收支平衡公式手动设定。
- **空闲回收引擎进程**：空闲 1 小时后释放子进程（2.2（c））。
- **后台四个条件**：重入与停机、活动指纹、冷却与失败退避、前台优先四个条件同时生效（3.3）。v0.8.0 起 weaver 每次运行的工作量也有预算上限，按重要性排序处理，做不完的下拍再来。
- **按引擎设便宜的默认模型**：v0.8.1 新增的按引擎默认模型（`<runtime>.model`）作用于渠道会话和后台分区：分区 frontmatter 没写 model 时，取全局配置里该引擎的默认模型，可以借此给分区统一配便宜模型（1.5）。job 不走这条默认值：job 的 `model` 字段必填，缺了就拒绝创建，上游文档明说"省略它从来不是便宜的选项"，因为早期版本会落到主机的兜底模型，而兜底可能是最贵的模型。
- **全链路账本**：每次调用（含每次分区会话）写一条用量记录（4.4）。账本没有自动保留策略，常驻主机会累积几百 MB，`duoduo-runtime-admin` 技能有归档流程。

尽管如此，"后台在有变化的心跳拍上消耗"仍是这类产品的固有成本项（`ALADUO_CADENCE_INTERVAL_MS` 可调），部署前要给用户讲清楚。

### 4.3 失败语义：每个部件回答"失败了会怎样"

评估一个无人值守系统，与其看功能清单，不如逐个问"这一步失败了会怎样"。duoduo 几乎每个部件都有明确答案：

| 失败场景 | 处置 |
|---|---|
| 引擎调用抛错 | 统一以 `[duoduo:drain-error]` 开头的文本回给用户（常见形式是 `agent turn failed at <阶段>` 后接错误摘要和诊断提示；个别在调用引擎之前就拒绝的情况措辞不同，但前缀相同），并写一条 `agent.error` 事件。不静默，不暴露堆栈 |
| 续接旧会话失败 | 自动降级为无历史重跑，写一条 `stage: "resume"` 的错误事件 |
| 引擎不可用 | 四种处置各不相同（1.2）：Claude 在收到消息时报错并提示修复；Codex 的渠道会话和 job 会话静默换成 Claude，只留警告日志，**用户拿到的是一个换了引擎的会话**；Grok 会话仍会创建、第一条消息报错、不降级；pi 缺模型指针时发消息报错并说明怎么配 |
| 分区会话超时或失败 | 中止本次执行，退避后再试（数字见 3.3）；连续失败不影响整个心跳；分区抛出的错误信息完整进日志 |
| 邮箱里有坏文件 | 移入隔离区，不阻塞其余待办 |
| 定时任务的结束状态 | 六种显式结束状态；每次运行在被认领时记下一个认领游标，结算时游标对不上就判为过期运行、结果不写 |
| 会话结束后又来消息 | 会话收尾时再检查一次自己的邮箱，确有新消息就再跑一轮，每次检查到新消息都会再跑，保证不丢消息；只有在邮箱读取出错、无法确认有没有漏掉消息时才保守地多跑一轮，这种保守重跑只允许一次，之后停下等待外部唤醒 |
| 后台子代理迟迟不回 | 输入通道保持打开，但若 10 分钟没有任何子代理消息，超时计时器到期后强制收尾（2.2（d）） |
| 遗忘 GC 中途失败 | `git reset` + `git checkout` 整体回滚，宁可不删 |
| daemon 关闭时还有工作在跑 | v0.8.0 起等待在途工作，最多等 30 秒；超时放弃时记一条日志，列出被放弃的会话名和所用引擎 |
| daemon 自身崩溃 | 分两种情况：遇到未捕获的同步异常（`uncaughtException`）视为状态可能已损坏，直接退出、把重启交给外部进程管理器；遇到未处理的异步错误（`unhandledRejection`）则只记一条日志，daemon 继续运行，目的是一个请求处理器里的异步错误不拖累整个 daemon |
| 渠道适配器进程崩溃 | **无自动重启**（2.5）：需人工 `channel start`，期间消息滞留平台侧 |

定时任务的六种结束状态：从未开始就失败 / 开始后失败 / 确认前取消 / 确认后取消 / 一条事件都没送进去 / 成功。一次运行按它开始时的定义结算，中途改了定义不影响。

规律：每条失败路径都收敛到"写日志 + 退避或降级 + 不扩散"三件事，而且失败本身也是 WAL 事件，可以复盘。反面是业务层把失败 catch 掉后只打一行日志就当没发生；daemon 对异步错误的兜底日志是最后一道防线，不是常规的错误处理手段。那种把所有失败都吞掉的系统无法维持一周无人值守。

### 4.4 可观测性：成本、事件、自我变更都可追溯

对自治 agent 而言，可观测性不是运维的附加项，而是信任的来源：用户敢让它常驻，是因为随时能查"它花了什么、做了什么、把自己改成了什么"。三条线各有读取面：

- **成本**：每次调用（含每次分区会话）写一条用量记录：四类 token 数（新读入、写入缓存、命中缓存、输出）、成本、工具调用次数、首字延迟、实际服务本轮的模型。"该跑什么"和"实际跑了什么"是两条独立记录，允许不一致，例如 Codex 已开始的会话保持启动时的模型，直到下一次 fork。账本记"实际"而不记"请求"，好处是接第三方中转服务时，它未经声明换成便宜模型也能在账本上看出来。出站回执携带本条回复的成本、模型、上下文占用，供渠道渲染页脚。
- **事件**：四个读取面。`spine.tail` RPC：按条数上限和事件 id 游标读取最近的事件，调用方靠反复调用它来跟进新事件，只读端口也允许调用，dashboard 就是每几秒轮询一次它。`duoduo spine cat / show`：把工具调用和结果折叠在一起，全文不截断，带头尾计数；v0.8.0 专为"agent 读自己的历史"做的读取面。dashboard：单文件零依赖，v0.8.1 重做，事件流可点击过滤。`duoduo daemon status`：列出此刻正在执行的每个工具调用（哪个会话、哪个工具、开始多久）；它只跟踪工具调用，模型正在生成文本、还没调用工具时列表同样为空，所以"列表为空"不等于"没有事情在发生"。
- **自我变更**：内核 git log 是指令与记忆的变更历史，每条提交信息说明演化了什么；指令指纹漂移在日志留 `fp_old → fp_new`。"它为什么变成这样"永远可以追溯。

> **给 PM 的两点**
> - 评估任何自治 agent 时先要一份"硬边界清单"（形如 4.1 的表）；给不出的，把它所有约束都当软约束看待，按"模型违反了会怎样"逐条追问。
> - duoduo 的信任模型是**单机单用户**：完整控制面靠文件系统权限，默认不弹审批。它不是能给多个用户同时共用、暴露到公网的服务（多租户）。这是产品边界，不是缺陷。

## 第五部分 · 总评：十二个可借鉴的设计，三个局限

**十二个可直接复用的设计**（不分先后）：

1. **双注入面 + 时间信息注入**（2.4）：稳定认知进系统提示，易变状态（含时间）进每轮输入。任何对话 agent 当天就能改，立刻降低缓存成本。
2. **入口分流**（2.1）：网关层判定"要不要动用模型"，运维命令零 token。
3. **合并消息 + "Reply once"**（2.2）：连发短句并成一个 turn。
4. **边界感知的打断**（2.2）：只在工具调用边界打断；插话优先于打断；后台永不打断前台；一次只准入一个 turn。
5. **先写日志再执行，重复消息重放回执**（2.1）：一条规则换来可重放、可审计、崩溃恢复三个属性；重复消息得到与首次一致的回复，对接 IM 的正确语义。
6. **软硬分层 + 硬边界清单**（4.1）：把不可逆伤害与持续消耗成本写进代码，其余放提示词并配可回滚存储。
7. **失败语义清单化**（4.3）：每个部件回答"失败了会怎样"，全部收敛到"写日志 + 退避或降级 + 不扩散"。4.3 的表可以当验收清单用。
8. **装配共用、命令分叉的多引擎方案 + 指令指纹比对**（1.3、1.4、1.6）：区分"记忆变了"和"身份变了"。
9. **checkbox 文件当轮转表 + 文件所有权清单**（3.3、3.7）：文件是人、模型、代码三方共同书写的接口，但每份文件有唯一所有者。
10. **记忆分层与预算**（3.6）：L1 硬预算、L2 指针按需展开、L3 原始日志提炼进入上层；加上"这行记忆有没有被读过"的使用统计。
11. **"代码测量、模型裁决"的流水线 + 单向信息流**（3.4、3.5）：只读检查发任务单 → 分区处理 → git 入库；每条信息流边都问过"会不会形成正反馈"；系统噪声进不了记忆。
12. **自我 = git 仓库，推理 = 外部引擎**（3.1、1.1）：认知演化记录为可 revert 的提交；工具执行循环整个由引擎承担，运行时因此代码量极小。

**三个局限：**

1. **闭源 + 单机**：License 为 Private，不能复制它的代码另起项目；所有调度都在一个进程的内存里完成，不能靠加机器提高吞吐；控制面靠文件权限而非账号体系。可以借鉴它的架构，不能复用它的代码。
2. **自我迭代止于提示词的结构与知识，且没有"改完验证"步骤**：它不能给自己写新工具或新代码（对比 pi 框架），也没有对"改完之后变好了没有"的自动验证。效果记录和 activation report 是事后证据，不是发布前测试。
3. **后台成本与引擎绑定**：后台的模型费用随变化而生、上限由心跳间隔决定，只有记忆或外部事件自上一拍以来有新变化的那一拍才会产生模型费用（每拍最多两个分区）；引擎是四个固定值（v0.8.0 起含 pi），换第五家仍要等上游。

## 附录 E · 对本仓库长期目标的启示

本仓库的长期目标是做一个会做金融预测、并用结果不断修正自己判断的 agent（细节见 [`AGENT_FRAMEWORKS_COMPARISON.md`](./AGENT_FRAMEWORKS_COMPARISON.md)）。duoduo 最值得复用的是第五部分的第 5、10、11 条：把 `prediction.made / prediction.resolved` 做成 WAL 事件（预测先于结果落盘）、把"信念库"做成带效果记录的记忆图、把校准复盘做成一个后台分区。第 9 条也有对应：预测记录的所有权按文件分，模型写预测，代码写结算。duoduo 缺少的"改完验证"步骤，正是金融场景必须自建的那一层。
