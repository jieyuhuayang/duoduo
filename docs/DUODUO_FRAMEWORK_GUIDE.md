## 0 结论与总览

**duoduo 是一个让大语言模型无人值守持续运行的程序；模型自身做不到的事（保存状态、调度、并发、边界检查）由运行时代码完成，需要判断的事交给模型。本文从模型的五个限制出发，逐项说明运行时补上了什么、怎样补上，以及无人值守时它用哪些检查控制出错和花费。**

0.1 节用一张表把这句话展开成全文的结构；0.2 节给出系统总览；0.3 节和 0.4 节是背景知识与术语表；0.5 节是读法。

### 0.1 模型的五个限制与运行时的对策

模型有五个限制：不能执行工具、两次调用之间没有记忆、感觉不到时间、没人提问就不运行、不会自己变好；duoduo（本文称"运行时"，定义见 0.4 节）对每一项有一个对策，各对应本文一个部分；无人值守本身带来的风险不是模型的限制，由第五部分单独处理。五个限制出自同一个事实：大语言模型本身是一个无状态的函数，给它一段文本，它返回一段文本；它不执行任何操作，不保存任何东西，不会自己开始运行，也不会因为被使用而改变。

| 模型的限制 | 后果 | 运行时的对策 | 所在部分 |
|---|---|---|---|
| 不能执行工具：读不了文件，跑不了命令 | 只能说，不能做 | 不直接调用模型 API，而是调用自带工具和执行循环的 agent 引擎（Claude Code、Codex、Grok、pi 四选一）。duoduo 自己不写推理逻辑和工具执行循环，同一份系统提示可以交给任何一个引擎；另外追加六个让模型操作 duoduo 自身的工具 | 第一部分 |
| 两次调用之间没有记忆 | 进程重启或对话关闭后，状态全部丢失 | 先记录，再执行：每条输入先追加进一个只追加的事件日志，然后才排队处理；会话邮箱只存指向事件的指针，不存正文；会话状态、job 定义、用量账本各有持久文件；对话历史由引擎保存，运行时记下会话 id 以便续接。每次调用前重新装配上下文，进程崩溃后从日志和指针恢复 | 第二部分 |
| 感觉不到时间，不知道自己被打断过 | 隔了三天再聊，它当作三秒前 | 每一轮把"距上次交互多久""上一轮被打断""某个 job 已完成"等信息写成文本块，放在用户输入之前送给模型 | 第二部分 |
| 没人提问就不运行 | 没有人说话时什么都不会发生 | 两套独立的定时器：job 扫描器每 60 秒检查一次，执行用户布置的定时任务；心跳约 37 分钟一次，只在记忆目录里的碎片或档案、或者外部来源事件有变化时唤醒一次性的后台分区会话（跳过条件见 3.3 节） | 第三部分 |
| 不会自己变好 | 同样的错误反复犯 | agent 的渠道人格、记忆和后台分工都是一个 git 仓库里的 Markdown 文件。后台分区会话读事件日志，把经验改写进这些文件；负责提交的分区定期把改动合成一个 git 提交，任何一次提交都可以用 `git revert` 撤销；下一次对话自动读到新版本 | 第四部分 |
| （不是模型的限制）无人值守 | 可能做错事，也可能持续花钱 | 少数由代码执行、不依赖模型遵守提示词的检查；一组成本控制措施；每条失败路径都有明确的处置方式 | 第五部分 |

五个对策背后是同一条分工规则，全文会反复用到它：

> **确定性的事交给代码：存储、排序、调度、并发、测量、校验。需要判断的事交给模型：推理、写作、决定记住什么、决定改什么。**

第六部分在前五部分之后做总评：列出十二个可以借鉴的设计和三个局限。

### 0.2 系统总览

前台处理消息和后台定时任务运行在同一个 daemon 进程里；agent 可以修改的设定与记忆放在 `~/aladuo`，运行数据放在 `~/.aladuo`。下图的上半部分是有人说话时的路径 ①–⑥（第二部分），下半部分是没人说话时的两套定时器（第三部分），最下面是后台改写记忆、前台读到新版的循环（第四部分）。

```
渠道适配器进程（飞书 / 终端 / 编辑器，每个平台一个独立进程）
   │ 消息                                          ▲ 回复
   ▼                                               │
daemon（一个常驻进程）
 ├─ 前台：有人说话时
 │    ① 事件日志：消息先追加写入磁盘
 │    ② 网关分流：运维命令直接回复，不调用模型
 │    ③ 会话邮箱：只写一行指针 "- [ ] @evt(id)"
 │    ④ 唤醒这个会话在内存里的执行体（actor）
 │    ⑤ 处理：合并消息 → 装配上下文 → 调用一次引擎
 │         系统提示：固定顺序的六层内容（1.3 节）
 │         每轮瞬时块：时间流逝、被打断、job 回执等（2.4 节），后接用户原文
 │         引擎：Claude Code | Codex | Grok | pi
 │    ⑥ 回执：写 outbox 记录和 agent.result 事件，推送给渠道
 │
 └─ 后台：没人说话时
      job 扫描器（每 60 秒）：到期的 job → job 会话 → 结果交回布置它的会话
      心跳（约 37 分钟）：只读检查（不调用模型）→ 任务单 → 后台分区会话
                                                        │
                                                        │ 读事件日志、改记忆文件、git commit
                                                        ▼
内核 git 仓库 ~/aladuo（渠道人格、记忆板与档案、后台分区提示词）
   │ 记忆板改动后：新会话装入新版；运行中的渠道会话在下一轮收到提示（4.6 节）
   └────────▶ 回到 ⑤ 的系统提示
```

两个目录名字只差一个点，内容完全不同：

| 目录 | 是什么 | 里面有什么 |
|---|---|---|
| `~/aladuo`（内核，kernel；可用环境变量 `ALADUO_KERNEL_DIR` 改） | agent 可以修改的设定与记忆，一个 git 仓库 | 内核根提示词、四个引擎的使用说明、全局与各渠道种类的配置和人格、记忆板与档案、后台分区的提示词与轮转表。身份提示 `meta-prompt.md` 不在这里：它随 npm 包分发，daemon 按环境变量指定的位置读取（4.2 节） |
| `~/.aladuo`（运行数据） | daemon 运行时读写的数据 | 事件日志、会话状态与邮箱、outbox、用量账本、job 定义、渠道实例记录、渠道适配器的安装目录，以及锁文件和进程间通信用的 socket 文件 |

不带点的是内核，带点的是运行数据。实际路径以 `duoduo daemon config` 的输出为准。

### 0.3 背景知识

读本文需要三类背景：大语言模型的几个基本概念，Claude Code 与 Claude Agent SDK 的关系，以及几项软件工程常识。已经熟悉的读者可以跳过本节。

#### 大语言模型相关

- **提示词（prompt）**：送进模型的输入文本。本文分两种：每次调用都放在最前面、讲身份和规则的"系统提示"；用户或运行时每一轮追加的"用户输入"。
- **上下文（context）**：一次调用送进模型的全部文本。模型一次能读的最大长度叫"上下文窗口"。
- **token**：模型计费和计算长度的单位。一个 token 大约是四分之三个英文单词；中文里一个汉字通常占一到两个 token。
- **输入缓存（prompt cache）**：引擎会缓存每次输入开头逐字相同的那一段。下一次输入只要开头相同，命中缓存的 token 按大幅折扣计费，响应也更快。缓存只在一段时间内有效，按服务和计费方式不同，从几分钟到一小时。因此系统提示越稳定，成本越低。本文说"缓存前缀"，指的就是输入开头这段相同的文本。
- **流式（streaming）**：模型不等全部生成完，每生成一段就送回一段，连接保持打开。本文说"流式会话"，指一条一直开着的连接。
- **压缩历史（compact）**：对话太长时，让模型把前面的历史总结成一段短摘要替换原文，腾出上下文窗口，会话本身不换。
- **agent 引擎（agent harness）**：模型加一组工具（读写文件、跑命令等）加一个循环：模型决定调用什么工具，引擎执行，把结果送回模型，直到任务完成。Claude Code、Codex、Grok、pi 都是这种程序。本文一律称"引擎"。
- **子代理（subagent）**：主会话临时开一个独立的小会话去做一件事，做完收回结果。
- **hook**：引擎提供的回调点，让调用方在工具调用之前或之后插入自己的逻辑。
- **MCP（Model Context Protocol）**：给引擎追加工具的一种跨厂商接口。**dynamicTools** 是 Codex 自己的对应接口，让调用方在运行时注册工具。
- **思考过程（reasoning / thinking）**：模型给出答案之前生成的推理文本。引擎可以把它流式送出，也可以不送。

#### Claude Code 与 Claude Agent SDK

本文里"Claude Code"指 Anthropic 的命令行工具（终端里的 `claude` 命令；命令行工具下文简称 CLI）。它和网页聊天的区别是它会自己执行操作：你说"把这个 bug 修了"，它会读代码、改文件、跑测试、看结果、再改，直到做完。

**Claude Agent SDK** 把 Claude Code 封装成一个库，让别的程序能调用它。它的 npm 包名是 `@anthropic-ai/claude-agent-sdk`（npm 是 JavaScript 程序的包管理器；"npm 包"是一份可安装的发布物，duoduo 本身也以 npm 包分发），核心函数是 `query()`：程序调用一次 `query("帮我……")`，SDK 跑完一整轮，把结果流式返回。

| | Claude Code（CLI） | Claude Agent SDK（库） |
|---|---|---|
| 给谁用 | 人，坐在终端前 | 程序，自动调用 |
| 形态 | `claude` 命令 | 代码里的 `query()` 函数 |
| 两者关系 | 实际执行任务的程序 | 启动 Claude Code 并与之通信的接口 |

duoduo 使用 Claude 引擎时调用的是 SDK。job 会话和后台分区会话的一轮对话就是一次 `query()` 调用；前台聊天会话则保持一条长期打开的 `query()` 连接，后面每一轮都送进同一条连接，空闲 1 小时后才释放（2.3 节）。

SDK 会另起一个 Claude Code 程序（子进程）来执行任务，两者经文本管道通信。这个程序随 SDK 一起安装，用户不必另装 `claude` 命令；想指定自己的 Claude Code 程序，设置环境变量 `CLAUDE_CODE_EXECUTABLE`。安装 duoduo 时如果带了 `--omit=optional`，这个程序会缺失，使用 Claude 的会话收到消息时会被拒绝，回复里写明怎样重装（1.2 节）。

**另外三个引擎：**
- **Codex** 是 OpenAI 的 CLI agent。duoduo 为会话启动 `codex app-server` 子进程，用 JSON-RPC 与它通信。JSON 是一种用花括号和引号书写结构化数据的文本格式；JSON-RPC 是一种约定：调用方发一条 JSON 文本写明"调用哪个函数、参数是什么"，对方回一条 JSON 结果。本文说"RPC"，都指这种远程函数调用。
- **Grok** 是 xAI 的 CLI agent。duoduo 为会话启动 `grok agent` 子进程，用 ACP（Agent Client Protocol，一个跨厂商的 agent 通信协议）与它通信。
- **pi** 是一个开源（MIT 许可）的编程 agent，npm 包名 `@earendil-works/pi-coding-agent`。它是 duoduo 的依赖，随 duoduo 一起安装，不需要另外安装；它运行在 duoduo 启动的一个 worker（工作进程）里。

#### 软件工程相关

- **git**：给一个文件夹记录版本的工具。本文只用到五个概念：commit 是存一个带说明的快照；revert 是生成一个撤销某次快照的新快照；diff 是逐行对比两个版本的差异；工作树是文件夹里现在实际的内容，可能比最新快照更新；`.gitignore` 列出哪些文件不进版本记录。
- **进程与子进程**：进程是一个正在运行的程序；子进程是由另一个进程启动的进程。
- **环境变量**：启动程序时传给它的一组"名字=值"设置。本文出现的 `ALADUO_*` 都是。
- **API key**：调用模型接口用的密钥。
- **哈希（sha256）**：把任意长的文本算成一串固定长度的字符，内容不同，结果几乎必然不同。用来判断"内容变没变"。
- **frontmatter**：Markdown 文件顶部用 `---` 包起来的配置块，格式是 YAML（一种"键: 值"逐行书写的配置写法，如 `runtime: claude`）。TOML 是 Codex 使用的另一种配置文件格式。
- **JSONL**：每行一条 JSON 的纯文本文件。
- **unix socket、TCP 端口、WebSocket**：unix socket 是本机进程之间通信用的一种文件形式的通道，谁能打开由文件权限决定；TCP 端口是网络端口，本机或远程程序都可能连上；WebSocket 是一种保持打开、双向推送的网络连接。
- **cron 表达式**：Unix 类系统的定时工具 cron 使用的五段式时间写法，如 `0 9 * * 1` 表示每周一 9 点。
- **GC（garbage collection）**：自动清理不再被引用的东西。本文里指自动清理从记忆板出发已经链接不到的记忆文件。

### 0.4 术语表

下表按"运行时与进程、会话与消息、内核与记忆、后台、job 与渠道、工具、通用说法"的顺序列出本文的术语。正文第一次用到时也会简要解释。

| 术语 | 含义 |
|---|---|
| **运行时** | 本文指 duoduo 这个常驻程序本身：调度、日志、心跳等确定性逻辑。它不做推理，也不执行引擎的内置工具（读写文件、跑命令），只实现追加给模型的六个自操作工具（1.6 节） |
| **引擎（配置字段 `runtime`）** | `claude`、`codex`、`grok`、`pi` 四选一，真正调用模型、执行工具的部件。配置文件里的 `runtime` 字段指引擎，不指 duoduo |
| **daemon** | duoduo 的常驻进程。调度、会话、邮箱、日志、心跳都在这个进程里；渠道适配器是独立进程；四个引擎都运行在 daemon 直接或经 SDK 间接启动的子进程里 |
| **host 模式** | daemon 直接运行在你的机器上、引擎能直接读写本机文件的模式。duoduo 只有这一种运行模式 |
| **网关** | daemon 里接收所有入站消息、决定要不要调用模型的组件。飞书渠道适配器的打包文件名叫 `feishu-gateway.js`，那是渠道适配器，不是这里的网关 |
| **事件日志（上游 Spine，WAL）** | 只追加的事件文件，路径 `~/.aladuo/var/events/YYYY-MM-DD.jsonl`。WAL 是 write-ahead log 的缩写，意思是"先写日志，再做事"。每条事件另有一行 by_id 索引，记录它在哪个文件的哪个位置 |
| **session / actor** | session 是一段对话或一次后台任务；actor 是它在内存中的执行体。一个会话键对应至多一个 actor |
| **会话键（session key）** | 会话的唯一名字，形如 `stdio:default:28d3ca682f86`（终端会话的最后一段是工作目录路径的哈希前 12 位）。前缀决定会话类型：`job:` 开头是 job 会话；`meta:`、`cadence:`、`system:` 开头是运行时内部的会话，后台分区会话用的就是 `meta:subconscious`；其余是渠道会话 |
| **渠道会话 / job 会话 / 分区会话 / 系统会话** | 渠道会话是有人在聊天平台上对话的会话（下文的"前台会话"即渠道会话）；job 会话执行一个 job；分区会话是心跳唤醒的一次性后台会话；系统会话是分区会话以外、会话键以 `meta:`、`cadence:` 或 `system:` 开头的运行时内部会话。job 会话和分区会话合称"后台会话" |
| **邮箱（mailbox）** | 每个会话的待办文件，只存事件指针 `- [ ] @evt(<事件 id>)`，不存正文 |
| **drain / turn** | drain 是会话处理一次邮箱待办的过程；turn 是对引擎的一次调用。多条相邻消息可以合并成一个 turn |
| **插话（steer）** | 模型正在运行一轮时，把用户新发来的消息送进这一轮，而不是等这一轮结束或中止它（1.5 节、2.2 节） |
| **outbox** | 出站回复的记录和投递状态 |
| **回执** | 一轮处理结束后写下的结果记录：一条 outbox 记录和一条 agent.result 事件（2.1 节）。"job 完成回执"专指 job 成功后留给 owner、随 owner 下一轮送达的结果（3.1 节） |
| **每轮瞬时块** | 每一轮放在用户输入之前的一组文本块，内容是时间流逝、上一轮被打断、job 回执这类每轮都可能变化的信息；它们不进系统提示（2.4 节） |
| **内核（kernel，`~/aladuo`）** | git 管理的目录，存放 agent 可以修改的设定与记忆：渠道人格、记忆板与档案、后台分区提示词等（4.1 节） |
| **身份提示（`meta-prompt.md`）** | 出厂的身份与行为准则文件，随 npm 包分发，不复制进内核。daemon 每次装配系统提示时，从环境变量 `ALADUO_META_PROMPT_PATH` 指定的文件或 `ALADUO_BOOTSTRAP_DIR` 指定的目录读取它；两者都没有设置时，系统提示里没有这一层（4.2 节） |
| **记忆板（`memory/CLAUDE.md`，上游 broadcast board）** | 渠道会话、job 会话和系统会话都会把它的正文放进系统提示。放入前去掉文件顶部的 frontmatter 和 HTML 注释，正文里用 `@路径` 引用的文件也一并读入。分区会话只拿到它的路径，需要时自己读 |
| **档案（dossier）** | `[[slug]]` 链接指向的深层文件：实体档案、`lesson-*`（纠错规则）、`groove-*`（重复任务的固定流程）。slug 是文件的简短标识名，如 `[[lesson-deploy-check]]` |
| **孤儿文件** | 从记忆板出发沿 `[[slug]]` 链接走不到的记忆文件，因此前台不会读到它 |
| **碎片（fragment）** | 后台从事件日志里提炼出的一条证据。大多数碎片对应记忆板的某一行，说明这一行"起作用了""该起作用却没起"或"没有相关证据"；另一类碎片记录记忆板上还没有的新信号，供修改记忆板时考虑是否新增一行 |
| **规则节点（node）** | 上游把 `memory/topics/` 下的一个 `lesson-*` 或 `groove-*` 文件叫一个节点 |
| **效果记录（`effectiveness/`）** | 由碎片汇总出的、记忆板每一行"起作用了几次"的当前统计，一行记忆对应一个文件，不进 git |
| **心跳（cadence）/ 一次心跳（tick）** | 后台定时器，默认每 2,220,000 毫秒（约 37 分钟）触发一次；每触发一次叫"一次心跳" |
| **后台分区（上游 subconscious）** | 一个提示词目录，心跳唤醒它运行一次分区会话。出厂的四个分区见附录 B。下文用 distiller、weaver、tracker、committer 分别简称 gradient-distiller、intuition-weaver、pattern-tracker、memory-committer；weaver 不指 4.2 节讲到的已退休分区 memory-weaver |
| **轮转表（`playlist.md`）** | 决定下一次心跳轮到哪个分区的文件，用 checkbox（`- [ ]` 勾选框）书写，agent 自己可以改 |
| **冷却 / 退避** | 冷却是一个分区运行后到下次可以运行之间至少要隔的心跳次数，写在分区 frontmatter 里；退避是分区运行失败后推迟下一次运行的时间，连续失败越多推迟越久，有上限（3.3 节） |
| **只读检查（lint）** | 心跳里运行时对记忆文件做的检查：是否太长、链接是否断了、有没有孤儿文件。它只测量，不改内容；发现问题就写任务单 |
| **信号 / 任务单** | 只读检查发现问题时产出一类"信号"（如 scan-gap、claude-compress，全部列在附录 B）；每个信号写成一份文本工单（`.pending` 文件）投进某个分区的收件箱，本文叫"任务单"。分区处理完就删掉它 |
| **契约过滤（contract）** | 分区 frontmatter 里的 `contract:` 声明它接收哪几类信号；运行时只把任务单投给声明了该信号的分区 |
| **指令指纹** | 对"当前这套指令"（身份提示、渠道人格、实例提示、记忆板、job 任务书及其验收标准）算的哈希，用来发现指令变了（4.6 节） |
| **配置签名** | 把会话的基本配置（工作目录、权限模式、工具集、附加目录等）写成一段 JSON 文本，逐字比较；不同时重建流式会话，并能从差异看出哪一项变了（2.3 节）。它不是哈希，与指令指纹无关 |
| **活动指纹** | 对记忆目录下碎片、实体档案、规则文件三个子目录的最新修改时间，以及最新一条外部来源事件的 id 算的哈希；没变时整次心跳跳过后台分区（3.3 节）。只改记忆板本身不会改变它 |
| **job** | 由用户或前台会话布置的定时或一次性任务，由一个 Markdown 文件定义；文件正文本文叫"任务书"。布置它的会话叫它的 owner。`keepalive` 类型的 job 跑完第一轮后不归档，会话进入休眠，收到通知或到了自己预约的时间再在原会话上继续；要结束它必须显式归档（3.1 节） |
| **渠道适配器（channel adapter）** | 把 duoduo 接到某个聊天平台（飞书、终端、编辑器）的独立进程，上游也叫渠道插件。IM 指即时通讯软件 |
| **渠道种类 / 渠道实例** | 种类指平台类型（飞书、终端）；实例指一个具体接入点（某个飞书群）。种类配置在 `~/aladuo/config/<kind>.md`，实例配置在 `~/.aladuo/var/channels/<id>/descriptor.md` |
| **自操作工具** | duoduo 追加给模型、用来操作 duoduo 自身的六个工具：ManageJob、RemindDuoduo、ViewSessions、Notify、QueueOutboundAttachment、Skip（1.6 节） |
| **技能（skill）** | 一份给引擎读的操作手册文件，教它完成某类运维任务，如刷新分区提示词、归档用量账本 |
| **冷启动** | 重新启动引擎进程，或重新建立与引擎的连接，并把整段系统提示重新送一遍。如果此时输入缓存已经过期（空闲回收之后通常如此），整段系统提示要重新写入缓存，这一轮拿不到缓存折扣 |
| **落盘** | 把数据写进磁盘上的文件。落盘之后，即使进程崩溃，数据仍在 |
| **游标** | 一个记录当前位置或当前持有者的标记，下次继续或核对时使用。本文有两处：读取事件日志时带上"上次读到的事件 id"，从它之后继续读（5.4 节）；job 每次运行被认领时记下一个认领游标，结算时游标对不上，说明这次运行已经被新的一次取代（5.3 节） |

### 0.5 三种读法

按可用的时间，本文有三种读法：

- **15 分钟**：读第 0 节，再读第一至第五部分每部分开头的第一段（该部分的结论），最后读第六部分。
- **1 小时**：从头到尾顺读。
- **深入核对**：按附录 C 找到每一节在 [`AGENT_INTERNALS_ANALYSIS.md`](./AGENT_INTERNALS_ANALYSIS.md) 里对应的证据节，或者直接读还原源码。

## 第一部分 · 推理交给四个可替换的引擎

**duoduo 自己不实现推理和工具执行：它把同一段系统提示交给 Claude Code、Codex、Grok、pi 四个引擎之一，并追加六个让模型操作 duoduo 自身的工具；四个引擎的接入方式、命令实现、权限和思考输出各不相同，代码按引擎逐项处理，引擎不可用时拒绝执行，不改用别的引擎。** 这一部分回答 0.1 节里"不能执行工具"这个限制。

1.1 节说明为什么调用引擎而不是模型 API；1.2 节至 1.5 节依次讲四个引擎的接入与失败处置、共用的系统提示、引擎与模型的选择、同名命令的不同实现；1.6 节讲追加给模型的六个工具；1.7 节讲无人值守下的权限与认证。

### 1.1 调用引擎，而不是模型 API

duoduo 调用的是完整的 agent 引擎，而不是模型 API（只负责"文本进、文本出"的接口）。工具执行循环、子代理、会话持久化都由引擎提供，运行时只管理状态和调度。这是整套架构成立的前提，下表对比两种做法：

| 直接调用模型 API 时，运行时必须自己写 | 调用现成引擎后直接得到 |
|---|---|
| 工具执行循环：读文件、跑命令、把结果送回模型、再循环 | 引擎内置全套工具和循环 |
| 子代理编排：把一个子任务交给独立上下文的模型实例，再收回结果 | Claude Code 的 Agent 工具、Codex 的 `spawn_agent`；pi 没有子代理工具，委派要走 job（3.1 节） |
| 会话持久化 | 引擎自己保存对话历史，duoduo 只保管一个会话 id |
| 干预正在进行的一轮 | Claude 的 SDK 提供"工具调用之前""工具调用之后"两个 hook；另外三个引擎各有插话接口（1.5 节） |
| 工具扩展协议 | MCP、dynamicTools 现成可用 |

Claude 的两个 hook 各管一件事。模型调用 Skip 工具时，"工具调用之前"的 hook 拦下这次调用，直接以"这一轮静默结束"终止这一轮（1.6 节）。用户在模型运行中发来的新消息，由"工具调用之后"的 hook 处理：某个工具调用结束时，hook 把新消息作为附加内容交给模型，模型在同一轮里接着读到它（2.2 节）。两件事都通过 SDK 的公开接口完成，duoduo 与引擎之间没有私有协议。

由引擎承担工具执行，也是 duoduo 能让模型修改自己的提示词和记忆的前提。后台分区会话修改记忆和提示词，用的就是引擎自带的 Edit（改文件）、Write（写文件）、Bash（跑命令）等工具；运行时只需把分区会话的工作目录设在内核里这个分区的目录，并把记忆目录加入它可以访问的目录（4.7 节）。duoduo 没有专门用于修改提示词或记忆的工具。反过来看，如果运行时自己写工具执行循环，就要自己实现并维护每一个工具，运行时的代码量会显著增加。

### 1.2 四个引擎的接入方式：接法不同，失败处置相同

四个引擎的进程形态、安装要求和探测方式各不相同，但引擎不可用时的处置是同一条规则：会话先绑定到配置指定的引擎，再检查这个引擎能不能用；不能用就拒绝执行，回给用户一段写明原因和修复办法的文字，不改用别的引擎。用户因此始终知道是哪个引擎在回答。pi 是唯一不存在"不可用"状态的引擎，它的失败出现在有没有配置模型这一步。下表逐项对比：

| | Claude | Codex | Grok | pi |
|---|---|---|---|---|
| 进程形态 | daemon 进程内调用 SDK；SDK 为每次调用或每条流式连接启动一个 Claude Code 子进程 | 每个会话一个 `codex app-server` 子进程，按行收发 JSON-RPC | 每个会话一个 `grok agent` 子进程，走 ACP 协议 | 每个会话一个 pi worker 子进程，worker 程序随 duoduo 的 npm 包分发 |
| 用户需要另装什么 | 不用另装：SDK 和 Claude Code 程序随 duoduo 安装；需要本机 Claude 登录态或 API key（1.7 节） | codex CLI，并执行 `codex login` | grok CLI，并执行 `grok login` | 什么都不用装；需要在 `~/.pi/agent` 里配好模型和凭据 |
| 对话历史怎么续 | 每轮成功后保存 SDK 会话 id，下次续接（resume） | 线程（thread，Codex 对一段对话历史的叫法）：新建、续接，或 fork——复制一份历史、换上新设定、在副本上继续 | ACP 的 `session/load` | pi 自己的会话文件，存放在 duoduo 的会话目录下 |
| 可用性探测 | 检查 SDK 和本平台的 Claude Code 程序文件是否存在（设了 `CLAUDE_CODE_EXECUTABLE` 就不查），5 秒超时；不检查登录态 | 运行 `codex --version` 和 `codex login status`，各 5 秒超时，输出里要有 "logged in" | 只运行 `grok --version`，5 秒超时；不检查登录态，没登录时错误要到会话实际调用 Grok 时才出现 | 不探测，永远列为可用 |
| 不可用时 | 拒绝执行，回复以 "Agent runtime 'claude' is unavailable" 开头，提示重装后重启 daemon | 拒绝执行，回复以 "Agent runtime 'codex' is unavailable" 开头，提示安装 codex CLI 并登录 | 拒绝执行，回复以 "Agent runtime 'grok' is unavailable" 开头，提示安装 grok CLI 并登录 | 没有"不可用"；会话缺模型时拒绝执行，回复以 "This pi session has no model yet" 开头 |
| 审批 | 默认 `bypassPermissions`，不弹审批 | `approvalPolicy: never`；另有沙箱（限制程序能写哪些目录的隔离环境），默认 `workspace-write`，即只能写工作区，可用 `ALADUO_CODEX_SANDBOX` 改为只读或不限制 | 启动参数 `--always-approve` | 不弹审批，与 Codex、Grok 一样全部放行 |
| 自操作工具怎么接入 | 进程内的 MCP 服务器 | dynamicTools；duoduo 另设一项 Codex 配置，让这些工具作为直接工具出现在工具列表里，而不是只能在 Codex 的代码执行模式里间接调用 | 经 ACP 把同一个 MCP 服务器挂给 Grok | 在 pi worker 里注册；调用时带本会话的口令经 RPC 回连 daemon，daemon 只接受四个固定的方法 |
| 思考过程是否送到渠道 | 送，思考增量推送给订阅这个会话的渠道 | 不送，握手时固定退订思考增量通知 | 送 | 送 |
| 特有限制 | 内置工具按白名单开放（5.1 节） | 内置工具不可禁用：duoduo 传入的禁用清单被忽略，只在 debug 级日志记一条 | 默认的 append 模式下，系统提示只在新建会话时传入，改动要到新会话才生效 | 没有子代理工具（Agent、TaskStop），委派要用 job |

**探测结果何时刷新，按引擎不同。** Claude 只在 daemon 启动时探测一次，结果一直沿用到 daemon 退出：启动时不可用，此后所有用 Claude 的会话都会被拒绝，修好之后要重启 daemon，拒绝回复里也这样写。

Codex 和 Grok 的探测结果有两种用途。daemon 启动时的探测结果决定"哪些引擎可选"，即 ManageJob 能选的引擎和渠道绑定时列出的引擎，所以启动之后才装好的引擎要重启 daemon 才会出现在这些列表里。一个已经配置为 Codex 或 Grok 的会话，则在它的 actor 启动时重新探测，运行时只记住成功的结果；被拒绝后 actor 随即结束，下一条消息会启动新的 actor 并重新探测，所以装好或登录之后不需要重启就能用上。

另外两处探测各有自己的时机。ManageJob 创建 Codex 或 Grok 任务时每次都重新探测，不可用就当场报错。后台分区会话遇到不可用的引擎，这次运行记为失败，按退避规则推迟下一次（3.3 节）。

**Codex 的思考过程不送到渠道，这一点固定在代码里。** duoduo 的 Codex 适配器在握手时退订三种思考增量通知，退订清单是代码里的常量，没有配置项或环境变量可以改变它，改提示词也不起作用。

**pi 不需要安装和登录，但必须配置模型。** pi 随 duoduo 一起安装，不需要外部 CLI，也没有登录探测；它回连 daemon 的那条 RPC 要校验每个会话的口令，并且只接受四个方法。pi 在 duoduo 里没有默认模型：一个 pi 会话必须有一个 `provider/modelId` 形式的模型指针，来源见 1.4 节，否则发消息时被拒绝。模型和凭据从用户自己的 `~/.pi/agent` 目录读取；按上游的 pi 使用说明，duoduo 不往这个目录写，每个会话需要写的模型数据放在 duoduo 自己的会话目录里。

### 1.3 四个引擎使用同一份系统提示

渠道会话、job 会话和系统会话的系统提示由一个函数按固定顺序拼接六层，四个引擎拿到的是同一段文本，差别只在传入方式和 `prompt_mode` 是否生效；后台分区会话不用这段系统提示。六层依次是：

1. 身份提示（`meta-prompt.md`，出厂的身份与行为准则，每次装配时从磁盘读取，读取位置由环境变量决定，见 4.2 节；读不到时这一层省略）
2. 渠道种类的人格（`~/aladuo/config/<kind>.md` 的正文）
3. 实例提示（该渠道实例 `descriptor.md` 的正文）
4. 记忆板（`memory/CLAUDE.md`）。前面加一段"这些指令覆盖默认行为、必须照做"的引导语；正文含 `[[slug]]` 链接时，后面再附一段规则，说明链接是档案入口，只在摘要不足以判断时才去读；正文里 `@路径` 引用的文件一并读入展开。记忆板为空时这一层省略
5. 运行上下文（会话键、渠道种类、引擎名）。这一层不含任何时间戳；时间信息放在每轮瞬时块里（2.4 节），因为输入缓存只在开头逐字相同时才命中
6. job 任务书（仅 job 会话有）

分区会话不收到这段六层系统提示，分区的提示词作为输入交给引擎（3.2 节）；只有在 Grok 上，分区会话另外收到身份提示和运行上下文这两层作为系统提示。

同一段文本交给四个引擎的方式如下。`prompt_mode` 是渠道配置或 job 配置里的一个字段，取值 `append`（默认）或 `override`：

| 引擎 | 传入方式 | `prompt_mode` |
|---|---|---|
| Claude | `append` 时追加在 Claude Code 内置系统提示之后；`override` 时不用内置提示，只用这段文本 | 有效 |
| Codex | 包进 `<aladuo:system-context>` 标签，作为 baseInstructions（Codex 对系统提示的叫法） | 无效：Codex 没有内置预设可以保留或替换；用 ManageJob 给 Codex 任务设置它会被当场拒绝 |
| Grok | `append` 时作为一组规则并入 Grok 自带的系统提示，只在新建会话时传入；`override` 时替换 Grok 自带的系统提示 | 有效 |
| pi | `append` 时追加在 pi 自带的系统提示之后；`override` 时替换 pi 自带的系统提示，但保留 pi 的工具清单与使用准则 | 有效 |

Codex 还有两处适配，让它读到和 Claude 同一套定义。第一，Codex 按自己的约定读工作目录里的 `AGENTS.md`，所以工作目录里有 `CLAUDE.md` 而没有 `AGENTS.md` 时，duoduo 自动建一个指向 `CLAUDE.md` 的符号链接（一个指向另一文件的快捷方式）。

第二，daemon 初始化时把每个后台分区目录下 `.claude/agents/*.md` 的子代理定义编译成 Codex 用的 `.codex/agents/<name>.toml`，内容没变就跳过，源文件删除时同步删除生成的文件；出厂的四个分区不带任何子代理文件，所以默认安装下这一步不产生文件，只有用户给分区加了子代理时才起作用。

### 1.4 引擎、模型、推理力度的选择与会话绑定

引擎、模型、推理力度三样分别选择，都是最具体的一层生效；一段对话历史只能在产生它的引擎上续接，所以 duoduo 拒绝把已有历史的会话改配成另一个引擎；绕过这项检查改了配置的，下一条消息被拒绝执行。

**引擎的选择链**按会话类型不同，从高到低是：

| 会话类型 | 选择顺序 |
|---|---|
| 渠道会话 | 渠道实例 `descriptor.md` 的 `runtime` → 渠道种类配置 `~/aladuo/config/<kind>.md` 的 `runtime` → 全局默认 → `claude` |
| job 会话 | job frontmatter 的 `runtime` → 全局默认 → `claude`。经 ManageJob 创建的 job 文件总会写明 `runtime`；创建时省略，取发起创建的会话自己的引擎 |
| 分区会话 | 分区 frontmatter 的 `runtime` → 全局默认 → `claude` |

全局默认来自环境变量 `ALADUO_DEFAULT_RUNTIME`；也可以写在 `~/.config/duoduo/config.json` 的 `defaultRuntime` 里，CLI 启动 daemon 时，若这个环境变量没有设置，就用它补上。写了不认识的值，一律按 `claude` 处理。

**模型与推理力度的默认值**按引擎分开存放。推理力度（effort）是让模型"想多久"的档位，越高越慢、越贵。每个引擎有自己的一对键：`claude.model`、`claude.effort`、`codex.model`、`codex.effort`，Grok 和 pi 同理。这些键可以写在三层：全局（`~/aladuo/config/runtime.md`）、渠道种类、渠道实例，越具体的层优先；job 会话的种类层是 `~/aladuo/config/job.md`，分区会话只读全局层。合并按键逐个进行：在种类层只写了 `codex.model`，全局层的 `claude.model` 仍然有效。

每个引擎用各自的键名，是因为模型 id 只对某一个引擎有意义：一个渠道从 Codex 切到 Claude 之后，不应把 GPT 的模型 id 带进 Claude。同样的考虑也用在会话上：用 `/model` 为会话存下的模型记着它属于哪个引擎，会话的引擎一变就被清掉。

两个值的校验宽严不同。`effort` 只接受 `low`、`medium`、`high`、`xhigh`、`max` 五个值；Claude 模型不支持 `max` 时按 `high` 执行，`/effort max` 的回复会写明这一点。通过 CLI、聊天里的 `/effort` 或 ManageJob 写错，当场拒绝并列出合法值；直接手改配置文件、job 文件或分区 frontmatter 写错，运行时只忽略这个值、记一条日志，然后按下一层的默认值运行。`model` 只要求非空且不含空白：模型 id 的取值范围是开放的，兼容端点和 pi 的各个模型提供方都有自己的模型名，所以写错的 id 留到真正运行时由引擎报错。

**job 会话里，会话自己的设置和 job frontmatter 谁优先，模型与推理力度不一样。** 模型方面，Claude、Codex、Grok 三个引擎上 job frontmatter 的 `model` 优先于会话自己的 `/model`；pi 相反，会话自己的 `/model` 优先。推理力度方面，四个引擎都是会话自己的 `/effort` 优先于 job frontmatter 的 `effort`。普通渠道会话没有 job frontmatter，看不到这个差异。

`duoduo session config` 的帮助文字把会话自己的 `/model` 列在 job frontmatter 之前。这个顺序对推理力度成立；对模型只在 pi 上成立，在另外三个引擎上与代码不符。

pi 会话的模型指针按以下顺序取第一个有值的：会话自己为 pi 存下的 `/model`、job frontmatter 的 `model`、配置层的 `pi.model`；分区会话取分区 frontmatter 的 `model`，没有再取全局层的默认值。无论模型从哪一层选出，用量账本记录的都是实际服务这一轮的模型，不是请求的模型（5.4 节）。

**会话绑定引擎。** 四个引擎保存对话历史的格式互不相通，所以一段历史只能在产生它的引擎上续接。运行时在会话状态里记下这段历史属于哪个引擎，并在两个时点拦下引擎的改动：修改配置时，和执行下一条消息时。

修改配置时的检查覆盖两条入口：用 `duoduo session config` 改一个渠道会话的引擎，或在渠道里重新绑定时选了另一个引擎。只要这个渠道下有会话的历史属于别的引擎，改动本身就被拒绝，回复列出这些会话，要求先在每个会话里发 `/clear`（清空前先把历史里值得保留的内容取出来），再重新设置。

其他改法不经过这项检查，例如直接手改渠道实例、渠道种类或 job 文件里的 `runtime`。这时会话被改配成另一个引擎后，下一条消息被拒绝执行，回复写明历史属于哪个引擎、现在配置的是哪个，并给出两种选择：改回原来的引擎后继续；或者在新引擎上开一段新会话，渠道会话发 `/clear` 后再发消息即可，job 则由它的 owner 决定。回复还提醒，旧历史仍保存在磁盘上，换引擎前可以先让子代理找到它并写一份摘要。不保留历史的 job（frontmatter 写了 `stateless: true`）每次都是新会话，不做这项检查。

### 1.5 同名命令在各引擎上分别实现

插话、`/compact`、`/model` 在四个引擎上各有一套实现，生效时间也不同；运行时不隐藏这些差异，例如 `/model` 的回复会写明在当前引擎上什么时候生效。

| 操作 | Claude | Codex | Grok | pi |
|---|---|---|---|---|
| 插话（模型运行中送入新消息） | 经"工具调用之后"的 hook，在某个工具调用结束时作为附加内容交给模型 | 调用 Codex 的 `turn/steer` 接口 | 调用 Grok 的插话扩展方法 | 调用 pi worker 的插话接口 |
| `/compact` 压缩历史 | 渠道会话交给 SDK 自带的压缩，这一步会调用模型；非渠道会话回复"只在交互会话中可用" | 调用 Codex 的线程压缩接口 | 调用 Grok 的压缩扩展方法 | 由 pi worker 执行压缩 |
| `/model` 换模型 | 有正在运行的连接时直接切换，下一轮起生效；新模型需要不同的上下文窗口配置时，下一轮开始前重建连接；没有连接时先存下，下一轮生效 | 先存下，下一条消息起 fork 一条新线程生效，历史保留 | 已有会话时经 ACP 立即切换；否则先存下 | 只接受 `provider/modelId` 格式，先存下，下一条消息重建 worker 时生效 |
| 输入 token 记账 | 三类，互不重叠，相加为总输入：新读入、写入缓存、命中缓存 | 两类：输入（已包含命中缓存的部分，即总输入）、命中缓存 | 三类：输入（已包含命中缓存的部分，即总输入）、命中缓存、写入缓存 | 与 Claude 相同：三类互不重叠，相加为总输入 |

插话只是模型运行中来了新消息时的第一选择；插话送不进去时怎样处理（软抢占、`/cancel` 强制中止），见 2.2 节。

表外还有三个与命令相关的事实。不带参数的 `/model` 在 pi 上列出本机现在能用的模型，但选了一个 pi 解析不了的 id 不会当场拒绝，要到下一条消息才报错。运行时没有撤销上一轮的命令，历史控制类命令只有 `/compact`。`/clear`（别名 `/reset`）让下一条消息开一个全新的引擎会话，这也是换引擎前清空历史的方法（1.4 节）。

### 1.6 追加给模型的六个自操作工具

duoduo 给模型追加六个操作 duoduo 自身的工具，按会话类型分配：渠道会话拿到全部六个；job 会话拿不到 Skip 和 QueueOutboundAttachment；后台分区会话和系统会话只有 ViewSessions 和 Notify。引擎自带的工具作用在文件和命令上；这六个工具作用在 job、会话、通知和投递上，由运行时实现、由引擎调用，在 Claude 上显示为 `mcp__aladuo__<工具名>`。

| 工具 | 做什么 | 渠道会话 | job 会话 | 分区会话、系统会话 |
|---|---|---|---|---|
| ManageJob | 创建、列出、读取 job | 有 | 有；只有 keepalive 类型的 job 能用它创建新 job（3.1 节） | 没有（pi 引擎上例外，见本节末） |
| RemindDuoduo | 给调用者自己预约一次将来的运行 | 有 | 有；只填时间，给本 job 加一次运行 | 没有 |
| ViewSessions | 只读查看本 daemon 的会话 | 有 | 有 | 有 |
| Notify | 给另一个会话发一条通知 | 有；必须写明目标 | 有；不写目标时发给 owner | 有；必须写明目标 |
| QueueOutboundAttachment | 这一轮结束时给用户发一个文件 | 有 | 没有 | 没有 |
| Skip | 这一轮不输出任何内容 | 有 | 没有 | 没有 |

**ManageJob 只做三件事，而且必须写明是哪一件。** 它的 `action` 只接受 `create`、`list`、`read`，缺了 `action` 直接报错。这样，如果某些 Anthropic 兼容网关在转发时丢掉了这个参数，调用方得到的是一个错误，而不是一次看起来成功、实际没有创建任何东西的调用。创建时 `model` 和 `acceptance`（怎样算做完，用可以检查的条件写）必填，pi 任务的模型必须是 `provider/modelId` 格式，推理力度写错当场拒绝。

结束、打断、改期一个 job 不在工具里，而是 shell 里的运维命令 `duoduo job archive`、`duoduo job interrupt`、`duoduo job reschedule`。模型调用 ManageJob 试图归档或改期，错误信息会指向这些命令；改期在 job 内部应改用 RemindDuoduo（见下文）。创建权限的完整规则见 3.1 节。

**RemindDuoduo 只给调用者自己排一次触发，不创建新会话。** 在渠道会话里，它接受一个时间（如 `@in 30m`，或带时区的 ISO 时间）和一段上下文说明：到时间后，这段说明作为一条消息送回这个会话，不打断正在进行的一轮；它只触发一次，醒来的那一轮如果还要再等，就再预约一次。上下文说明是醒来那一轮唯一的输入，工具说明要求把它写给"一个什么都不记得的自己"：为什么要回来、第一步做什么、证据在哪、谁在等。预约成功后返回一个 id，这次预约会出现在 ManageJob 的列表里，可以用 `duoduo job archive <id>` 在触发前取消。

在 job 会话里，RemindDuoduo 只接受时间，作用是给这个 job 额外加一次运行，原有的调度类别不变；再调用一次会替换尚未触发的时间，时间必须在将来。job 怎样用它实现轮询见 3.1 节。

**ViewSessions 和 Notify 让会话之间互相找到并传话。** ViewSessions 是只读的：不带参数时列出所有活跃会话的会话键、别名和类型，并标出调用者自己；带会话键时查看这个会话的状态、工作目录和相关文件路径；它从不创建、恢复或修改任何东西。它也是模型查找 Notify 目标、查找附件所需会话键的方式。

Notify 把一段文字作为事件投进目标会话的邮箱，并唤醒目标会话。目标写会话键或会话的显示别名，不能是自己；只有 job 会话可以不写目标，此时发给它的 owner。Notify 投递成功只表示写进了目标邮箱；目标会话长时间没人读取时的拒投规则见 3.1 节。

每条通知带一个链深度，用来防止两个会话互相通知形成循环：被通知唤醒的会话再发通知，深度加一，达到 5 层时拒绝。按代码判断（未实测），这项限制只在 Claude 的 job 会话和系统会话上完整生效，它们每次运行都取这一批消息里的最大深度；分区会话由心跳启动而不是由通知唤醒，深度从 0 开始。Claude 渠道会话的常驻连接和 Grok 会话只在建立连接时取一次深度，连接存续期间再被通知唤醒，深度不会更新。Codex 会话的工具在建立连接时把深度固定为 0，pi 会话经 RPC 发出的通知不带深度，这两个引擎上的通知链不受 5 层限制。

**QueueOutboundAttachment 和 Skip 只给渠道会话，因为只有渠道会话直接面对用户。** QueueOutboundAttachment 把一个文件排进这一轮的发送队列，这一轮结束时随回复发出；排队前按渠道声明的能力检查文件类型和大小，渠道不支持时工具返回错误，工具说明要求模型把限制告诉用户并给出替代办法。pi 是例外：pi 上这个工具总是先回复"已接受"，daemon 在工具调用结束后才做这项检查，不合格的文件只记一条警告日志，模型看不到这个错误，也就无法转告用户。

Skip 让这一轮不向用户输出任何内容。调用时必须给出理由；下一轮开头的一个瞬时块（2.4 节）告诉模型上次跳过的理由、时间和已经过去多久。工具说明要求 Skip 是这一轮的第一个动作，因为之前已经流式输出的文字仍可能到达用户。在 Claude 上，"工具调用之前"的 hook 拦下 Skip 调用并直接结束这一轮；在 Codex 上，调用 Skip 之后这一轮的后续产出不再投递。

job 会话和分区会话拿不到这两个工具：它们不能静默跳过一轮，也不能直接给用户发文件；job 的结果经回执或 Notify 交给 owner（3.1 节），分区会话的产出是它改写的文件（第四部分）。所以写 job 任务书时，不要写"把报告作为附件发给用户"这类 job 会话做不到的指令。

**pi 引擎上的分配有一处不同。** pi 的工具在 pi worker 里注册，worker 对 ManageJob 不按会话类型过滤，所以用 pi 运行的分区会话和系统会话也能看到 ManageJob；另外三个引擎上这两类会话没有这个工具。上游的 pi 使用说明写的是分区会话没有 ManageJob，与代码不符。其余五个工具在 pi 上的分配与另外三个引擎相同，只是 QueueOutboundAttachment 的能力检查推迟到工具调用结束之后（见上文）。

### 1.7 无人值守下的权限与认证

四个引擎默认都不弹审批，限制改由代码实现：Claude 的工具白名单、控制面的访问限制和 Codex 的沙箱；Claude 的认证来源在安装向导里三选一。不弹审批的原因是 daemon 无人值守，任何审批弹窗都会让会话无限期卡住。

四个引擎的审批设置见 1.2 节的表。Claude 未显式配置时一律使用 `bypassPermissions`；渠道配置和 job 配置里没有这个字段，只能用环境变量 `ALADUO_PERMISSION_MODE` 改。工具白名单和控制面访问限制的完整定义在 5.1 节。

有两个配置键容易误用：渠道或 job 配置里接受 `allowedTools` 和 `disallowedTools`，但它们都不决定 Claude 能用哪些内置工具。`allowedTools` 只影响权限的自动批准，不会把内置工具加进白名单；`disallowedTools` 只能禁用 `mcp__` 前缀的 MCP 工具，对内置工具无效。

写了对内置工具无效的项，daemon 不报错，只打一条警告并忽略这些项；这条警告不去重，每次为会话构建引擎参数时都会再打印一次，不影响运行。要给 Claude 增加内置工具，唯一的入口是配置里的 `claude.tools`（ManageJob 的对应参数叫 `extra_tools`，写进 job 文件后也是 `claude.tools`），它只能增加工具，不能去掉白名单里已有的工具。

**认证来源**只涉及 Claude，在首次安装向导 `duoduo onboard` 里三选一，对应环境变量 `ALADUO_CLAUDE_AUTH_SOURCE` 的三个取值：

- `claude_code_local`：使用本机 `claude login` 的登录态。daemon 启动时删除一组固定的环境变量，防止旧的 key 或端点覆盖本机登录态：API key、认证令牌、接入端点、opus/sonnet/haiku 三个默认模型名，以及 API 超时和关闭非必要网络请求两项开关。这组以外的 `ANTHROPIC_` 变量不会被清理，例如 `ANTHROPIC_MODEL` 会原样传给引擎。
- `anthropic_api_key`：使用 API key。填了 key 时，同时把 API 超时设为 3,000,000 毫秒，并关闭 Claude Code 的非必要网络请求；交互向导里 key 留空，则什么都不写，之后可以自己设置 `ANTHROPIC_API_KEY`。交互向导不问模型名；非交互安装（没有终端交互、全部选项由环境变量给出）时如果设置了 `ANTHROPIC_DEFAULT_SONNET_MODEL`，opus、sonnet、haiku 三个默认模型都指向它。
- `compatible_endpoint`：使用任何 Anthropic 兼容端点。duoduo 给 Claude Code 注入端点地址 `ANTHROPIC_BASE_URL` 和令牌。向导里的模型名是可选项：填了，三个默认模型全部指向这一个第三方模型，此时用 `/model` 在档位之间切换没有意义；留空则不写任何默认模型变量，Claude Code 按自己的档位名向端点请求，切换档位是否有效由端点决定。超时和关闭非必要网络请求两项与 `anthropic_api_key` 相同。

**对产品设计的含义。** 第一部分的几项决定是连在一起的。选择调用现成引擎，运行时只需管理状态和调度，但也就放弃了跨引擎的统一体验：同名命令的生效时间、能不能看到思考过程、能不能禁用内置工具，都随引擎而变。差异消除不了，duoduo 的做法是把它写明：命令的回复说明在当前引擎上何时生效，引擎不可用或与历史不符时拒绝执行并说明原因，而不是换用另一个引擎继续执行。一个提示词装配函数加几段按引擎的适配代码，比每个引擎各维护一份提示词更不容易出现内容不一致。最后，常驻 agent 不能依赖逐次审批，立项时就要决定哪些限制写进代码（工具白名单、沙箱、控制面访问限制），哪些只写在提示词里，后者的风险在第五部分评估。

## 第二部分 · 有人说话时：一条消息的处理

**每条消息先写进只追加的事件日志，再决定要不要调用模型；需要调用时，相邻的短消息合并成一次调用，稳定的内容放进系统提示，每轮变化的信息放在用户消息前面；进程崩溃后，运行时从事件日志和邮箱里的指针恢复没做完的工作。** 这一部分回答 0.1 节里的两个限制：模型在两次调用之间没有记忆，也感觉不到时间。

本部分先按时间顺序讲一条消息经过的六个步骤（2.1），再展开其中处理一步的三个问题：模型正在运行时来了新消息怎么办（2.2），同一个会话的引擎进程什么时候保留、什么时候回收（2.3），送给模型的文本怎样分成两部分装配（2.4）；然后讲进程崩溃或重启之后怎样恢复（2.5），最后讲消息从聊天平台进入 daemon 的那一段（2.6）。不由人触发的输入来自 job 扫描器和心跳，见第三部分。

### 2.1 六个步骤

一条消息从进入 daemon 到回复送出经过六步：写日志、分流、写指针、唤醒、处理、回执。顺序的要点是先把"收到了"写进磁盘，再做任何可能失败的事，所以进程在任何一步崩溃，已经收到的消息都不会丢。

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① 写日志 | 渠道适配器调用 daemon 的 `channel.ingress` 接口送来消息。daemon 把它封装成一条带唯一 id 的事件，先追加到当天的事件日志文件 `~/.aladuo/var/events/YYYY-MM-DD.jsonl`，再往 by_id 索引追加一行"这条事件在哪个文件、从第几个字节开始、有多长"。运维命令也照样写日志 | 模型调用慢，也可能失败。把"收到"和"处理"分开，崩溃后恢复只需要重新读文件（2.5 节） |
| ② 分流 | 网关按输入开头的命令决定去向（见下表）：运维命令由网关直接执行并回复，其余输入交给会话 | 在入口就判定要不要调用模型；网关能回答的，不花一次模型调用 |
| ③ 写指针 | 在目标会话的邮箱里写一条待办 `- [ ] @evt(<事件 id>)`，只记事件 id，不复制正文 | 正文只在事件日志里存一份，不会出现两份内容不一致 |
| ④ 唤醒 | 在 daemon 进程内广播一条 session.wake 通知，唤醒这个会话键对应的 actor（会话在内存中的执行体）；还没有 actor 就新建一个 | 每个会话键至多一个 actor，同一个会话的状态不会被两处代码同时修改 |
| ⑤ 处理 | actor 执行一次 drain：从邮箱顶部取出一批待办（2.2 节），装配上下文（2.4 节），调用引擎；引擎的每次工具调用和结果都作为事件写回事件日志 | 一次调用可以处理几条消息，见 2.2 节 |
| ⑥ 回执 | 写一条 outbox 记录（出站回复；渠道会话的记录附带这一轮的 token 用量、费用和实际使用的模型），并追加一条 agent.result 事件；订阅了这个会话的渠道适配器立即收到推送 | 渠道可以把每一轮的花费显示给用户（5.4 节）；回执与触发它的事件关联，重复提交时可以直接返回这份回执 |

**分流规则。** 第②步按输入的第一个词决定去向：

| 输入 | 去向 | 是否调用模型 |
|---|---|---|
| `/status`、`/config`、`/debug`、`/stats`、`/task`、`/model`、`/effort`、`/cancel`、`/clear`（别名 `/reset`） | 网关直接执行并回复，不进邮箱 | 否 |
| `/compact` | 进入会话邮箱，由会话在第⑤步处理。在 Claude 渠道会话上，它被原样交给 Claude Agent SDK 自带的压缩功能，由模型把历史总结成摘要；Claude 上的非渠道会话直接回复"只在交互会话里可用"；其他引擎各有实现（1.5 节） | Claude 渠道会话上会；其他引擎由各自的压缩实现决定（1.5 节）；Claude 非渠道会话不会 |
| `/loop` 加一段描述 | 这是一条注入提示：网关把一段预置的编排说明拼在用户描述前面，作为普通消息交给会话，由模型按说明创建 job（3.1 节） | 是 |
| 只输入 `/loop`，不带描述 | 网关回复用法 | 否 |
| 其余所有输入，包括网关不认识的斜杠开头的输入 | 作为普通消息进入会话邮箱 | 是 |

网关执行 `/clear` 之后，还会在这个会话的下一轮给模型附一条说明：会话已经重置，不要接着做重置前的工作（2.4 节的"网关命令执行说明"）。`/model` 和 `/effort` 改的是这个会话之后使用的模型和推理力度，生效时间因引擎而异（1.4、1.5 节）。

**去重只认幂等键。** 渠道可以给每条消息附一个幂等键，即渠道为这条消息给出的唯一编号，用来识别重复提交。第①步写日志之前，daemon 先查这个键：处理过，就不再写日志、不再入队，直接返回原来那条事件和上次的回执，不会再调用一次模型。去重不比较消息内容：同样的文字不带幂等键发两次，会得到两次回答。去重记录保存在一个只追加的文件里，daemon 启动后处理第一条入站消息时把它整份读入内存；文件中读不出来的行被跳过并记一条日志，不影响其余记录。

**事件日志与索引。** 事件日志只追加，代码里没有修改或删除已写入事件的路径。一次追加是两次写入：先写日志行，再写索引行，两者不构成一个原子操作（要么都成功、要么都不生效的写入）。by_id 索引是近期缓存：daemon 每次启动时只保留最近 7 天日志文件的索引条目（`ALADUO_SPINE_INDEX_RETENTION_DAYS`），装载时丢弃字节位置不合法的条目。索引里查不到的事件，运行时以邮箱待办写入的时间为上限，从那一天的日志文件开始向更早的日期逐个扫描，所以较老的待办仍能读到正文，只是读得慢一些。

**第④步的并发限制。** 同时处于运行状态的渠道会话最多 10 个（`ALADUO_SESSION_MAX_CONCURRENT_CHANNEL`），job 会话最多 6 个（`ALADUO_SESSION_MAX_CONCURRENT_JOB`），两类分别计数，所以后台任务再多也占不掉前台的名额；超出上限的唤醒排队等待。在一个 daemon 进程内，同一会话的状态修改按会话键排队执行；正在归档的会话拒绝一切唤醒和投递。

跨进程还有一把写锁，保证一个数据目录同一时刻只有一个 daemon。锁文件记录持有者的进程号、本机开机标识和最近一次心跳时间，持有者每 30 秒刷新一次；持有者进程已退出、机器重启过、或超过 120 秒没有刷新，新的 daemon 才能接管，否则拒绝启动（5.1 节）。

### 2.2 合并与插话

相邻的短消息合并成一次引擎调用；模型正在运行时到达的新消息，优先插进正在进行的这一轮，插不进去就等这一轮结束后单独处理，只有在没有插话通道时才中止当前一轮；`/cancel` 立即中止。三种处理的目的相同：少调用、少重跑，并尽量不截断一个正在执行的工具。

**合并：一轮不等于一条消息。** 真人常连发几条短句。drain 每次从邮箱顶部取一批待办：最多 5 条，属于同一类事件，相邻两条的时间间隔不超过 3 分钟。这一批如果全是普通聊天消息（没有斜杠开头的命令），并且来自同一个渠道实例、回复到同一组会话，就拼成一段输入，开头说明"下面这 N 条是时间上挨得很近的事件，按从旧到新排列，当作一次连续的更新处理，只回复一次"；否则这一批里的消息逐条处理，每条一轮。

合并不引入等待：drain 只合并邮箱里已经排着的消息，不会为了凑满一批而推迟处理。一批之外的消息留给下一次 drain，所以一段连发可能被分成几轮处理。

**插话（steer）。** 一个会话同一时刻只运行一轮；后到的消息不会被并进正在运行的这一轮的输入，只能经插话通道进入，或者排队。模型运行中到达新输入时，运行时按下表处理：

| 到达的输入 | 当前一轮的状态 | 处理 |
|---|---|---|
| 普通消息 | Claude 渠道会话：引擎已接受这一轮的输入；模型没有调用 Skip；这一轮不是由后台通知触发的；新消息不带附件 | 插话：先暂存，等模型下一次工具调用完成时送进这一轮；已有一段暂存的插话时，新文字追加进去 |
| 普通消息 | Codex、Grok、pi 会话：引擎报告有一轮正在进行；模型没有调用 Skip；这一轮不是由后台通知触发的 | 插话：经引擎自己的插话接口直接送进这一轮，附件一并送入 |
| 普通消息 | 引擎已接受这一轮的输入（Claude）或已有一轮在进行（Codex、Grok、pi），但模型已调用 Skip、这一轮由后台通知触发、Claude 上新消息带附件，或者引擎拒绝了插话 | 不打断，等这一轮结束后作为新的一轮处理 |
| 普通消息 | 没有可用的插话通道：Claude 渠道会话的这一轮输入还没被引擎接受；Codex、Grok、pi 的这一轮还没开始；前一条消息的插话还在处理中 | 软抢占（下一张表） |
| `/cancel` | 任意 | 网关直接中止当前一轮，不等工具返回，也不等流式输出结束；Claude 渠道会话的常驻连接（2.3 节）一并关闭 |
| 其他斜杠命令；后台投递（Notify、job 结果、自己预约的唤醒） | 任意 | 只排队，不打断 |

Claude 上暂存的插话是经 SDK 的"工具调用之后" hook 作为附加上下文交给模型的；如果这一轮在下一次工具调用之前就结束了，暂存的文字退回邮箱，作为下一轮处理，不会丢失。Codex、Grok、pi 的插话接口各不相同（1.5 节），运行时把文字直接送进引擎正在运行的那一轮；送不进去时，消息留在邮箱里，等这一轮结束后处理。由后台通知触发的一轮不接收用户的插话，效果是用户消息总能得到属于自己的一轮回复，不会被夹在一段后台处理里。

**软抢占。** 软抢占是指中止当前一轮、让新消息在下一轮处理，但中止的时机尽量避开正在执行的工具：

| 会话 | 中止时机 |
|---|---|
| Claude 渠道会话（持有常驻流式连接，2.3 节） | 当前一轮的输入还没被引擎接受：等接受后立即中断；已被接受：立即中断 |
| 其他会话（没有常驻流式连接） | 模型正在流式输出：等它下一次发起工具调用时中止；有工具正在执行：等所有工具返回后中止；两者都不是：立即中止 |

被中止的那一轮，待办通常算作已处理，不会自动重跑。对一部分中止（例如 Codex 会话被中止、Claude 的常驻连接被关闭），运行时把被中止的那条输入的原文保存下来，下一轮作为"被打断的上下文"放在用户消息前面（2.4 节），模型由此知道上次被打断时在处理什么；另一部分中止（例如 Claude 在引擎已接受输入之后被中断）不另外保存，因为这条输入已经在引擎自己的对话历史里。Claude 渠道会话的输入还没被引擎接受就被中止时，待办留在邮箱里，之后重新处理。

模型还会得知一轮是怎样结束的。用户用 `/cancel` 中止一轮之后，模型下一次读到的输入里带有一行 "[Request interrupted by user]" 标记（Claude 渠道会话，以及 Codex、Grok、pi 会话），模型由此知道这一轮是人结束的，而不是无故中断。在 Codex、Grok、pi 上，抢占中止一轮时如果还有工具调用没有完成，下一次改带另一行标记，说明这次工具调用是为了送达后面的消息才被中止的、没有被拒绝，需要的话可以重新执行。

### 2.3 常驻连接与空闲回收

Claude 渠道会话在多轮之间复用同一条流式连接；基本配置或身份类指令变化时重建，`/cancel`、`/clear` 和空闲回收会关闭它。渠道会话空闲 1 小时后，运行时回收它占用的引擎进程；Claude 上的非渠道会话在模型答完之后仍保持输入通道，直到它派出的子代理全部回调。

**常驻连接。** 同一个 Claude 渠道会话的各轮都送进同一条流式 `query()` 连接，不为每条消息重新启动一次 Claude Code。这省掉两样东西：一是冷启动的时间，冷启动指重新启动引擎进程或重新建立连接，并把整段系统提示重新送一遍；二是输入缓存的失效，连续几轮送进同一条连接时，输入开头逐字相同，缓存持续命中。Codex 和 Grok 会话同样保留各自的常驻子进程，pi 会话保留它的 worker。

这条连接在两种情况下重建。一是会话的基本配置变了：运行时把工作目录、权限模式、工具集、附加目录、模型的上下文档位等写成一段 JSON 文本，叫配置签名，每轮开始前与上一次逐字比较，不同就关掉旧连接、开一条新连接，并在日志里记下是哪一项变了。配置签名不是哈希，与 4.6 节的指令指纹是两回事。二是身份提示、渠道人格或实例提示变了（4.6 节）；记忆板单独变化时一般不重建，细节见 4.6 节。此外，`/cancel`、`/clear` 和下面的空闲回收会关掉这条连接，模型切换无法在原连接上生效（1.5 节）或连接意外断开时，下一轮也会新建一条。

**空闲回收。** 渠道会话一轮处理完、邮箱里没有新待办时，actor 进入空闲状态，立即归还并发名额（2.1 节），然后最多等待 1 小时（`ALADUO_SESSION_IDLE_MS`，默认 3,600,000 毫秒）。等待期间来了新消息，就在原 actor 上继续处理。等满 1 小时时分两种情况：还有渠道连着这个会话，运行时中止 Claude 的流式连接、关闭 Codex、Grok 和 pi 的进程，但保留 actor，下一条消息到来时冷启动；没有渠道连着，actor 整个退出。job 会话和系统会话不进入空闲等待，邮箱处理空了 actor 就结束。

上游更新说明给出的回收理由是：一个长期在线的渠道会让它接触过的每个会话都一直占着一个引擎进程，而空闲 1 小时后模型端的输入缓存早已过期，继续占着进程没有收益，回收的代价只是长时间沉默后的第一条回复慢一些。

渠道还可以开启空闲自动压缩：会话空闲超过设定的分钟数、且上下文超过设定的 token 数时，运行时替会话执行一次 `/compact`，下一轮给模型附一条"已自动压缩"的说明（2.4 节）。这项默认关闭，Codex 会话不做，配置方法见 5.2 节。

**后台会话保持输入通道。** 这一机制只用于 Claude 引擎上的非渠道会话（job 会话、分区会话和系统会话）。模型给出最终回复之后，运行时不立即关闭这一轮的输入通道，而是等模型派出的后台子代理全部回调完成才结束这一轮，否则子代理的结果送不回来。运行时通过 SDK 发出的"任务开始"和"任务通知"两类消息跟踪这些子代理，后台运行的 Bash 命令不计入。模型答完后，如果连续 10 分钟（`ALADUO_HOLD_INPUT_IDLE_TIMEOUT_MS`）没有收到引擎的任何消息而子代理仍未全部回调，运行时强制关闭输入通道并记一条警告。

渠道会话不使用这一机制，前台对话不会因为子代理而延长。渠道会话里的子代理完成后，由 Claude Code 自己续写并输出结果，运行时把这段续写作为一轮输出送回渠道；子代理的完成通知只作为一条生命周期事件写进事件日志，不进邮箱，也不另外唤醒会话。

### 2.4 稳定内容与每轮内容分开装配

送给模型的文本分成两部分：很少变化的内容放在系统提示里，每轮都可能变化的信息写成"每轮瞬时块"放在用户消息前面；系统提示里不含任何时间戳。这样系统提示在多轮之间逐字不变，输入缓存可以反复命中。本文列出的设计中，这是最容易移植到其他 agent 的一项：它只涉及提示词各段放在哪里，不需要改变系统结构。

| 部分 | 内容 | 放在哪里 | 为什么 |
|---|---|---|---|
| 系统提示 | 1.3 节列出的六层 | system prompt | 很少变化；开头稳定，输入缓存持续命中 |
| 每轮瞬时块 | 下表的九类信息 | 用户消息之前的文本块 | 每轮都可能变化；放进系统提示会让缓存每轮失效 |

九类瞬时块按固定顺序排列，最后是用户原文：

| 顺序 | 瞬时块 | 什么时候出现 |
|---|---|---|
| 1 | 重启提示 | daemon 重启后，渠道会话的第一轮（2.5 节） |
| 2 | 自动压缩提示 | 空闲自动压缩之后的下一轮（2.3 节） |
| 3 | 网关命令执行说明 | 网关执行 `/clear` 之后，告诉模型这件事已经生效，不要重复执行（2.1 节）；`duoduo job interrupt` 给出的理由也经这一块送给被打断的 job（3.1 节） |
| 4 | 时间流逝 `<time-context>` | 渠道会话收到用户消息，且距上一次交互超过阈值（默认 60 分钟，渠道配置 `time_gap_minutes`，设为 0 即关闭）；写明上一次交互和现在的时间、中间隔了多久 |
| 5 | 上一轮 Skip 的说明 | 上一轮模型用 Skip 结束、没有输出（1.6 节），这一轮是用户消息；写明当时给出的理由、那一轮的产出用户没有看到，以及已经过去的时间 |
| 6 | 被打断的上下文 | 上一轮被中止，且运行时保存了被中止的输入（2.2 节）；附上这些输入的原文 |
| 7 | job 完成回执 | 这个会话布置的 job 成功完成（3.1 节） |
| 8 | job 触发信息 `<job-tick>` | job 会话：这是第几次运行、本次触发时间、上一次运行时间 |
| 9 | 记忆板更新提示 | 渠道会话：记忆板在这个会话上一次看到之后被修改过（4.6 节） |

每一类在注入过的那一轮之后清除，不会重复出现在后续轮次。用户输入以 `/` 开头时，运行时跳过全部瞬时块，只发原文：命令不应该和时间、打断之类的信息混在一起。

时间信息只能以文本送进模型，因为模型本身没有时钟：两次调用隔 3 秒还是 3 天，对它完全一样。duoduo 主要用三处文本告诉模型时间：渠道会话里的时间流逝块，job 会话里的 job 触发信息，分区会话提示词里的当前时间（3.2 节）；上一轮 Skip 的说明、重启提示和网关命令执行说明里也带有时间。反过来，系统提示里不放时间戳也是出于同一个原因：输入缓存只在开头逐字相同时命中，一个精确到分钟的时间戳就会让每次的开头都不一样。

### 2.5 崩溃恢复

daemon 重启后的恢复就是重新读文件：取得数据目录的写锁，扫描会话目录，把邮箱里还有待办的会话重新唤醒；渠道会话在重启后的第一轮收到"你运行在新的 daemon 进程下"的提示，附带重启原因。正常停止和崩溃对正在进行的那一轮处理不同：正常停止时它被中止，崩溃时它的待办留在邮箱里，重启后重新处理。

**启动顺序。** daemon 启动时依次做这几件事：取得写锁，另一个 daemon 还在运行就拒绝启动（2.1 节）；补齐内核里缺失的出厂文件（4.2 节）；修剪 by_id 索引（2.1 节）；读取重启原因文件；扫描会话目录，逐个唤醒邮箱或收件箱里还有待办的会话。正在归档的会话和工作目录已经不存在的会话不唤醒。这些唤醒只排队，不抢占任何正在进行的一轮。

**停止与崩溃时正在进行的那一轮。** 两种情况的处理不同：

| 情况 | 正在进行的那一轮 | 重启之后 |
|---|---|---|
| 正常停止或重启（`duoduo daemon restart`、进程收到停止信号） | daemon 立即中止所有正在进行的一轮，再最多等 30 秒让它们收尾。收尾方式与 2.2 节的中止相同：待办通常算作已处理，被中止的输入按 2.2 节的规则保存；引擎还没接受输入的，待办留在邮箱里 | 已算作已处理的会话不会自己再跑一轮；下一次被唤醒时，保存下来的输入作为"被打断的上下文"交给模型（2.4 节）。留在邮箱里的待办，以及 30 秒内没收尾完的，按崩溃处理 |
| 崩溃（进程被强制结束、机器断电） | 待办只在一轮处理结束时勾掉，所以还留在邮箱里 | 启动时被唤醒并重新处理。再次处理前，运行时先查这条事件有没有已经写出的回执：有，说明崩溃发生在回执写出之后，只补勾邮箱，不再调用模型；没有，这条消息重新处理一轮 |

**重启原因与唤醒。** `duoduo daemon restart -r "<原因>"` 在停掉旧 daemon 之前，把原因写进数据目录里的一个文件；新 daemon 启动时读取一次并删除这个文件，把原因放进重启提示。从 agent 会话里执行、却没有带 `-r` 的重启命令会被 CLI 拒绝，因为被这次重启切断的会话没有别的途径得知原因。重启提示只发给渠道会话，job 会话和分区会话收不到。

`--wake <会话键或别名>` 指定的会话会在重启后收到一条唤醒消息，由新 daemon 送达，内容是"daemon 重启过，可能切断了你正在做的一轮，先检查那项工作是否完成"并附上原因；它不受 3.1 节"无人读会话的拒投"检查的限制。按上表，一个回答到一半被重启中止的会话，不加 `--wake` 就要等到下一条消息才会继续。唤醒名单和原因写在同一个文件里，所以即使发起重启的那个会话随旧 daemon 一起结束，唤醒也不会丢。这个文件不经过事件日志：它必须在新 daemon 存在之前写好，而事件日志只由 daemon 自己写。

**进程内的异常。** daemon 进程内出现未捕获的同步异常时，运行时认为内部状态可能已经损坏，进程直接退出，是否重启由外部的进程管理器决定；未处理的异步错误只记一条日志，daemon 继续运行（5.3 节）。

### 2.6 渠道适配器

每个聊天平台对应一个独立的渠道适配器进程：它在平台格式和 daemon 的渠道协议之间转换，并在平台一侧执行 @ 过滤、访问策略和 `/setup` 绑定。适配器不在 daemon 的恢复机制之内，崩溃后不会自动重启。

**协议。** 渠道适配器与 daemon 之间只经一套协议通信：入站调用 `channel.ingress`（本机经 unix socket 上的 JSON-RPC），出站打开一个 WebSocket 订阅，按订阅时声明的类型接收最终回复、流式增量和工具调用动态，并逐条确认收到。协议包含能力协商：适配器声明自己能接收哪些文件类型、认得哪些"流结束原因"，daemon 把适配器不认得的结束原因改报为"被中断"，所以适配器不必与 daemon 同步升级。接入一个新平台，就是写一个新的适配器包，用 `duoduo channel install <包名>` 安装，daemon 不需要修改。

以飞书为例，一条群消息的路径如下：

```
你在飞书群里 @机器人 说话
  │  飞书开放平台 ──WebSocket 长连接──▶ 飞书渠道适配器进程
  │    （长连接由本机主动发起，不需要公网服务器或回调地址）
  │  适配器先过滤：群里没 @ 机器人的消息不送进 daemon（默认），
  │  只记下来，作为背景附在下一条 @ 消息前面；私聊默认放行；
  │  剥掉 @ 前缀；下载附件
  ▼
适配器 ──channel.ingress──▶ daemon（进入 2.1 节的六个步骤）
  ▼
适配器 ◀──WebSocket 订阅推送（回复 / 流式增量 / 工具动态）── daemon
  │  渲染成纯文本或飞书卡片；流式回复不断更新同一张卡片；
  │  处理期间给用户那条消息加表情回应表示进度，按"收到、思考、
  │  调用工具、开始输出"依次更换，回复完成后撤掉；
  │  音频附件发成飞书语音消息
  ▼
飞书 API 发回群里
```

**会话键与绑定。** 飞书适配器把"群 ID + 工作目录路径的哈希"编成会话键，形如 `lark:<群 ID>:<哈希>`，私聊再加上用户 ID。所以同一个群固定对应一段连续的对话历史；所有群共用同一套身份、渠道人格和内核记忆。一个群第一次使用时，由群成员发 `/setup`：适配器发一张设置卡片，选择项目目录（只列出含 `CLAUDE.md` 的目录）、引擎、是否要求 @ 才响应，结果写进 daemon 侧这个渠道实例的 `descriptor.md`。`/setup` 由适配器自己处理，不进 daemon；群绑定之后，只有最初绑定的那个人可以再执行 `/setup`。

**行为配置**写在三层 Markdown 里，越具体的层越优先，但全局层只承载模型选择类的设置：

| 层 | 文件 | 作用范围 | 承载什么 |
|---|---|---|---|
| 全局 | `~/aladuo/config/runtime.md` | 所有渠道 | 只读取模型选择类的键：各引擎的模型与推理力度，Claude 的模型别名与模型档案 |
| 渠道种类 | `~/aladuo/config/feishu.md` | 所有飞书实例 | 行为键（系统提示是否叠加引擎内置提示、引擎、时间流逝阈值、空闲自动压缩、是否流式输出、工具列表等）、模型选择类的键、`feishu:` 块，以及种类提示词（渠道人格） |
| 渠道实例 | `~/.aladuo/var/channels/<id>/descriptor.md` | 一个具体的群或私聊 | 与种类层相同的键，另有显示名、绑定人、是否要求 @；正文是实例提示 |

行为键只在种类层和实例层之间取值，实例层有就用实例层；模型选择类的键在三层里逐项覆盖（1.4 节）。渠道专属的键写在 `feishu:` 块里，例如进度卡 `feishu.process_card`：`off`（默认）不显示进度卡；`replace` 用同一张卡片先显示处理进度和正在调用的工具，完成后在原位置换成答案；`keep` 保留进度卡，答案另发一条。

**凭据与过滤策略**是适配器进程自己的环境变量，写在 `~/.config/duoduo/.env`，由 CLI 启动适配器时按适配器声明的变量名单传入，不进任何 Markdown：

| 环境变量 | 取值与默认 | 作用 |
|---|---|---|
| `FEISHU_APP_ID`、`FEISHU_APP_SECRET` | 必填 | 飞书应用的凭据 |
| `FEISHU_DM_POLICY` | `open`（默认）、`allowlist`、`pairing` | 私聊谁能用。`allowlist` 只接收 `FEISHU_ALLOW_FROM` 名单里的用户；`pairing` 目前与 `open` 行为相同，没有实现配对流程 |
| `FEISHU_GROUP_POLICY` | `open`（默认）、`allowlist`、`disabled` | 群消息谁能用。`allowlist` 要求这个群在 `FEISHU_ALLOW_GROUPS` 名单里，或发送者在 `FEISHU_ALLOW_FROM` 名单里 |
| `FEISHU_REQUIRE_MENTION` | 默认开启 | 群里要 @ 机器人才响应。某个群用 `/setup` 设置过时，以这个群实例配置里的值为准 |
| `FEISHU_GROUP_CONTEXT_REMINDER` | 默认开启 | 没有 @ 机器人的群消息不送进 daemon，但记在本地，作为背景附在下一条 @ 机器人的消息前面 |
| `FEISHU_RENDER_MODE` | `auto`（默认）、`raw`、`card` | 回复渲染成纯文本还是卡片 |
| `FEISHU_STREAMING_CARD` | 默认开启 | 流式回复是否持续更新同一张卡片。这个变量不在已发布的飞书适配器声明的变量名单里，经 CLI 启动时写了也传不到适配器，流式卡片始终开启（按发布清单和代码判断，未实测） |

"群里要 @ 才响应"由适配器执行，daemon 只保存开关。飞书平台侧还有一个限制：想让机器人收到没有 @ 它的群消息，要在飞书开放平台为应用申请"获取群组中所有消息"这项敏感权限，并发布新版本。

**进程管理。** 渠道适配器由 CLI 以脱离终端的方式启动，daemon 不监管它。适配器崩溃后不会自动重启，要用 `duoduo channel feishu status` 发现，再用 `duoduo channel feishu start` 启动；恢复之前，这个平台上的消息不会进入 duoduo，已经生成、还没送出的回复留在 outbox 里，适配器重新订阅时补发。`duoduo upgrade` 只处理 npm 上有新版本的适配器：重新安装它们，并在 daemon 重启后重新启动升级前正在运行的那些；已是最新版本的适配器不受影响。

**对产品设计的含义。** 这一部分的设计把"消息""批""轮"三个层次分开，一条消息不必对应一次模型调用：合并、插话、常驻连接分别减少调用次数、中止重跑和冷启动，代价是实现上要处理插话、抢占、回收这些边界情况。可靠性没有依赖任何额外的服务：队列是邮箱里的待办文件，事件日志是 JSONL 文件，锁是带时间戳的 JSON 文件，人和模型都能直接读这些文件核对状态；它的定位因此是单机上的个人 agent，吞吐上限也在这里。渠道适配器在这套恢复机制之外，做成产品时要么给适配器加一个进程守护，要么把手动重启写进运维手册。

## 第三部分 · 没人说话时：两套独立的定时器

**没有人说话时，两套互不相关的定时器驱动运行时：job 扫描器每 60 秒检查一次，启动到期的 job，把结果交回布置它的会话；心跳约 37 分钟一次，同时触发两件事：一是不调用模型的维护，二是检查记忆或外部事件有没有变化，有变化才运行后台分区。** 这一部分回答 0.1 节里"没人提问就不运行"这个限制。两套定时器的分工不同：job 替用户做事，任务书由用户或前台会话写；后台分区替 agent 自己做维护，提示词由 agent 自己修改（第四部分）。两者的触发间隔、跳过规则和结果去向各自独立，一方运行缓慢不会拖住另一方。

本部分先讲 job（3.1），再讲心跳和它唤醒的分区会话（3.2），最后讲一次心跳在什么条件下不运行分区（3.3）。

### 3.1 job：用户布置的定时任务

job 是一个 Markdown 文件定义的定时或一次性任务：创建时校验调度规则，并要求写明模型和验收标准；由 60 秒一次的扫描器按期启动；失败时唤醒布置它的会话，成功时结果随这个会话的下一轮一起送达。布置 job 的会话叫它的 owner。

**定义与调度规则。** 一个 job 是 `~/.aladuo/var/jobs/active/<id>.md` 这一个文件，旁边的 `<id>.state.json` 记录运行历史：运行过几次、上次结果、下一次预约的时间。文件正文是任务书，frontmatter 里的字段如下：

| 字段 | 谁写 | 含义 |
|---|---|---|
| `cron` | 创建者，必填 | 调度规则，写法见下表 |
| `model` | 创建者，必填 | 这个 job 用哪个模型。不写就拒绝创建，不沿用主机的默认模型：主机默认模型因机器而异，有的机器上就是最贵的那个 |
| `acceptance` | 创建者，必填 | 验收标准：怎样算做完，写成可以检查的条件，例如哪个文件必须存在、哪条命令必须成功退出。运行时把它附在任务书后面，要求模型结束前逐条核对，做不到的要明说 |
| `runtime` | 创建者，可选 | 用哪个引擎；不写时用创建者会话自己的引擎 |
| `effort`、`prompt_mode`、`stateless`、`cwd_rel` 等 | 创建者，可选 | 推理力度；系统提示是否叠加引擎的内置提示（1.3 节）；每次运行是否从空白对话开始；工作目录（相对于工作区根目录，这个目录必须已经存在并带有 `CLAUDE.md`；不写时 job 在运行时管理的一个私有目录里运行，目录里的文件跨次保留）。工作目录与 job id、`cron` 一起决定 job 的会话键，改动其中任一项，job 就换一个会话键运行，不再接着原来的对话历史 |
| `owner_session` | daemon 自动写入 | 创建它的会话，结果送回这里 |
| `type`、`created_at` | daemon 自动写入 | 扫描器用 `created_at` 判断第一次什么时候到期 |

`cron` 有五种写法：

| 写法 | 含义 |
|---|---|
| `@every 2h` | 每隔固定时长运行一次；第一次在创建后约 60 秒内 |
| `@in 30m` | 等一段时间后运行一次；运行结束后自动归档 |
| `once` | 尽快运行一次；运行结束后自动归档 |
| `keepalive` | 第一次在创建后约 60 秒内运行；运行完不归档，会话进入休眠，之后收到 Notify、`duoduo session notify` 或到了自己预约的时间，在原会话上继续；只能手动归档 |
| 标准 cron 表达式，如 `0 9 * * 1` | 按日历时间运行，时间按 UTC 计算 |

时长可以组合书写，如 `1d6h4m`，单位是 s、m、h、d、w。写错的规则、超出可表示范围的时长在创建时就被拒绝，不会等到运行时才静默失败。`stateless: true` 不能用在 `keepalive` 上：休眠的 job 靠同一段对话延续上下文，每次从空白开始就接不上前一条消息。指定 Codex 或 Grok 引擎时，创建时就检查它是否可用，不可用直接拒绝；pi 的模型必须写成 `provider/modelId`。这些必填项和检查由模型使用的 ManageJob 工具执行；daemon 控制面另有一个 `job.create` 方法，不检查模型和验收标准，CLI 不使用它。

扫描器每 60 秒运行一次，daemon 启动时和新建 job 时另外立即扫描一次，与心跳无关。到期的 job 先写一条 job.spawn 事件、在 job 会话的邮箱里放一条待办，再启动 job 会话。一次运行从 job 会话启动开始，到它的邮箱处理空为止，运行期间收到的通知在同一次运行里处理。三种情况这一次不启动：上一次运行的会话还没结束；这个会话正在归档；上一次运行失败还不到 5 分钟。

**创建权限与自我预约。** 能创建 job 的是渠道会话和 `keepalive` 类型的 job。普通 job 是执行者，它调用 ManageJob 创建 job 会被拒绝，拒绝信息让它改用 Notify 告诉 owner 需要什么，由 owner 决定。`keepalive` job 可以派发 job，但不能再创建 `keepalive`：`keepalive` 会话不会自己结束，允许它们互相派生会让常驻会话的数量没有上限。ManageJob 只能创建、列出和读取 job（1.6 节）。

分区会话和系统会话在 Claude、Codex、Grok 上没有 ManageJob 这个工具。用 pi 引擎运行时是例外：pi worker 不按会话类型过滤 ManageJob，这两类会话也能创建 job（1.6 节）。

会话需要"过一段时间再回来看一次"时，调用 RemindDuoduo 给自己预约（工具本身的规则见 1.6 节）。渠道会话的预约登记为一条唤醒记录，和 job 一样由这个 60 秒扫描器到期触发；job 会话的预约是给这个 job 追加一次运行。一次性任务等待某个条件时，标准写法就是反复自我预约：每次醒来检查条件，还没满足就再约一次。

结束、打断、改期不是 ManageJob 的动作，而是下面三条 CLI 命令。用户在终端里执行它们，模型也可以通过 shell 工具执行；运行时在需要时提示模型用哪一条，例如周期 job 失败时发给 owner 的通知写明：同样的失败以前出现过的话，可以用 `duoduo job archive` 停掉它，停掉时要告诉用户。

| 命令 | 作用 |
|---|---|
| `duoduo job archive <id>` | 停止以后的调度；正在进行的那一轮照常跑完；文件移进归档目录，不删除。尚未触发的自我预约也用它取消 |
| `duoduo job interrupt <id> -r "<理由>"` | 结束正在进行的那一轮。理由必填：它会作为这个 job 下一轮开头的说明，被打断的会话由此知道上次为什么中断 |
| `duoduo job reschedule <id> <时间>` | 追加一次运行，不改变原来的调度类别；时间写成 `@in 30m` 这样的时长，或带时区的 ISO 时间 |

`/loop` 是把一句话变成 job 的入口（2.1 节）。在前台对话里输入 `/loop 每 20 分钟检查一次 staging 部署，坏了立刻告诉我`，网关把一段预置的编排说明拼在这句话前面交给模型。说明要求模型从描述里读出任务、节奏、引擎和模型，然后按工作量和是否需要评判质量选一种结构：

| 结构 | 适用 | 做法 |
|---|---|---|
| 一个 `@every` job | 每次做的事固定、工作量轻 | 每次从空白对话开始；需要比较前后变化时，把上次的状态写进指定文件 |
| 一个 `@in` job | 由事件决定何时结束的短任务 | 每次结束前用 RemindDuoduo 约下一次，不再约就结束；结束前先通知 owner |
| 一个 `keepalive` 主控 job 加若干执行者 | 工作量大，或产出需要评判质量 | 主控派发子代理或一次性 job 做具体工作；需要评判质量的部分另起一个上下文独立的评审者来评判；主控自己不做重活，也不评判自己布置的工作 |

模型先把计划交给用户确认，包括选定的结构、每段工作的完成标准、每个 job 的调度规则、引擎、模型、后备检查的间隔、停止和暂停的方法、第一次触发的时间；用户确认后才创建，除非用户在消息里明确说不用确认。计划里没有成本估算，一个 job 花了多少钱只能事后在用量账本里查（5.4 节）。

不花模型调用的监控可以这样做：一个普通的后台脚本定时查询数据源，只在有新数据时执行 `duoduo session notify` 唤醒一个 `keepalive` job，由它判断要不要上报，需要时再 Notify 主会话；另配一个间隔较长的 job 做后备检查。没有新数据的时段不调用模型。

**结果送回 owner。** 结果的去向没有配置项，固定送回 owner。失败会唤醒 owner 处理一轮；成功不唤醒，结果作为"job 完成回执"随 owner 的下一轮一起送达（2.4 节）。这样区分的理由是：失败需要有人处理；成功只需要 owner 下次运行时知道，为一句"做完了"专门启动一轮不值得。一次运行里模型已经调用过 Notify 时，这次成功不再自动发回执，因为已经通知过了；失败无论如何都投递。

一次运行按结束时的情况结算，下表列出各情况对 owner 的影响：

| 这次运行怎样结束 | job 怎样处理 | owner 收到什么 |
|---|---|---|
| 成功 | 记为成功；`once`、`@in` job 自动归档 | 完成回执，随下一轮送达，不唤醒 |
| 运行中出错 | 记为失败；`once`、`@in` job 自动归档；周期 job 下次到期照常启动（距这次失败至少 5 分钟）；`keepalive` job 回到休眠 | 失败通知，并被唤醒 |
| 启动阶段就出错，例如引擎不可用 | 记为失败，job 保留；`once`、`@in`、`keepalive` job 5 分钟后重新启动，周期 job 下次到期时启动（距这次失败至少 5 分钟） | 失败通知，并被唤醒 |
| 引擎已接受这一轮后被取消，例如 daemon 重启 | 记为失败；`once`、`@in` job 归档；周期 job 下次到期照常启动；`keepalive` job 回到休眠 | `once`、`@in` job 被归档时收到失败通知；其余 job 不通知 |
| 引擎接受这一轮之前被取消 | 不记录结果，job 保留；上一次结果不是成功的 `once`、`@in`、`keepalive` job 之后重新启动，周期 job 等下一次到期，上一次成功过的 `keepalive` 保持休眠 | 不通知 |
| 没有送入任何待办 | 记为失败，job 保留；`once`、`@in`、`keepalive` job 5 分钟后重新启动，周期 job 等下一次到期 | 不通知 |

表中 `once`、`@in` job 的自动归档都有同一个例外：运行中又预约了下一次（RemindDuoduo 或 `duoduo job reschedule`）时不归档，等那次触发。owner 取的是这次运行开始时 job 文件里的 owner，运行中修改 job 文件不改变这次的收件人。

所以 owner 没收到消息不等于 job 成功完成：成功的回执要等 owner 下一次运行才看得到，有些被取消的运行则什么都不投递。`/loop` 的编排说明因此要求主控 job 用自我预约定期回来检查，不把沉默当作完成。

**无人读会话的拒投。** 用 Notify 往渠道会话投递前，运行时先检查这个会话有没有人在读：如果它既有还没被取走的输出，又已经超过设定时长没有任何渠道取过输出，这次 Notify 直接失败，不写进这个会话。时长由 `ALADUO_NOTIFY_UNCONSUMED_HOURS` 设定，默认 1 小时，设成 0 或负数即关闭这项检查；`duoduo session notify --force` 可以单次绕过。

失败信息不只是一句报错：它说明这个会话已经多久没人读、积压了几条，并列出同一时长内确实有人读过的其他渠道会话，发送方可以改投；一个都没有时，它直接说明没有任何地方会有人看到，不要重发。这项检查只对渠道会话生效，job、分区和系统会话不受影响；job 的完成回执走上面"结果送回 owner"的路径，也不受影响。若没有这项检查，通知会写进一个没有人读取的会话，发送方无从得知。

### 3.2 心跳与后台分区会话

心跳本身不调用模型：每次心跳先在进程内广播一条通知，再做几步确定性的维护；后台分区收到通知后，按轮转表选出下一个可以运行的分区，为它开一个不保存历史的一次性引擎会话。心跳这一侧只有分区会话调用模型。

**心跳。** 心跳是 daemon 里的一个定时器，默认每 2,220,000 毫秒（约 37 分钟）触发一次，用 `ALADUO_CADENCE_INTERVAL_MS` 修改。每次心跳先广播 cadence.tick 通知，然后运行维护步骤：

1. 只读检查：测量记忆文件，发现问题时把任务单投进声明接收这类信号的分区的收件箱，并清掉已经不再成立的旧任务单（4.3 节）。两个实验开关同时打开时，还会执行遗忘 GC，这是运行时唯一会删除记忆文件的地方，默认关闭（5.1 节）。
2. 清理已归档会话留下的记录。
3. 写一条 system.cadence_tick 事件。

上一次维护还没做完时，这一次的维护跳过，但广播照发；后台分区收到广播后与维护步骤同时开始，互不等待，所以慢的维护不会拖住分区，慢的分区也不会拖住维护。job 扫描器不在这些步骤里，它是 3.1 节那个独立的 60 秒定时器。

**轮转表。** 每个后台分区是内核 `subconscious/` 下的一个目录，目录里的 `CLAUDE.md` 是它的提示词，frontmatter 写着它是否启用、冷却几次心跳、每次最多运行多久，还可以指定引擎、模型和推理力度。出厂有四个分区（附录 B）。决定轮到谁的是 `subconscious/playlist.md`：`## Current Round` 下每个分区一行 checkbox。

每次心跳从上往下找第一个没勾选、已启用、不在失败退避期、冷却已满的分区（3.3 节），运行它，勾掉这一行，并在 `## History` 里记一行运行时间；整轮都勾完后，用所有启用的分区重建新的一轮。表里的分区已停用或已删除时，直接勾掉并看下一个。轮转表是纯文本，agent 被明确授权修改它：出厂的后台分区总纲写明任何人都可以编辑轮转表，包括分区自己。

**一次分区会话。** 运行时为选中的分区开一个一次性的引擎会话：不保存对话历史，工作目录是这个分区的目录，记忆目录作为附加目录一并交给它。送给它的提示词由四段拼成：

1. 分区自己的 `CLAUDE.md` 正文；
2. 分区信息：名字、工作目录、收件箱路径、引擎；
3. 运行上下文：当前时间，当前活跃的渠道会话和 job 会话各有几个，内核、记忆目录、记忆板、实体与主题档案、碎片、注册表、事件日志、job 目录、各分区收件箱的绝对路径，以及读事件日志用的 `duoduo spine` 命令前缀（只给前缀，用法写在后台分区总纲和各分区提示词里）；
4. 收件箱里的任务单，有才附上。

后台分区总纲写明分区不记得上一次做过什么，除非写进了文件。跨次心跳的协作因此全靠文件，任何一次运行崩溃，下次重跑即可。分区会话能用的工具由代码限定（5.1 节）。

每个分区有运行时长上限（frontmatter 的 `max_duration_ms`；出厂四个分区在 15 到 35 分钟之间，没写时默认 60 秒）。超时就中止这次运行，之后才到的结果只记一条日志，然后丢弃。

每次运行的结果分四种：成功、超时、出错、输出为空（只对 gradient-distiller 和 intuition-weaver 两个分区检查）。成功写一条标明来自后台分区的 agent.result 事件，其余三种写 agent.error 事件；这四种结果都按分区名写一条用量记录，所以后台每次运行的花费都能落到具体分区（5.4 节）。

分区要用的引擎（frontmatter 指定的或默认的）不可用时，不启动会话：写一条 agent.error，按"出错"计入连续失败次数并退避（3.3 节），不写用量记录，也不改用其他引擎。用 pi 引擎的分区没有配置模型时，也按这种情况处理。

### 3.3 四个跳过条件

一次心跳要依次通过四项检查才会运行分区，任何一项不通过就少运行或不运行，所以记忆目录和外部事件都没有变化时，后台不调用模型：

| 条件 | 检查什么 | 不通过时 |
|---|---|---|
| 1 重入与停机 | 上一次心跳启动的分区会话是否还在运行；daemon 是否正在停止 | 这次心跳不运行分区 |
| 2 活动指纹 | 记忆目录和外部事件自上一次心跳以来有没有变化 | 这次心跳不运行分区 |
| 3 冷却与退避 | 轮转表里的某个分区距上次运行是否已隔够设定的心跳次数，是否处在失败后的退避期 | 跳过这个分区，看轮转表里的下一个 |
| 4 前台优先 | 当前活跃的会话是否不超过 1 个 | 这次心跳只运行一个分区；通过时最多运行两个 |

**活动指纹。** 运行时对四个值算一个哈希：记忆目录下 `fragments/`、`entities/`、`topics/` 三个子目录（包括更深的子目录）里最新的修改时间，加上最新一个事件日志文件里最后一条外部来源事件的 id。哈希与上一次心跳相同，就不运行分区。daemon 启动后的第一次心跳总会通过这项检查。记忆板 `memory/CLAUDE.md` 不在这三个子目录里，所以只改记忆板不会让这项检查通过。

外部与内部按事件的来源种类划分。以下六类来源算内部，不参与活动指纹：心跳写的事件；job 扫描器为到期 job 写的启动事件；后台分区；会话执行过程，即前台引擎的回复、工具调用和错误；会话之间的路由投递，包括 Notify、job 结果和自我预约的唤醒；网关自己的回复。其余都算外部，包括渠道消息、job 会话启动、完成和失败时写的事件、用 `duoduo session config` 修改会话配置时写的配置变更事件。所以一个 job 到点运行并完成，即使没有任何人说话，下一次心跳也会通过这项检查。

分区运行、前台引擎的回复写下的事件不算外部事件，但它们如果在 `fragments/`、`entities/`、`topics/` 里写了文件，修改时间就变了，下一次心跳同样会通过这项检查。出厂的 gradient-distiller 把新事件写成 `fragments/` 下的碎片，所以一次外部事件之后，可能连续几次心跳都运行分区，直到分区不再写这三个目录。

**冷却与退避。** 冷却按心跳次数计：一个分区运行之后，至少再过 frontmatter 里 `cooldown_ticks` 次心跳才能再被选中，被活动指纹挡掉的心跳也计数。出厂四个分区的冷却是 3 到 7 次心跳，按默认间隔约 1.9 到 4.3 小时。失败后还有退避，只有超时和出错两类失败会推迟下一次运行。记连续失败次数为 n（任何一种失败都加一，成功清零），心跳间隔为 T：

| 失败类型 | 不推迟的情况 | 推迟多久 |
|---|---|---|
| 超时 | n 不超过 2 | n × T，最多 2 小时 |
| 出错（包括引擎不可用） | n 不超过 1 | 2 × n × T，最多 4 小时 |
| 输出为空（只检查 gradient-distiller 和 intuition-weaver） | 总是不推迟 | 不推迟，但 n 照样加一 |

按默认间隔 37 分钟算，连续第 3 次超时推迟 111 分钟，第 4 次起推迟 2 小时；连续第 2 次出错推迟 148 分钟，第 3 次推迟 222 分钟，第 4 次起推迟 4 小时。

**前台优先。** 每次心跳先运行一个分区；运行完后，如果当前活跃的会话不超过 1 个，同一次心跳再运行下一个可运行的分区，每次心跳最多两个。分区之间依次运行，不并行。有两个或更多会话在活跃时，后台每次心跳只运行一个分区会话。

**对产品设计的含义。** 把"替用户做事"和"替自己维护"分成两套定时器，各自有独立的触发间隔、跳过规则和结果去向，后台自我维护出问题时不会拖住用户布置的任务，反过来也一样。job 这一侧的几项规定可以直接用在产品里：创建时必须写明模型和验收标准，把花费和"做完"的标准在创建那一刻定下来；结果只按成功和失败两种情况决定是否唤醒 owner，不另设投递配置；投递前检查有没有人在读，把"投递成功"和"有人看到"当成两件事。

心跳这一侧的做法是先用代码判断有没有新情况，有才调用模型，再用冷却、退避和前台优先限制调用次数；这些限制之后仍会产生的后台花费由什么决定、部署时怎样告诉用户，见 5.2 节。

## 第四部分 · 自我改进（本文核心）

**duoduo 的自我改进是改文件，不是改代码：渠道人格、记忆和后台分工都是内核 git 仓库里的 Markdown 文件，由后台分区会话里的模型读事件日志、修改这些文件，再由 memory-committer 分区提交进 git；运行时只做其中确定性的部分。** 运行时做的事有四件：每次心跳测量记忆文件和事件日志，发现问题时写成任务单；只把任务单投给声明能处理它的分区；维护分区的轮转表；在会话每次处理之前比对指令指纹，让改动生效。改不改、怎么改，全部由模型判断。这是 0.1 节那条分工规则在自我改进上的应用。

本部分按一次改动经过的顺序展开：改动存放在哪里（4.1、4.2），改动怎样产生（4.3），怎样防止改动自我强化（4.4），改出来的记忆怎样进入上下文（4.5、4.6），谁有权改什么（4.7），上游更新怎样进入内核、什么时候会覆盖 agent 自己的改动（4.8）。

### 4.1 设定与记忆存放在一个 git 仓库里

**内核目录 `~/aladuo`（下称内核，位置可用环境变量 `ALADUO_KERNEL_DIR` 修改）是一个 git 仓库：会演化的文本进 git，可重建的运行状态、工作文件、本机私有的指令文件和可能含凭据的配置由 `.gitignore` 排除。**

daemon 启动时如果发现内核还不是 git 仓库，就执行 `git init`、写入 `.gitignore`、把内核里当时的全部文件（`.gitignore` 排除的除外；首次安装时就是出厂文件）做成第一个提交（提交信息 `memory: genesis`）；内核已经是 git 仓库时，只把 `.gitignore` 里缺少的上游条目补上。

`.gitignore` 的第一行注释写明，下面列出的是运行状态，不属于认知演化；最后一条 `config/runtime.md` 另有一行注释说明原因。被排除的文件分四类：

| 类别 | 条目 | 不进 git 的原因 |
|---|---|---|
| 可重建的运行状态 | `memory/fragments/`、`memory/effectiveness/`、`memory/state/`、`subconscious/inbox/` | 按上游的说明，碎片可以从事件日志重新提炼，效果记录可以由碎片重新汇总（两者的含义见 4.3）；其余是运行期状态 |
| 引擎和编辑器的工作文件 | `.claude/`（引擎在工作目录里的配置目录）、`*.tmp` | 工作过程中产生的文件，不属于设定和记忆 |
| 本机私有的指令文件 | `CLAUDE.local.md` | Claude Code 约定的本机私有指令文件，只在这台机器上生效，按约定不进版本库 |
| 可能含凭据的配置 | `config/runtime.md` | 全局配置里的模型档案可以写入 API 凭据，注释写明不进历史 |

`.claude/` 这一条匹配任意层级的目录，所以用户在分区目录下用 `.claude/agents/*.md` 定义的子代理也不进 git，不受 git 撤销的保护。

内核的目录结构：

```
~/aladuo/                          ← git 仓库
├── CLAUDE.md                      ← 内核根提示词：说明在这个目录里工作的会话是 agent 在操作自己
├── claude-runtime.md  codex-runtime.md  grok-runtime.md  pi-runtime.md
│                                  ← 四个引擎的使用说明
├── config/
│   ├── runtime.md                 ← 全局配置层（模型档案、各引擎的模型与推理力度默认值），不进 git
│   └── stdio.md  feishu.md  acp.md  job.md
│                                  ← 各渠道种类和 job 的默认配置，渠道种类的文件还带该种类的人格提示
├── memory/
│   ├── CLAUDE.md                  ← 记忆板（出厂为 0 字节）
│   ├── entities/<slug>.md         ← 实体档案：人、工具、项目
│   ├── topics/lesson-*.md         ← 纠错规则
│   │          groove-*.md         ← 重复任务的固定流程
│   ├── fragments/<日期>/          ← 碎片，不进 git
│   ├── effectiveness/<slug>.md    ← 效果记录，不进 git
│   └── state/                     ← 运行状态，不进 git
└── subconscious/
    ├── CLAUDE.md                  ← 后台分区总纲：分区能改什么、不能改什么
    ├── playlist.md                ← 轮转表
    ├── inbox/                     ← 出厂带的占位目录，不进 git；运行时投递任务单的收件箱在 ~/.aladuo/var/subconscious/<分区>/inbox/
    └── <分区名>/CLAUDE.md          ← 各分区的提示词
```

**运行时自己做的提交固定使用作者 `aladuo <aladuo@local>`，分区做的提交只是按提示词使用这个作者。** 运行时自己执行的 git 命令（判断内核是否已是仓库、`git init`、首次提交）固定使用这个作者，并屏蔽用户的全局和系统 git 配置；补 `.gitignore` 条目是普通的文件写入，不经过 git。遗忘 GC（4.5）的提交在命令里显式指定同一个作者名。

memory-committer 用这个作者名提交是提示词里的要求，不是代码强制：分区会话里的 Bash 继承 daemon 的环境，committer 如果漏写作者参数，提交会使用用户全局 git 配置里的身份。

身份提示（npm 包里的 `meta-prompt.md`，不在内核里，见 4.2）把这个设计写成了 agent 对自己的认识："My continuity is in files, not in any single inference"，即它的连续性在文件里，不在任何一次推理里。身份提示还说，它的记忆是一张图：打过交道的人、工具和反复出现的事件各成一份档案，彼此按名字链接；新近发生的事先以碎片的形式存在，直到被证明值得在记忆里占一个位置。

同一份身份提示里还有一条写作规则，与本文的写法一致：能用字面说法就不用比喻或修饰，因为修饰展示的是说话者，而不是要传达的意思，还会带进说话者没有选择的联想。

### 4.2 出厂文件只补缺失，不覆盖已有文件

**npm 包里的 `bootstrap/` 目录是出厂文件。daemon 每次启动都执行同一套初始化：内核为空时整体复制；内核已有内容时只补缺失的文件，不覆盖任何已有文件。** 这一条就是"npm 升级不会覆盖 agent 已经改过的文件"的实现。（以上是正常安装的行为；环境变量 `NODE_ENV=development` 的开发模式另有覆盖规则。）

因为初始化在每次启动时都执行，已有文件不会被改动，但出厂文件被删除后会在下一次启动时补回。删掉一个出厂分区的目录，它会以出厂状态（`schedule.enabled: true`）重新出现；要停用出厂分区，应把它 frontmatter 里的 `enabled` 改成 `false`，而不是删除目录。

只补缺失这条规则有三类例外，都是上游所有的文件：

1. **身份提示 `meta-prompt.md` 和仪表盘页面 `dashboard.html` 从不复制进内核。** 仪表盘页面在每次访问 `GET /dashboard` 时从出厂目录读取，出厂目录默认就是包内的 `bootstrap/`。身份提示在每次装配系统提示时从磁盘读取，读取位置见列表后的说明。
2. **`~/.aladuo/var/` 各子目录里的 `DUODUO.md` 每次启动重新复制。** 它们是运行时各个数据目录的使用说明，放在运行时数据目录而不是内核里。身份提示只告诉 agent"去运行时目录里找 `DUODUO.md`"，不把说明内容写死在提示词里。
3. **内核的 `.gitignore` 每次启动补上缺少的上游条目。** 只追加，不删除用户自己加的行（4.1）。

**身份提示从哪里读取，取决于两个环境变量。** 代码只在环境变量 `ALADUO_META_PROMPT_PATH` 指定的文件、或 `ALADUO_BOOTSTRAP_DIR` 指定目录下的 `meta-prompt.md` 里找它；两个变量都没有设置时，系统提示里的身份这一层为空。npm 包里的启动脚本、CLI 和 daemon 的代码都不设置这两个变量；默认安装后 daemon 进程是否带着它们启动，本文没有实测。

读取位置指向包内时，升级 npm 包后身份提示立即换成新版。身份提示本身约 14 KB。无论读取位置在哪里，身份提示和仪表盘页面都不在内核里，内核里 agent 自己写的文件不受它们的更新影响；上游提供的文件和 agent 自己写的文件因此在文件层面就分开了。

出厂文件里与产品设计关系最大的有三项：记忆板 `memory/CLAUDE.md` 出厂为 0 字节，记忆从零开始积累；四个出厂分区的提示词决定后台的初始行为，合计约 47 KB（gradient-distiller 约 17 KB、intuition-weaver 约 18 KB、pattern-tracker 约 8 KB、memory-committer 约 4 KB），每次分区会话的输入都包含自己那一份去掉 frontmatter 后的全部正文；各 `DUODUO.md` 让 agent 按需查找运行时的能力，而不是把它们全部写进提示词。

**出厂文件里已经没有、但较早安装的内核里可能还留着的两个分区（memory-weaver 和 cadence-executor），运行时每次启动时把它们退休：只关闭调度，不删除。** 它们的职责在当前出厂配置里由别处承担：记忆板的修改由 gradient-distiller 和 intuition-weaver 两个分区分工完成，任务单由运行时直接写进各分区的收件箱（4.3）。退休分三步：

1. 先确认目录确实是官方的那一份，而不是用户挪作他用的同名目录。判断依据是 frontmatter（文件顶部的配置块）：memory-weaver 必须带有效的、声明自己名字的 `contract:`，cadence-executor 必须没有 `contract:`。对不上就不动。
2. 如果 `~/.aladuo/var/meta/partitions/<分区名>.retired` 这个标记文件已经存在，说明退休做过了，这次不再处理；分区本来就是停用状态时也不处理。
3. 否则先写标记文件，再把该分区 frontmatter 里的 `schedule.enabled` 改成 `false`，心跳从此不再唤醒它。分区目录本身和它的 git 历史都不动。

用户想继续运行这个分区，手工改回 `enabled: true` 即可，标记文件保证运行时不会再改第二次。

### 4.3 从事件日志到记忆板的流水线

**运行时负责发现问题，模型负责处理问题：每次心跳里的只读检查测量记忆文件和事件日志，把发现写成任务单投进分区收件箱；四个出厂分区按"写碎片、改记忆板和档案、写规则节点、提交 git"分工处理。** 心跳本身怎样运行、分区在什么条件下被唤醒，见 3.2 和 3.3 节；本节讲被唤醒之后做什么。

**只读检查与任务单。** 只读检查是运行时代码，不调用模型，也不修改任何记忆内容（默认关闭的遗忘 GC 除外，见 4.5）。它发现某类问题时，产出一类"信号"，把信号写成一份文本工单（`.pending` 文件，本文叫任务单）投进某个分区的收件箱。各类信号的触发条件和收件分区如下：

| 信号 | 运行时在什么情况下发 | 投给 |
|---|---|---|
| scan-gap | 事件日志里有一段外部事件还没交给 distiller 处理。当天的事件要等最后一条用户消息之后至少过去一个心跳间隔才交出；每段时间区间只交一次，上一张没处理完不发下一张 | gradient-distiller |
| fold-gap | 有碎片比 intuition-weaver 上一次运行结束的时间更新 | intuition-weaver |
| claude-compress | 记忆板超过 100 个非空行，或有一行超过 200 个字符（计数规则见 4.5） | intuition-weaver |
| claude-lint | 记忆板上有 `[[slug]]` 链接指向不存在的档案 | intuition-weaver |
| claude-flatten | 记忆板上有 Markdown 标题行 | intuition-weaver |
| entity-converge | 有实体档案还没有整理成 What it is now、Relationship、Open variables 这几段固定结构；按体积从大到小，每次取一份 | intuition-weaver |
| merge | 记忆板链接的某个名字同时存在 `entities/` 下的实体档案和 `topics/` 下的同名档案，且已有效果记录；`topics/` 那份的类型标为领域知识的除外 | intuition-weaver |
| revise | 记忆板链接的 `topics/` 下某个行为类档案已有效果记录，但仍是旧的 `# Pattern:` 写法（要求改写成 lesson 或 groove 节点）；效果变弱的排在前面 | pattern-tracker |
| node-converge | 某个 lesson 或 groove 节点出现了规定格式之外的小节，或超过 200 行 | pattern-tracker |
| orphan-newborn | `topics/` 下有文件从记忆板走不到、也没有别的文件引用，且 48 小时内改动过（孤儿文件的定义见 4.5）；每个文件单独一张 | 文件名以 lesson- 或 groove- 开头的投 pattern-tracker，其余投 intuition-weaver |
| orphan-islands | `topics/` 下有文件从记忆板走不到，但被别的文件引用 | intuition-weaver |
| activation-report | 记忆板存在时每次都生成一份报告：在最近 30 个有用户消息的日子里，记忆板每一行指向的档案被前台会话读过几次，以及哪些文件被读过、却从记忆板走不到 | intuition-weaver |

投递遵守四条规则：

1. 每类信号每次心跳至多一张任务单，唯一的例外是 orphan-newborn，每个新孤儿文件各一张。实体档案、规则节点这类按文件发现的问题，每次只取排在最前面的一份，其余留给以后的心跳。
2. 收件箱里同名任务单还没被处理掉之前，不重复投递，也不覆盖。
3. 任务单只投给在 frontmatter 的 `contract:` 里声明"我接收这类信号"的分区，这叫契约过滤。作为投递对象的几个分区都不接收任何信号、且遗忘 GC 没有打开时，整次检查直接跳过（契约过滤的细则见 5.1 节）。
4. 一次检查的各个步骤全部成功后，运行时删掉自己先前投递、而这次检查已不再产生的任务单（问题已经消失，或分区已不再接收这类信号）。scan-gap 按区间只发一次，不参与这一步；分区自己写进收件箱的文件也不动。

**四个分区的分工。** 下图是出厂配置下信息的走向：

```
事件日志里的外部事件（用户消息、job 的开始与结束等）
   │  只读检查发 scan-gap
   ▼
gradient-distiller ──写──▶ memory/fragments/  碎片：每条指向记忆板某一行，或标为新信号
   │  只读检查发 fold-gap
   ▼
intuition-weaver ────写──▶ memory/effectiveness/  每行的效果记录
                     写──▶ memory/CLAUDE.md（记忆板）、memory/entities/（实体档案）
pattern-tracker ─────写──▶ memory/topics/lesson-*、groove-*（规则节点）
   │
   ▼
memory-committer ── git add + git commit：允许范围内的全部改动，每次运行至多一个提交
   │
   ▼
会话下一次处理之前比对指令指纹（4.6）
```

gradient-distiller（下称 distiller）负责提炼证据。收到 scan-gap 任务单时，它用 `duoduo spine cat --interval '<日期>[t1,t2]' --kind external` 读出任务单指定区间内的外部事件，由用户消息打开的回合还附带模型在这一回合里的工具调用和回复；命令输出以一行结束标记收尾，distiller 必须看到这行标记才算读完。

它把记忆板整份放在上下文里，逐条事件对照记忆板的每一行判断：这一行起作用了（STRENGTHENING），该起作用却没起（WEAKENING），没有相关证据（NEUTRAL），或者事件里有记忆板上还没有的长期信号（NEW_SIGNAL）。判断为值得记录的，写成一个碎片文件放进 `memory/fragments/<日期>/`，里面记下来源事件的标识、指向的记忆板行和判断标签。对 WEAKENING，它可以再标出失败原因：是模型没打开这一行指向的档案（recall-miss），还是这一行本身的内容错了（direction-wrong）。

处理完区间后，即使没写任何碎片，它也删掉任务单表示已处理；时间不够时，它记下读到哪一条，下次从那里继续。distiller 只写碎片和这个续读位置，不改记忆板。

intuition-weaver（下称 weaver）负责改记忆板，是记忆板、效果记录和实体档案的唯一写者。收到 fold-gap 后，它自己找出"过期"的行（有碎片比这一行的效果记录更新），按时间从新到旧处理：把这一行的全部碎片重新汇总，整份重写 `memory/effectiveness/<slug>.md`（效果记录是现状快照，记录这一行目前有几条增强、中性、削弱证据和代表性样本），并在同一次运行里决定这一行的去留。

标为 NEW_SIGNAL 的碎片汇总进 `memory/effectiveness/new-signals.md`；一个候选只有在多份不同的碎片里反复出现，或者用户明确提出了长期要求时，才在记忆板上新增一行，否则内容先写进档案。weaver 对记忆板能做的只有五种动作：新增、改写、调整顺序、把一行移出记忆板（上游叫 retire，与 4.2 的分区退休无关）、修正指针。它按对行为影响的大小给任务单排序，在时长预算内能做多少做多少；没做完的任务单留在收件箱，问题还在，运行时就会继续投递。

pattern-tracker（下称 tracker）负责提炼规则，是 lesson 和 groove 节点的唯一写者。只有最新的碎片比最新的规则节点更新，或者收件箱里有可处理的任务单时，它才开始工作。一次完整的纠正经过（模型偏离、人纠正、纠正后的做法被接受）就足以写成一个 lesson；一组碎片显示同一类任务被反复执行、并收敛到稳定步骤时，写成一个 groove。每个节点只写一条规则，格式是"触发条件 + 执行步骤"。

新建的规则节点必须从一个记忆板可达的档案链接过去，而且链接只能加在 tracker 自己写的 `topics/` 文件里；找不到这样的位置时，它不消费对应的碎片，在报告里写明缺哪条链接，留到以后处理。

memory-committer（下称 committer）负责提交。每次运行时，它把工作树（磁盘上文件的当前内容）里允许范围内的改动合成至多一个提交。允许范围是记忆板、`memory/entities/`、`memory/topics/`、各分区的 `CLAUDE.md`（后台分区总纲除外）、`playlist.md` 和 `config/` 下的 Markdown 文件。修改时间落在这次运行期间的文件先跳过（写者可能还没写完），下次再提交；剩下的改动如果全是空白或行序调整，这次不提交。

提交信息的格式是 `<范围>(<方面>): <演化了什么>`，范围取 memory、subconscious、config 之一，方面是一个说明改了什么的简短标签；只说"做了事"、不说"演化了什么"的提交信息不被接受。committer 只执行 `git add` 和 `git commit`，不审查内容，理由见 4.7。

**改动在写入磁盘时就生效，不等提交。** 前台会话读的是工作树里的 `memory/CLAUDE.md`，不是 git 最近一次提交里的版本。所以 weaver 改完记忆板，新开的会话立刻用上新版，在跑的渠道会话下一轮收到提示（4.6）；committer 的提交是为了留下可以撤销的历史，不是改动生效的前提。

上游把这条流水线叫 "text gradient"，借用机器学习里"梯度"一词表示"该往哪个方向改"：碎片告诉 weaver 每一行该往哪个方向改，activation report 告诉它哪些行指向的档案根本没人读。实际执行判断的仍然是模型。

**一个例子：一次纠正怎样变成记忆板上的一行。** 下面的步骤之间都隔着若干次心跳（默认每次约 37 分钟），具体隔多久取决于轮转表的顺序、各分区的冷却和 3.3 节的跳过条件：

1. 用户在飞书上纠正 agent："发周报之前先核对上周的数字。"这条消息作为外部事件写进事件日志。
2. 这段时间的事件还没交给 distiller。最后一条用户消息之后过了一个心跳间隔，下一次心跳的只读检查给 distiller 投一张 scan-gap 任务单，写明这段时间区间。
3. 轮到 distiller 时，它读出这段区间，发现记忆板上没有相关的行，写一条 NEW_SIGNAL 碎片；如果记忆板上有相关的行而模型没照做，就写一条 WEAKENING 碎片。
4. 新碎片比 weaver 上次运行更新，下一次心跳给 weaver 投 fold-gap。weaver 把这条新信号记进 `new-signals.md`。用户说的是一条长期要求，满足"用户明确提出"这一条件，weaver 在记忆板上新增一行：触发条件"发周报之前"，方向"先核对上周的数字"，必要时带一个指向档案的 `[[slug]]`。
5. tracker 如果从碎片里看到一次完整的纠正经过，并能从一个可达的档案链接过去，会另写一个 lesson 节点记录具体步骤。
6. 第 4 步 weaver 把这一行写进磁盘之后（不等第 7 步的提交），新开的渠道会话在系统提示里直接带上这一行；已经在跑的渠道会话在下一轮收到"记忆板已变"的提示（4.6）。
7. committer 下一次运行时把记忆板和档案的改动做成一个提交。这一步只留下可以撤销的历史，不影响第 6 步。

第 2 步和第 3 步之间可能等得比较久。任务单写在运行时数据目录里，不改变 3.3 节的活动指纹；投递任务单的那次心跳之后，如果既没有新的外部事件、记忆目录也没有变化，后台分区不会运行，这张任务单要等到下一次有变化的心跳才被处理。

### 4.4 防止正反馈的三条规则

**duoduo 用三条规则防止系统把自己产生的信号当成新证据：每处修改都要有行级证据；只有外部事件能成为证据；信息只能单向流动。** 系统把自己的输出当成新的输入时，同一个信号会被反复计入、一次比一次强，这种正反馈是自治系统最常见的失败。前两条主要写在分区提示词里，其中"只看外部事件"也由读取事件日志的命令和运行时的只读检查在代码里执行；第三条一部分由代码里有没有对应的通道决定，一部分写在后台分区总纲里。

**第一条：每处修改都要有行级证据。** distiller 的每个碎片必须写明它检验的是记忆板哪一行，或者明确标为"没有对应的行"。weaver 在改记忆板的任何一行之前，必须先拿到这一行的证据，证据只有三种来源：这一行的效果记录；任务单附带的轨迹证据；或者实测到这一行"冷"了，即两项条件同时成立——在 activation report 的整个统计窗口里，这一行指向的档案没有被读过，并且没有更新的碎片引用这一行。三种都没有，就不改，只在报告里写明缺什么证据。

只有两类纯形式修复不需要效果证据：删除记忆板里的标题行（标题行没有指针，本来就不会有效果记录）；把一行里写得过多的细节移回它指向的档案（内容只是换位置，行为和指针都不变）。分区报告里的每个数字也必须能由磁盘上的文件复算：涉及这次新写和原有的证据时，要写成"N 条新增 + M 条原有 = 总数"的形式，对不上就按文件能证明的数字往下调。这样，"事件 → 碎片 → 效果记录 → 修改"每一步都是可以复查的文件，模型无法在没有依据的情况下宣称"这条经验很有效"。

**第二条：只有外部事件能成为证据。** 事件按来源分为内部和外部两类，划分标准见 3.3 节：运行时自己产生的事件属于六类内部来源，一律不能成为记忆证据；其余来源的事件，例如渠道消息，job 会话的开始、完成和失败，算外部事件。这条规则在四处执行：

- 运行时决定把哪段时间交给 distiller 时，只统计外部事件。
- distiller 读日志用的 `--kind external` 按事件来源过滤。由用户消息打开的回合，会把回合里模型的工具调用和回复一起列出来，供 distiller 看清当时发生了什么；但提示词规定这些内部记录本身不能作为碎片的来源，碎片的出处必须落在那条外部事件上。job 的开始和结束事件单独列出，不展开回合，其中的结果摘要就是全部证据。
- weaver 的提示词写明只有外部事件能成为记忆证据；一张只带内部运行痕迹的任务单，除了对已有记忆文件做纯粹的维护，不会引起任何内容修改。
- activation report 里的数字是运行时对记忆层的测量，只用来影响 weaver 的判断，不写进记忆板、档案或效果记录。

**第三条：信息只能单向流动。** 下表逐条列出各方之间有没有通道、通道是什么：

| 方向 | 通道 |
|---|---|
| 外部世界 → 后台分区 | 只经事件日志，而且只有外部事件能成为证据 |
| 后台分区 → 前台 | 为此设计的途径有三种：记忆板（新会话直接注入，在跑的渠道会话下一轮收到更新提示）；档案文件（前台按 `[[slug]]` 指针按需读取）；Notify 通知（投进目标会话的邮箱，不插入对方正在进行的一轮）。碎片和效果记录不注入前台，身份提示也只引导前台去读记忆板和档案。另有一条提示词没有提到的途径：渠道种类配置，见表下说明 |
| 前台 → 后台分区 | 运行时没有提供直接通道：分区收件箱只由运行时的只读检查填写，分区会话也不读任何会话邮箱。前台的经验只能先写进事件日志，再被 distiller 读到 |
| 运行时 → 模型 | 只发带上下文的任务单；运行时不改写记忆板、档案和分区提示词的正文（运行时直接写哪些内核文件，见 4.7） |
| 分区 → 分区 | 总纲禁止改其他分区的提示词；跨分区的需求写进自己的最终报告。最终报告作为来源为后台分区的内部事件写进事件日志，不会成为记忆证据 |
| 分区 → 收件箱 | 分区对收件箱唯一的写操作，是删除自己处理完的任务单 |

后台分区到前台的第四条途径是渠道种类配置 `config/<种类>.md`。它的正文是渠道会话系统提示里的人格层（1.3 节）；总纲的授权清单里没有它，禁止清单里也没有它，Claude 分区能直接写它，committer 的允许范围也包括它。分区改了它，新开的渠道会话直接用上新人格，在跑的渠道会话由指令指纹发现变化，按 4.6 节的规则换上新人格。

表中说的是运行时提供的通道。前台的 Claude 会话有 Bash、默认不弹审批，能写启动 daemon 的那个系统用户有权限的任何文件，包括分区收件箱，运行时不做检查（5.1 节）；"前台不直接改后台"这条边界没有代码检查。

另有一条规则防止运行时和分区之间形成循环：总纲规定，一条检查结果在对应的任务单执行之后仍然反复出现，说明问题出在指导写作的那份提示词（上游称 charter），而不在检查结果指向的那个文件；分区把它作为提示词问题写进最终报告，不再按任务单反复处理。tracker 的提示词对孤儿警告有同样的规定：已经报告过无法链接的节点再次收到警告时，只在报告里写一行、删掉任务单，不再重做。

### 4.5 记忆分层与预算

**duoduo 把记忆分成三层：记忆板有行数和长度预算，自动注入；档案默认不读，按指针按需读取；原始记录不注入前台，由后台提炼后才进入上两层。** 这样分层，是因为自我改进的产出只有进入模型的上下文才起作用，而上下文窗口有限。

| 层 | 载体 | 怎样进入上下文 | 预算与规则 |
|---|---|---|---|
| 第一层：记忆板 | `memory/CLAUDE.md` | 渠道会话、job 会话和系统会话把它的正文放进系统提示（1.3 节），模型不用主动去读；记忆板为空时这一层不出现。分区会话只拿到它的路径，需要时自己读 | 至多 100 个非空行，每行至多 200 个字符；超出就发 claude-compress 任务单 |
| 第二层：档案 | `[[slug]]` 指向的实体档案和规则节点 | 默认不读，模型按指针自己读 | 身份提示规定的检查点：做有后果的动作之前，必须先打开相关档案 |
| 第三层：原始记录 | 事件日志、碎片、效果记录 | 不注入前台的上下文；由分区会话读取，事件日志经 `duoduo spine` 命令读取 | 经分区提炼才进入上两层 |

Claude 分区会话启动时，运行时把记忆目录列为附加目录，同时显式关掉 Claude Code 自动读入附加目录里 `CLAUDE.md` 的功能，所以记忆板不会被自动带进分区会话，分区需要时自己读。

**记忆板的每一行由触发条件、一句方向和一个 `[[slug]]` 指针组成。** 模型遇到触发条件时打开指针指向的档案，在档案里读具体做法；不需要单独步骤的简短规则可以不带指针。记忆板上不允许有标题，行与行的聚类靠顺序表达；运行状态、带日期的回顾、计数之类的内容放进档案。计数时不算空白字符，一个 `[[slug]]` 链接只算 1 个字符；两个上限可以分别用环境变量 `ALADUO_MEMORY_MAX_LINES` 和 `ALADUO_MEMORY_MAX_LINE_CHARS` 修改。

行的顺序本身也起作用：weaver 的提示词写明，模型对一段文本开头和结尾的内容关注度高、中间的关注度低，相邻的行会被当成一组来读，所以它把最需要生效的行移到开头和结尾，把相关的行放在一起。

**档案的检查点由身份提示规定。** 对一个有档案的具名实体或具名流程，在执行破坏性的 Bash、Edit、Write 操作，通知别人，做持久的状态改动，或给出确定的建议或拒绝之前，模型必须在当前会话里打开那份档案；要执行一个由 lesson 或 groove 节点描述的重复流程之前，必须先读那个节点。除此之外默认不读：记忆板上的摘要已经足够回答的简单问题，直接回答。模型对人说话时不提文件路径。

档案里的每条主张都标明它属于哪一类知识：`[observation]` 是记录下来的事实，`[inference]` 是推断，`[instruction]` 是承诺遵守的规则，`[conditional: 事件]` 只在该事件发生时有效，`[hypothesis (unratified)]` 是未经确认的假设，`[superseded 日期: 新结论]` 表示已被取代。

发生冲突时，当前观察到的事实可以推翻档案里的 observation 和 inference；对 instruction，当前观察只能用来判断这条规则的前提还是否成立，不能直接推翻规则。例如档案写着"部署前必须跑测试"，今天测试跑得很快，也不能因此跳过。

**运行时会不会自动清理一个记忆文件，只看它能否从记忆板出发沿 `[[slug]]` 链接走到，不看访问次数。** 访问次数由 activation report 统计，交给 weaver 判断。运行时从记忆板出发，沿链接逐层找出所有能走到的档案，这个检查只针对 `memory/topics/` 下的文件；走不到的叫孤儿文件，再分三种状态：被别的档案引用、只是没接到记忆板上的，叫 ISLAND；没有被引用、且最后修改距今不到 48 小时的，叫 NEWBORN，运行时先给它的写者发一张 orphan-newborn 警告；没有被引用、且超过 48 小时的，叫 STALE。

时间只在这里起作用，而且看的是修改时间：改动一个 STALE 文件，它就回到 NEWBORN。只有 STALE 文件可能被遗忘 GC 删除，删除用的是 `git rm`，文件仍在 git 历史里；遗忘 GC 默认关闭，打开它需要满足的全部条件见 5.1 节。运行时不记录某个文件是否真的收到过警告，三种状态每次都按修改时间和引用关系重新计算。

一行能否留在记忆板上，由 4.3 和 4.4 的证据决定：效果变弱的行是改写或移出的候选；统计窗口里指向的档案没人读、也没有更新碎片引用的行，默认移出记忆板。统计窗口只数有用户消息的日子，所以一段时间没人使用，不会让记忆板上的行因为"没人读"而被移出。

### 4.6 改动如何生效：指令指纹

**记忆板改动后，新开的会话直接装入新版；在跑的渠道会话不重建，下一轮收到一条"记忆板已变"的提示。身份提示、渠道人格或 job 任务书改变时，Claude 的流式连接重建，Codex 分叉出一条带新指令的线程。运行时靠比对指令指纹区分这几种情况。**

每次处理之前，运行时从磁盘重新读取"当前这套指令"，对它算一个哈希，即指令指纹。参与计算的有：身份提示；渠道会话的种类人格和实例提示；记忆板（展开其中 `@路径` 引用的文件之后的正文）；job 会话的任务书和验收标准。运行时把新指纹与会话存档里的指纹比较，另外单独算一个只针对记忆板的哈希和一个不含记忆板的指纹，用来判断是不是"只有记忆板变了"。

因为每次都按文件内容计算，用保留原修改时间的方式覆盖提示词文件，改动也能在下一次处理时被发现；分区的提示词在每次运行分区之前、job 的任务书在每次处理之前，同样从磁盘重新读取。指令指纹与 3.3 节的活动指纹、2.3 节的配置签名是三个互不相关的机制，术语表里分别有定义。

比较结果分三种情况，各引擎的处理不同：

| 情况 | Claude | Codex | Grok、pi |
|---|---|---|---|
| 只有记忆板变了 | 流式连接不重建，继续使用原来的系统提示，输入缓存不中断。新版记忆板在这条连接下次重建时进入系统提示，例如空闲回收之后，或者压缩历史之后（压缩后缓存本来就要重建，运行时借这个时机换上新版） | 渠道会话沿用原线程；job 会话从原线程分叉一条新线程 | 会话不重建，只更新存档里的指纹 |
| 身份提示、种类人格、实例提示、任务书或验收标准变了 | 关闭当前流式连接，下一轮用新系统提示重建连接，续接原会话，对话历史保留 | 从原线程分叉一条带新指令的线程，按 Codex 的分叉方式继承原有历史（本文没有实测）；没有可分叉的线程，或分叉请求失败时，改为新建线程，历史不保留 | 会话不重建，只更新存档里的指纹 |
| 都没变 | 不做任何事 | 不做任何事 | 不做任何事 |

表中 Claude 一列说的是渠道会话使用的流式连接。Claude 的 job 会话不使用流式连接，每次运行都带上当前的系统提示，所以任何改动都在下一次运行时生效。不保留历史的 job（frontmatter 写了 `stateless: true`，3.1 节）每次运行都是一段新会话，不续接、也不分叉，同样在下一次运行时用上新指令。

Codex 需要分叉，是因为它的系统提示只在新建线程或分叉线程时随请求交给 Codex，续接已有线程时请求里不带指令。

Grok 和 pi 上，新文本何时到达引擎取决于它们的传入方式（1.3 节）：Grok 在 `override` 模式下，文本一变就在下一次调用前重新载入会话，在默认的 `append` 模式下只有新建的会话才带上新文本；pi 的 worker 进程只在启动时接收一次系统提示，新文本要等 worker 重新启动才生效。

记忆板变了之后，所有渠道会话（不论引擎）都会在下一轮的每轮瞬时块（2.4 节）里收到一条提示，说明记忆板已经变了、需要时去读哪个文件；读不读由模型决定。同一版记忆板的提示只发一次。

还有一项设置保证改动能进入正在续接的 Claude 对话：Claude Agent SDK 默认在一段对话第一次请求时记下系统提示，之后每次请求和续接都原样沿用，直到这段对话被压缩。duoduo 调用 SDK 时显式关掉了这项记录，否则上表中"续接原会话、换上新系统提示"不会生效。

指纹变化时，新指纹写进会话的状态文件。日志级别为 info 时（环境变量 `ALADUO_LOG_LEVEL`；未设置时默认 warn，`NODE_ENV=development` 时为 info），daemon 日志记下新旧两个指纹（fp_old、fp_new）；Claude 的流式连接因指令变化或压缩后换记忆板而被标记重建时，daemon 日志不论级别都会记一条 needsRecreation 记录。要追溯每一次自我修改在什么时候生效，需要把日志级别设为 info（5.4 节）。

### 4.7 谁能改什么

**分区能改什么写在提示词里，少数硬检查写在代码里，每个文件都有约定的写者。** 代码强制的检查（契约过滤、分区工具白名单等）列在 5.1 节；本节讲提示词层的授权、修改的方式、内容质量由谁把关，以及每个文件归谁写。

**授权清单写在后台分区总纲 `subconscious/CLAUDE.md` 里。** 这份清单是提示词层的约束，模型有可能违反；违反后可以从 git 历史发现并撤销。

分区可以改的文件：

- 自己分区的 `CLAUDE.md`，改进自己的工作方式；
- 新建分区目录，增加新的能力；
- `playlist.md`，调整运行节奏；
- `memory/CLAUDE.md`，影响 agent 在所有会话里的想法。

分区不能碰的东西：

- 事件日志，它是不可更改的历史；
- 锁文件；
- 收件箱：由运行时填写，分区唯一能做的是删除自己处理完的任务单；
- job 调度：重复性的需求写进最终报告，不自己建 job；在 Claude、Codex、Grok 上，分区会话也拿不到创建 job 的工具（pi 上的例外见 1.6 节）；
- 其他分区的 `CLAUDE.md`：跨分区的需求写进最终报告；
- 任何分区的 `contract:` 声明：这是给运行时读的机器声明，归运行时所有，随上游刷新。

**修改用的是普通工具，没有专门的"自我修改"工具。** 每个分区会话以自己的分区目录（`~/aladuo/subconscious/<分区名>/`）为工作目录启动，修改自己就是在这个目录里使用 Edit、Write、Bash。对默认的 Claude 引擎，工作目录只是起点，不是沙箱：会话以不弹审批的方式运行（1.7 节），用绝对路径同样能读写内核里的其他文件，授权清单里的 `playlist.md`、`memory/CLAUDE.md` 都在分区目录之外，Claude 分区就是这样修改它们的。

分区若在 frontmatter 里配置为 Codex 引擎，情况不同：Codex 会话在沙箱里运行，分区会话的默认级别是 workspace-write（可用环境变量 `ALADUO_CODEX_SANDBOX` 改成 read-only 或 danger-full-access）。按 Codex 对 workspace-write 的定义，会话只能写自己的工作目录，也就是分区目录（这一点是 Codex 的行为，本文没有实测）。

运行时也不把记忆目录加进 Codex 的可写范围，所以默认配置下 Codex 分区写不了 `playlist.md` 和 `memory/CLAUDE.md`，授权清单里这两项对它不成立。

**committer 不审查内容，因为拦住提交拦不住坏内容生效。** 前台会话读的是工作树（4.3），一行坏内容写进磁盘就已经生效，是否被提交不影响这一点；如果 committer 因为内容不合格而不提交，这行内容照样生效，却因为不在 git 历史里而无法用 revert 撤销。所以 committer 把允许范围内的改动全部提交，靠 git 历史恢复。内容质量由另外三处把关：写者自己的证据规则（4.4 第一条）；来源边界，内部事件不能成为证据（4.4 第二条）；下一次心跳的只读检查（超长、断链、标题行等）。任何一行出了问题，都可以用一次 git revert 撤销。

**文件所有权清单**说明每份文件由谁写。duoduo 里的文件由人、模型、运行时三方共同书写，每一份都有约定的写者：运行时写哪些文件由代码决定，模型之间的分工由提示词约定。

| 文件 | 写者 | 其他各方 |
|---|---|---|
| 事件日志 | 运行时，只追加 | 人和模型只读 |
| 会话邮箱 | 运行时：写入指针、处理、删除已完成的条目 | 人和模型都不应修改 |
| `playlist.md` | 三方共同书写 | 运行时每次运行一个分区后把它的 `- [ ]` 勾成 `- [x]` 并在 History 下记一行，整轮勾完后用所有启用的分区重建新一轮；分区和人都可以直接改写；刷新流程用上游的空表覆盖它（4.8） |
| 记忆板、实体档案 | 模型：出厂分工下 intuition-weaver 是唯一写者；总纲本身允许任何分区改记忆板 | 运行时只测量，从不改写；人可以改，git 留痕 |
| 效果记录 | 模型：intuition-weaver 是唯一写者 | 不进 git；weaver 由碎片整份重新生成，人改了会在这一行下次被重新汇总时被覆盖 |
| lesson、groove 节点 | 模型：pattern-tracker 是唯一写者 | 运行时只测量，唯一的例外是默认关闭的遗忘 GC（4.5）；人可以改，git 留痕 |
| 碎片 | 模型：gradient-distiller | 不进 git |
| 各分区 `CLAUDE.md` 的正文 | 该分区自己 | 其他分区不得修改；人触发的刷新流程用上游版本覆盖出厂分区的正文，分区自己的修改也被覆盖（4.8） |
| `contract:` 声明 | 上游，经刷新流程更新 | 运行时只读取；总纲禁止模型修改；运行时把分区提示词交给模型时去掉了整个 frontmatter |
| frontmatter 里的 `schedule:`、`runtime:`、`model:`、`effort:` | 人（成本和引擎的设置） | 刷新流程只保留这四项的本地值；运行时只对退休分区改一次 `schedule.enabled` |
| frontmatter 里的其他键（如 `claude.tools`、`prompt_mode`） | 人 | 刷新流程不保留，本地值丢失（4.8） |
| 后台分区总纲 `subconscious/CLAUDE.md` | 上游 | committer 不提交它；刷新时整份换新 |
| 渠道种类配置 `config/<种类>.md` | 人：直接编辑，或用 `duoduo session config --kind` 写入 | committer 提交进 git；总纲没有提到它，Claude 分区也能写（4.4） |
| 全局配置 `config/runtime.md` | 人：直接编辑，或用 `duoduo session config --global` 写入 | 不进 git |
| 身份提示 `meta-prompt.md`、`~/.aladuo/var/**/DUODUO.md` | 上游 npm 包 | 升级 npm 包后换成新版（身份提示要求读取位置指向包内，见 4.2）；前者不进内核，后者每次启动重新复制 |
| 锁文件、索引、会话状态 | 运行时 | 任何一方都不应手改 |

**运行时自动写入内核的只有以下几类：**

- 出厂文件的初始化和补缺失（4.2）；
- 首次建仓的提交和 `.gitignore` 的上游条目（4.1）；
- `playlist.md` 的勾选、History 记录和整轮重建；
- 退休分区的 `schedule.enabled`（4.2）；
- 分区用 `.claude/agents/*.md` 定义的子代理：运行时每次启动为它们生成一份 Codex 格式的副本（`.codex/agents/*.toml`，1.3 节），并删掉已没有来源的副本；
- 默认关闭的遗忘 GC 执行的 `git rm`（4.5）。

除此之外，只有人或模型显式执行的命令会经由运行时的代码写内核，例如 `duoduo session config` 写配置文件，`duoduo memory reclaim` 手动处理孤儿文件。

产品经理评估这类系统时会问："它会不会把自己改坏？"所有权表不能排除这种可能：它是提示词层的分工，不是代码限制，Claude 分区会话默认不弹审批，能写内核里的任何文件。

所有权表能回答的是另一个问题：改坏之后能不能恢复。按这份分工，模型会改的记忆板、档案、规则节点、分区提示词、轮转表和渠道种类配置都在 git 里，改坏了可以 revert；碎片和效果记录不进 git，但可以从事件日志和碎片重新生成；`config/runtime.md` 和分区的 `.claude/agents/*.md` 不进 git，改坏了只能手工恢复。

### 4.8 上游更新怎样进入内核

**npm 升级只补缺失文件，不覆盖 agent 的修改；分区提示词的刷新由人触发，会覆盖出厂分区的文件，被覆盖的内容留在刷新前的 git 历史里。回滚由人或模型执行 git revert，运行时没有自动回滚。** 上游的更新经下表四项机制进入内核：

| 机制 | 效果 |
|---|---|
| 只补缺失文件（4.2） | 内核已存在时，升级只补缺失的文件（包括被删除的出厂文件），不覆盖 memory、subconscious、config 里任何已有的文件。例外只有 4.2 列出的三类上游文件，以及退休分区的 `schedule.enabled`（只改一次） |
| 身份提示和仪表盘不进内核（4.2） | 读取位置指向包内时，随 npm 升级立即更新，不动内核 |
| 分区提示词的刷新由人触发 | 通过 `duoduo-runtime-admin` 技能里的 subconscious refresh 流程进行，会覆盖上游存在的文件，见下文 |
| 契约声明和提示词写在同一个文件里（4.3） | 分区刷新到哪个版本，运行时就按该版本声明的信号投递，不会把新版的信号投给看不懂它的旧提示词 |

**刷新流程先看差异，再合并，最后提交一个回滚点。** 刷新前内核的 git 工作树必须是干净的，否则无关的改动会混进刷新提交；这也保证了刷新前的内容都已经在 git 历史里。流程是：取回上游某个版本标签下的 `subconscious/`，先把与本地的差异给用户看，本地改过上游文件时要用户明确同意；然后逐个复制上游存在的文件，用户自建的分区不动；最后在内核里提交一次，这个提交就是回滚点，刷新后的提示词出了问题，用户可以 `git revert` 它。

**刷新会覆盖上游存在的全部文件。** 被覆盖的有：出厂分区的正文，包括分区按总纲授权对自己做的修改；后台分区总纲；`playlist.md`，当前轮次和 History 记录被重置为上游的空表。

对两边都有的分区 `CLAUDE.md`，frontmatter 只保留 `schedule:`、`runtime:`、`model:`、`effort:` 四项的本地值，因为这些是用户调整成本和引擎的设置；上游文件的 frontmatter 只有 `schedule:` 和 `contract:`，所以 `claude.tools`、`prompt_mode` 等其余本地键在刷新后丢失。技能建议先刷新、再在后续提交里重新应用这些修改；另一种做法是跳过某个文件，代价是这个文件拿不到上游的更新。

运行时在每次运行分区之前都从磁盘重新读取分区提示词，所以刷新后不需要重启 daemon；身份提示不在内核里，它的变化随 npm 升级生效（前提是读取位置指向包内，见 4.2），不需要刷新。

**"回滚点"指 git 里可以 revert 的提交（committer 的提交、刷新流程的那次提交），不指任何自动机制。** 除了遗忘 GC 在提交失败时尝试撤回它自己刚做的删除（5.1 节），运行时里没有回滚内核改动的代码，回滚总是由人执行，或者由模型通过 Bash 执行。这是分工规则的直接结果：自动回滚需要先判断"改坏了没有"，而判断属于模型和人，不属于运行时。

**对产品设计的含义。** duoduo 给自我修改划定的范围是提示词和记忆，不包括代码；记忆板、档案、规则节点、分区提示词、轮转表和渠道种类配置的每次修改都能落进一个可以 revert 的 git 提交。在这个范围内，它可以新建分区、改轮转表、改记忆板。

允许 agent 修改自己，前提是四项机制同时存在：git 历史让这些文件的改动都能撤销；证据规则和来源边界让内部噪声进不了记忆；契约过滤和分区工具白名单是代码强制的检查；指令指纹让改动显式生效，新指纹写进会话状态文件（日志级别为 info 时还记下新旧指纹）。缺少其中任何一项，错误的自我修改就可能既发现不了、也撤销不了。

记忆的做法值得单独注意：在检索增强（RAG，每次检索相关文档放进输入）和长上下文（把全部资料放进输入）之外，duoduo 用预算把知识压缩成短规则，把细节留在指针后面，以此应对"记忆条目越多，进入上下文的无关内容越多"的问题。这套自我改进没有改完之后的验证：效果记录和 activation report 都是修改生效之后的统计，不是生效之前的测试（6.2 节）。

## 第五部分 · 边界、成本与失败

**duoduo 只用代码强制五项检查，防止的是越权调用（工具白名单、控制面分层）、任务单误投（契约过滤）、并发写坏状态（写锁与归档屏障）和误删记忆（遗忘 GC）；花费由 5.2 节的措施限制，其中活动指纹、每次心跳至多两个分区、job 必须指定模型也由代码执行。其余约束写在提示词里：模型违反后落在内核里的改动可以从 git 历史发现并撤销，其余的只能从事件日志和运行日志追查。每一类失败都有规定的处置，事后可以从账本、事件日志和 git 历史查到发生了什么。**

本部分依次说明代码强制哪些检查（5.1）、用哪些措施控制花费（5.2）、每类失败怎样处置（5.3），以及事后从哪里查到花费、事件和修改记录（5.4）。

### 5.1 代码强制的检查清单

下表五项检查由运行时代码执行，不依赖模型是否遵守提示词；提示词里的授权清单（4.7 节）不在表内。

| 检查 | 防止什么 | 代码怎么做 | 详见 |
|---|---|---|---|
| 工具白名单 | 无人值守的会话调用未经允许的内置工具 | 白名单只对 Claude 引擎的会话和分区生效。Claude 会话默认只有 15 个核心工具：Bash、Read、Write、Edit、Grep、Glob、Agent、TaskStop、Skill、ToolSearch、TaskCreate、TaskGet、TaskUpdate、TaskList、SendMessage；WebSearch、WebFetch 等联网工具不在其中。Claude 引擎的分区会话默认只有 Bash、Read、Write、Edit、Grep、Glob 六个。增加内置工具的唯一入口是 frontmatter 里的 `claude.tools` 列表（渠道种类、渠道实例、job、分区都可以写），列出的工具与核心工具取并集。其他三个引擎不用这份白名单：Codex 的内置工具无法禁用，改由沙箱限制它能写的目录；Grok 会话固定关闭 Grok 自带的六个工具（三个定时调度工具，以及监控、工作流、更新目标），其余照常可用；pi 没有这一层限制 | 1.7 |
| 契约过滤 | 任务单投给不处理这类信号的分区 | 只读检查产生的任务单，只投给 frontmatter 的 `contract:` 里 `consumes` 列表声明了该信号的分区。契约里的信号名带版本后缀（如 `scan-gap.v2`），版本不同也不投：声明 `scan-gap.v1` 的分区收不到 `scan-gap.v2`。分区不存在、`contract:` 里声明的分区名与目录名不一致（防止提示词被复制到别的目录后冒用分区名）、或分区已停用时都不投。没有声明 `contract:` 或 frontmatter 解析失败的分区，例如没有刷新过提示词的旧分区和用户自建的分区，只在实验开关 `ALADUO_EXP_MEMORY_CHECK` 打开时才收到任务单 | 4.3 |
| 写锁与归档屏障 | 两个 daemon 或两段代码同时修改同一份状态 | 一个数据目录只允许一个 daemon：锁文件记录进程号、本机开机标识和最近一次心跳时间，持有者已退出、机器重启过或心跳过期，才能被新的 daemon 接管。同一会话的状态修改在进程内按会话键排队执行。正在归档的会话拒绝一切唤醒和投递 | 2.1 |
| 遗忘 GC | 误删记忆文件 | 这是运行时唯一会删除记忆文件的地方，默认关闭。三个条件同时满足才删：两个实验开关 `ALADUO_EXP_MEMORY_CHECK` 与 `ALADUO_EXP_MEMORY_FORGET` 都打开；文件在 `memory/topics/` 下，并处于 STALE 状态，即从记忆板出发走不到、没有其他文件引用、最后一次修改已满 48 小时（`memory/entities/`、碎片和效果记录从不在候选之列）；负责它的分区（`lesson-*`、`groove-*` 归 pattern-tracker，其余归 intuition-weaver）能接收孤儿警告。删除用 `git rm` 加一次提交，只删已经提交过、没有本地修改的文件，所以被删的文件都能从 git 历史找回；git 正被其他程序占用时本次不删。代码在提交失败时用 `git reset` 和 `git checkout` 恢复这批文件，但按代码推断（在临时 git 仓库上复现过，没有在运行中的 daemon 上实测），默认目录布局下这次提交和恢复都会因为路径写法不匹配而失败：文件已从磁盘删除，删除停在 git 的暂存区（已准备好、还没提交的改动），要等之后某次提交把它带进历史 | 4.5 |
| 控制面分层 | 本机其他用户的程序或网页驱动 agent | 完整控制只经 unix socket；TCP 端口 20233 只放行 6 个只读方法；远程完整控制要显式配置口令和端口 | 本节下文 |

控制面是外部程序（CLI、渠道适配器、dashboard）向 daemon 发指令和读状态的接口，按连接方式分为三种监听：

| 监听 | 谁能连接 | 允许什么 |
|---|---|---|
| unix socket（`~/.aladuo/run/daemon.sock`） | 文件权限 0600、所在目录必须是 0700，只有启动 daemon 的那个系统用户能打开 | 全部方法 |
| TCP 端口 20233，只监听本机地址 | 本机的程序；daemon 检查 HTTP 请求头里声明目标地址的 Host 字段和声明来源网页的 Origin 字段，拒绝不属于本机的值，防止网页借用户的浏览器向这个端口发请求 | 只放行 `system.status`、`usage.get`、`job.list`、`spine.tail`、`system.runtime.info`、`system.config` 六个只读方法，其余方法返回 "Method not available on read-only endpoint" |
| 远程监听，默认不开 | 每个请求都附带口令 `ALADUO_DAEMON_TOKEN`（用 `duoduo daemon token new` 生成）的程序 | 全部方法 |

远程监听由三个环境变量控制：`ALADUO_DAEMON_HOST`（监听地址）、`ALADUO_DAEMON_TOKEN`（口令）和 `ALADUO_REMOTE_PORT`（端口）。三项都设置时开远程监听，地址是 127.0.0.1 也照样开；三项不全时不开，除下列两种情况外 daemon 正常启动。有四种配置会让 daemon 拒绝启动：`ALADUO_DAEMON_HOST` 是非本机地址却没有口令；非本机地址、有口令，却没有设置远程端口；三项都设置了但端口号不在 1 到 65535 之间；三项都设置了但远程端口与只读端口相同。

表外的约束都写在提示词里，例如分区不得修改其他分区的提示词、不得改动事件日志和收件箱（4.7 节）。表内的检查也不等于把模型与主机隔离开：Bash 在 Claude 会话的核心工具里，会话默认不弹审批（1.7 节），所以在没有外层隔离时，一个 Claude 会话拥有启动 daemon 的那个系统用户的文件和网络权限。它可以用 Bash 修改表中检查所读取的配置，例如分区可以编辑自己 `CLAUDE.md` 的 frontmatter，在 `claude.tools` 里给自己加工具，下一次心跳读入后生效；它也可以运行 `duoduo` 命令，经 unix socket 调用完整控制面。duoduo 自身不给 Claude 会话配置沙箱。要限制模型能碰到的文件和网络，可用 Codex 的沙箱、Claude Code 自己的设置文件（duoduo 为 Claude 会话加载用户级和项目级设置；其中的权限规则在默认不弹审批的模式下是否生效，本文未验证），或者把整个 daemon 放进容器或虚拟机。

因此评估风险时应逐项问"如果模型违反了这条约束，会发生什么"。违反提示词约束而改动的记忆和提示词会被提交进内核 git 历史，人能看到 diff 并撤销，下一次心跳的只读检查还会报告断链和超长；表内的检查由代码执行，模型能改变的只是检查所读取的配置，不能改变检查逻辑本身。这些配置的修改记录分两种情况：分区 frontmatter 和渠道种类配置在内核里，修改会进入 git 历史；全局配置 `config/runtime.md` 被 `.gitignore` 排除，渠道实例配置和 job 文件在运行数据目录里，这三处的修改都不进 git，只能从事件日志和运行日志追查。

### 5.2 成本控制措施

duoduo 的成本措施分四类：减少模型调用次数，降低每次调用的输入花费，限制后台的工作量和所用模型的价格，释放闲置的引擎进程；另有用量账本记录每次调用的花费，不减少花费本身，但让每一笔都能事后核对。下表第一列标出每项措施所属的类别。

| 类别 | 措施 | 减少什么 | 详见 |
|---|---|---|---|
| 减少调用次数 | 入口分流 | 查状态、改配置、取消等运维命令由网关直接回复，不调用模型 | 2.1 |
| 减少调用次数 | 合并消息 | 邮箱顶部最多 5 条、相邻间隔不超过 3 分钟的普通消息合并为一次调用 | 2.2 |
| 降低输入花费 | 系统提示不含时间戳 | 每轮系统提示的开头逐字相同，输入缓存持续命中；时间等每轮变化的信息放在每轮瞬时块里 | 1.3、2.4 |
| 降低输入花费 | 常驻流式会话 | Claude 渠道会话复用同一条连接，省去每轮的冷启动（0.4 节） | 2.3 |
| 降低输入花费 | 只改记忆板时不重建会话 | 在跑的会话保留原来的系统提示，缓存前缀不变 | 4.6 |
| 降低输入花费 | 空闲自动压缩 | 长时间空闲后，下一条消息要把整段上下文重新写入缓存；按推荐设置（空闲 50 分钟，短于 1 小时的缓存有效期），在缓存过期前先压缩历史，下一条消息写入的内容更短 | 本节下文 |
| 限制后台工作量与模型价格 | 后台跳过条件 | 没有新变化的心跳不运行分区；活跃会话超过 1 个时一次心跳只运行一个分区；每次心跳最多运行两个分区 | 3.3 |
| 限制后台工作量与模型价格 | weaver 按时长预算工作 | 每次运行把收件箱里的任务单按重要性排序，做到时长预算快用完为止，剩下的下次再做 | 4.3 |
| 限制后台工作量与模型价格 | 按引擎的默认模型 | 渠道会话和分区没有指定模型时，使用配置里该引擎的默认模型（`<引擎>.model`），可以借此给后台分区统一配较便宜的模型 | 1.4 |
| 限制后台工作量与模型价格 | job 创建时必须指定模型 | 不沿用主机的默认模型：主机默认模型因机器而异，有的机器上就是最贵的那个 | 3.1 |
| 释放闲置进程 | 空闲回收引擎进程 | 会话空闲 1 小时后释放它占用的引擎进程和内存；这时缓存已过期（5 分钟有效期早已过期，1 小时有效期也刚好过期），保留进程没有收益 | 2.3 |
| 事后核对 | 用量账本 | 不减少花费本身；每次调用（包括每次分区会话）写一条用量记录，花费可以按会话、按分区查到 | 5.4 |

空闲自动压缩由渠道配置里的两个键控制：`auto_compact_idle_minutes`（会话空闲多少分钟后触发）和 `auto_compact_min_context_tokens`（上下文至少多大才压缩），可以用 `duoduo session config` 按渠道实例或渠道种类设置。两个键都大于 0 才启用，默认都不设。运行时每 60 秒检查一次内存里的渠道会话，对空闲时长和上下文大小都达到阈值、且上次压缩之后有过新事件的会话，替它执行一次 `/compact`；每次检查最多触发 8 个会话。触发时间只取决于设定的空闲分钟数，运行时不知道模型服务的缓存有效期，所以空闲分钟数要由用户按所用服务的有效期来定，`smart-compaction` 技能给出的推荐值是 50 分钟。Claude、Grok、pi 会话都参与，Codex 会话不参与。Claude 的压缩结果带有压缩后的上下文大小，阈值不高于这个大小时运行时不再触发，免得反复压缩却降不到阈值以下；Grok 和 pi 的压缩结果没有这个数，阈值只能按 `smart-compaction` 技能里的收支平衡公式手动设定。

这些措施之后仍有一项无法消除的后台花费：只要外部事件或记忆目录自上一次心跳以来有变化，心跳就会运行分区会话。心跳间隔由 `ALADUO_CADENCE_INTERVAL_MS` 设定（默认 2,220,000 毫秒，约 37 分钟），它与"每次心跳最多两个分区"、各分区的运行时长上限一起决定了后台花费的上限，部署前应向用户说明。

### 5.3 失败处置表

duoduo 对每一类失败都规定了处置，并留下记录（日志、事件，或回给用户的一段说明）；影响限于出错的那个会话或那一次运行，例外有两个：daemon 进程内未捕获的同步异常会让进程退出，渠道适配器进程崩溃后这个平台的消息全部停止进入 duoduo。下表按发生位置列出。表中的 agent.error 是事件日志里记录"一次执行失败"的事件类型，agent.result 是记录"一次回复"的事件类型。

| 失败场景 | 处置 | 详见 |
|---|---|---|
| 引擎调用抛错 | 回给用户一段以 `[duoduo:drain-error]` 开头的文字，常见形式是 `agent turn failed at <阶段>` 加错误信息（最长 4000 字符，不含调用栈）和按引擎给出的排查提示；模型的上下文档位配置（`claude.model_profiles`）解析失败时，在调用引擎之前就拒绝，措辞不同但前缀相同。同时写一条 agent.error 事件。由空闲自动压缩引起的错误只写事件，不发到渠道。下面三行的拒绝不带这个前缀 | — |
| 会话的工作目录不可用 | 拒绝执行（workspace_unavailable）：工作目录不是绝对路径或已不存在时，回给用户原因，建议从已存在的目录重新打开，或换一个新的命名会话 | — |
| 引擎不可用 | 拒绝执行（runtime_unavailable），回给用户原因和修复办法，不改用其他引擎。Codex 和 Grok 会话在下一条消息时重新探测，装好或登录后不用重启；Claude 只在 daemon 启动时探测一次，修好后要重启 daemon。pi 不存在"不可用"，缺模型指针时拒绝执行并说明怎么配置 | 1.2 |
| 会话历史属于另一个引擎 | 拒绝执行（runtime_mismatch），说明历史属于哪个引擎、现在配的是哪个；渠道会话发 `/clear` 后即可在新引擎上继续 | 1.4 |
| 续接旧会话失败 | 降级为不带历史重跑这一轮，并写一条阶段为 `resume` 的 agent.error 事件 | — |
| 后台子代理迟迟不回 | 输入通道保持打开；模型答完后连续 10 分钟收不到引擎的任何消息时，计时器强制关闭输入通道、让这一轮结束，并记一条警告 | 2.3 |
| 会话收尾后又来消息 | 收尾时再检查一次有没有新到、还没合并进邮箱的消息，有就再跑一轮；检查时读取出错、无法确认有没有漏掉消息时，保守地再跑一轮，这种保守重跑连续只允许一次，之后等外部唤醒 | — |
| 分区会话超时或报错 | 中止这次运行，写一条 agent.error 事件，错误信息完整写入日志；按连续失败次数推迟下次运行（超时最长推迟 2 小时，报错最长 4 小时）；同一次心跳的其他步骤照常进行 | 3.3 |
| job 的一次运行结束 | 按六种结束情况结算：启动阶段失败、运行中失败、引擎接受这一轮之前被取消、之后被取消、没有送入任何待办、成功。每次运行被认领时记下一个认领游标（上一次调度的时间），结算时游标对不上，说明这次运行已被新的一次取代，不写结果；结算以运行开始时的 job 定义为准，中途修改定义不影响这一次 | 3.1 |
| 邮箱里有读不了的待合并文件 | 移入该会话的隔离目录（quarantine），其余待办照常处理 | — |
| 事件索引或去重记录里有读不了的行 | 装载时跳过这一行（无法解析，或记录的字节位置不合法），其余照常读取。索引整体读失败时按"索引里没有这条事件"处理：调用方给出了时间上限（邮箱待办的写入时间）时，改为按日期倒序扫描日志文件；没有给出时间上限时，这次读取返回空 | 2.1 |
| 遗忘 GC 提交失败 | 代码用 `git reset` 和 `git checkout` 把这批文件恢复原状，本次不删；按代码推断，默认目录布局下恢复本身也会失败，删除停在 git 的暂存区 | 5.1 |
| daemon 关闭时仍有工作在跑 | 最多等 30 秒；超时放弃时记一条日志，列出被放弃的会话及各自的引擎 | 2.5 |
| daemon 进程内的异常 | 未捕获的同步异常视为状态可能已损坏，进程直接退出，是否重启由外部进程管理器决定；未处理的异步错误只记一条日志，daemon 继续运行，这样一个请求处理中的异步错误不会让整个 daemon 退出 | 2.5 |
| 渠道适配器进程崩溃 | 不会自动重启，要人工运行 `duoduo channel <种类> start`；恢复之前，这个平台上的消息不会进入 duoduo | 2.6 |

表中的处置有一个共同点：失败都留下记录，处理范围限于出错的那个会话或那一次运行（开头所说的两个例外除外）。引擎调用抛错、续接失败、分区会话失败写 agent.error 事件；渠道会话因工作目录不可用、引擎不可用或历史不符被拒绝时，拒绝说明作为一条普通回复写入 outbox，记为 agent.result 事件，不写 agent.error（job 等非渠道会话被拒绝时仍写 agent.error）。两种记录都可以用 5.4 节的方式复盘。daemon 对未处理的异步错误只记日志、继续运行，这是最后一层保护，不是常规的错误处理：如果业务代码捕获错误后只打一行日志就继续，无人值守时错误会累积而不被发现。

### 5.4 可观测性

花费、事件和对自身的修改三类记录都可以事后查询：用量账本记录每次调用花了多少，事件日志记录发生了什么，内核的 git 历史记录记忆和提示词被怎样修改。用户能否放心让 agent 常驻，取决于能否查到它花了什么、做了什么、改了什么。下表列出读取方式。

| 读取方式 | 读什么 | 谁用 |
|---|---|---|
| 用量账本 `~/.aladuo/var/usage/<会话键>.jsonl`，RPC `usage.get` 汇总 | 每次调用一条：token 数（按引擎分为新读入、写入缓存、命中缓存、输出等类，见 1.5 节）、成本、工具调用次数与出错次数、首个 token 的延迟、实际服务这一轮的模型 | 运维者核算成本；dashboard 的用量部分 |
| 出站回执里的这一轮统计 | 这一轮的耗时、输入与输出 token、缓存命中率、成本、模型、上下文占用 | 渠道适配器，用来在每条回复下方显示一行统计（页脚） |
| RPC `spine.tail`（只读端口可调用） | 按条数上限和事件 id 游标读取最近的事件：调用方带上"上次读到的事件 id"，从它之后继续读 | dashboard（每 3 秒调用一次）和其他监控程序 |
| `duoduo spine cat` 与 `duoduo spine show` | 按日期和时间段读事件日志：一次工具调用与它的结果合成一行，正文不截断，头部和尾部都给出计数，尾部计数出现才说明整段已经读完；`show` 输出单条事件的完整 JSON | 分区会话读自己的历史；排查问题的人 |
| dashboard（`GET /dashboard`，daemon 自带的一个网页，不引用外部脚本） | 会话、job、用量和事件流，事件流可以点击过滤；每个会话显示实际服务的模型，有待生效的模型时显示为"实际模型 → 待生效模型" | 人 |
| `duoduo daemon status` | daemon 是否健康、进程号、版本、运行数据目录；心跳的上次时间与间隔；轮转表当前这一轮已完成几个分区；此刻正在执行的工具调用（会话、工具名、已运行多久）；输出曾被取走、但现在没有订阅者的渠道会话，以及它们的输出最近一次被取走是多久以前；只读检查与遗忘 GC 是否打开，以及各分区的契约 | 人；判断某个会话为什么拒收 Notify |
| RPC `system.status`（只读端口可调用，dashboard 每 5 秒读一次） | 每个会话实际服务的模型，以及已请求但尚未生效的模型；正在执行的工具调用；渠道会话最近一次输出被取走的时间和当前订阅者数 | dashboard 和其他监控程序 |
| 内核 git 历史 | 记忆板、档案、分区提示词、轮转表和渠道种类配置（`config/` 下的 `.md`）的改动：memory-committer 每次运行把这些改动合成至多一个提交，提交说明写明演化了什么，本次运行期间还在被修改的文件留到下次；遗忘 GC 的删除按设计另有自己的提交（默认目录布局下这次提交可能失败，见 5.1 节） | 人回溯"它为什么变成这样"，必要时 revert |
| daemon 运行日志（`~/.aladuo/run/daemon.stdout.log`、`daemon.stderr.log`，`duoduo daemon logs` 查看） | 指令指纹变化时的新旧指纹、会话重建、分区运行结果等 | 人。日志按严重程度分级，指纹变化这类记录属于 info 级，而默认级别是 warn，只写更严重的记录；要看到它们需设 `ALADUO_LOG_LEVEL=info` |

三处读法需要说明。第一，"该用哪个模型"和"实际用了哪个模型"是两条独立记录，允许不一致，例如 Codex 会话改了模型之后，要到下一轮开始时 fork 出新线程才换上新模型，在此之前两者不同；账本记的是实际服务的模型，所以接第三方中转服务时，对方未经声明换成便宜模型也能在账本上看出来。第二，`duoduo daemon status` 只跟踪工具调用：模型正在生成文字、还没调用工具时，列表同样为空，所以列表为空不表示没有工作在进行。第三，用量账本只追加，没有自动保留策略，长期运行的主机会累积到几百 MB；`duoduo-runtime-admin` 技能给出了归档步骤。

**对产品设计的含义。** 评估任何一个无人值守的 agent，先要一份类似 5.1 节的清单，写明哪些约束由代码执行、各自读取什么配置；给不出这份清单的产品，应把它的全部约束当作提示词约束看待，逐条问"模型违反了会怎样"。duoduo 的信任边界是单机、单用户：完整控制面靠文件系统权限区分用户，默认不弹审批，Claude 会话拥有启动 daemon 的那个用户的权限。它适合一个人在自己的机器上长期运行，不适合多个用户共用，也不适合直接暴露到公网；需要这些场景的产品要另外设计账号、权限和隔离，调整 duoduo 的配置解决不了。

## 第六部分 · 总评

**duoduo 有十二个可以移植到其他 agent 产品的设计，其中多数遵循同一条分工：确定性的事交给代码，需要判断的事交给模型。它的局限有三个：代码闭源且只能单机运行，自我修改限于提示词和记忆且没有修改后的验证，后台花费随变化产生、上限由心跳间隔和分区设置决定，没有按金额的上限。**

### 6.1 十二个可借鉴的设计

十二个设计里，第 9、10 条要以第 3 条为前提，因为第 9 条的证据和第 10 条的读取统计都来自事件日志；其余各条可以单独移植。下表按本文的节序排列，"适用条件"一列说明在什么情况下值得移植。

| # | 设计 | 所在节 | 适用条件 |
|---|---|---|---|
| 1 | 调用自带工具执行循环的 agent 引擎，运行时不自己编写工具执行循环 | 1.1 | 产品需要读写文件、执行命令，并且能接受引擎由外部厂商发布和升级 |
| 2 | 一份系统提示供多个引擎使用；同名命令在各引擎上分别实现，并在回复里写明差异 | 1.3、1.5 | 需要同时支持多个 agent 引擎 |
| 3 | 先写事件日志再执行；带同一幂等键重复到达的消息重放上次的回执，不再调用模型 | 2.1、2.5 | 需要崩溃后续跑未完成的工作、事后审计，或上游平台会重复投递同一条消息 |
| 4 | 入口分流：不需要模型的运维命令由网关直接回复 | 2.1 | 用户会在同一个对话窗口里发查询状态、改配置、取消之类的命令 |
| 5 | 把相邻的连发消息合并为一次调用；模型运行中来的新消息优先插进正在进行的一轮，必须中止时尽量等到工具调用的边界 | 2.2 | 用户在即时通讯软件里习惯连发短句，或模型会执行有副作用的工具 |
| 6 | 稳定内容放系统提示，时间、被打断等每轮变化的信息放在每轮瞬时块里 | 2.4 | 按输入缓存计费、同一会话多轮调用的对话 agent；改动只涉及提示词各段的位置，不需要改变系统结构 |
| 7 | 用 checkbox 文件做轮转表，并给每个文件指定唯一的写者 | 3.2、4.7 | 人、模型、代码三方都会修改同一组文件 |
| 8 | 设定与记忆放在一个 git 仓库里，每次修改是一个可以 revert 的提交 | 4.1 | agent 会修改自己的提示词或记忆 |
| 9 | 运行时只测量并写任务单、由模型决定修改内容的流水线；信息只能单向流动，运行时自己产生的事件不能成为证据 | 4.3、4.4 | 希望 agent 根据使用经验修改自己的记忆，同时要避免它把自己产生的信号当作新证据 |
| 10 | 记忆分层并设预算，统计每行记忆指向的档案有没有被读过 | 4.3、4.5 | 记忆随使用不断增加，而上下文窗口有限 |
| 11 | 用指令指纹区分"只有记忆变了"和"身份或任务变了"，分别处理 | 4.6 | 会话会续接，而提示词或记忆会在会话运行期间被修改 |
| 12 | 代码强制的检查清单与失败处置表 | 5.1、5.3 | 任何无人值守运行的 agent；两张表也可以直接当验收清单使用 |

### 6.2 三个局限

duoduo 的三个局限分别出在分发方式、自我修改的范围和后台花费上，下面逐条说明。

1. **代码闭源，只能单机运行。** 上游 README 的许可声明是 "Private. All rights reserved."，npm 包里只有压缩后的 JavaScript，不能复制它的代码另起项目，也不能自己扩展它：引擎只有 `claude`、`codex`、`grok`、`pi` 四个取值，接入第五种引擎要等上游修改代码；模型和模型服务商（provider）的选择不受这个限制，例如 pi 引擎可以使用用户在自己的 pi 配置里接入的任何服务商。全部调度都在一个 daemon 进程的内存里完成，一个数据目录只允许一个 daemon（5.1 节），不能靠增加机器提高吞吐；完整控制面靠文件系统权限区分用户，没有账号体系。可以借鉴它的架构，不能复用它的代码。
2. **自我修改限于提示词和记忆，而且没有修改后的验证。** agent 能改的是提示词、分区的设置和轮转表、记忆文件（4.7 节）；duoduo 没有让 agent 给自己编写新工具或修改运行时代码的机制。作为对照，pi 作为独立的编码工具使用时，允许 agent 给自己编写扩展代码（见 [`AGENT_FRAMEWORKS_COMPARISON.md`](./AGENT_FRAMEWORKS_COMPARISON.md)）。duoduo 也没有"改完之后是否变好"的自动检验：效果记录和 activation report 是修改生效之后的统计，不是生效之前的测试。
3. **后台花费随变化产生，上限由心跳间隔和分区设置决定，没有按金额的上限。** 只有外部事件或三个记忆目录（fragments、entities、topics）自上一次心跳以来有变化，那一次心跳才会运行分区，每次最多两个（3.3 节）。分区自己写这三个目录也算变化，所以一次外部事件之后可能连续几次心跳都运行分区，直到分区不再写入。能调的是心跳间隔，以及各分区的冷却次数、单次运行时长上限、是否启用、所用引擎、模型和推理力度；没有按金额设定的预算上限。

## 附录 B · 出厂四个后台分区

npm 包出厂四个后台分区：gradient-distiller 写碎片，intuition-weaver 改记忆板，pattern-tracker 写规则节点，memory-committer 提交 git；前三个在 frontmatter 的 `contract:` 里声明接收哪些信号，memory-committer 不接收任务单。下表的冷却与超时取自各分区 frontmatter 的 `schedule:`，各信号的含义见 4.3 节。契约里的信号名带版本后缀（如 `scan-gap.v2`、`fold-gap.v1`），表中省略后缀。

| 分区 | 冷却 / 超时 | 接收的信号 | 职责 |
|---|---|---|---|
| gradient-distiller | 5 次心跳 / 35 分钟 | scan-gap | 用 `duoduo spine cat` 读某一天某个时段的外部事件，逐条对照记忆板的每一行，写成回指具体某一行的碎片。它写的文件只有碎片和自己的扫描进度文件，不写记忆板 |

| pattern-tracker | 7 次心跳 / 15 分钟 | node-converge、revise、orphan-newborn | `memory/topics/` 下 `lesson-*` 与 `groove-*` 的唯一写者：一次"偏离 → 人纠正 → 按纠正做成功"写成 lesson，同类任务反复出现并收敛出固定步骤写成 groove。按任务单改写已有节点，文件名不变：node-converge 把偏离规定格式的节点改回规定格式，revise 按记忆板和效果记录的证据把节点整份重写成当前的规则 |

运行时的退休名单里另有 memory-weaver 和 cadence-executor 两个分区。老内核里如果仍有这两个目录，且确认是官方那份，运行时在启动时把它们 frontmatter 里的 `schedule.enabled` 改为 `false`，并在 `~/.aladuo/var/meta/partitions/` 下留一个标记；目录和 git 历史都不动，这个修改只做一次（4.2 节）。它们在哪个版本退出出厂列表见附录 D。

**两条否定性结论。** 本文有两个结论不是由某段代码直接证明的，而是由"在 daemon 和 CLI 两个打包文件里都找不到对应代码"得出的：

1. **渠道适配器进程崩溃后不会自动重启（2.6 节）。** CLI 以脱离终端的方式启动适配器进程，把进程号写进文件后就不再监听它是否退出；CLI 里启动适配器的只有 `duoduo channel <种类> start` 和升级流程两处，升级流程只重新启动升级前正在运行的适配器；daemon 的打包文件里没有管理适配器进程的代码，连记录适配器进程号的文件名都没有出现。具体代码位置见证据文档第 9 节。
2. **运行时不会自动回滚对提示词和记忆的修改（4.8 节）。** daemon 和 CLI 的打包文件里都没有执行 `git revert` 的代码；daemon 里唯一恢复文件的 git 操作，是遗忘 GC 在自己的提交失败时尝试撤回刚做的删除（5.1 节，代码证据见证据文档 12.3 节）。分区提示词刷新流程的技能原文也写明，回滚点是那次刷新提交，由用户执行 `git revert`。

**pi 与飞书的证据没有还原的函数名。** 还原流水线只覆盖 daemon 和 CLI 两个打包文件。pi 引擎的 worker 程序 `pi-worker.js` 和飞书渠道适配器 `feishu-gateway.js` 也在包内的 `dist/release/` 目录里，但没有经过还原，里面的函数没有真名。daemon 这一侧启动 pi worker、与它交换消息的代码在还原范围内；发生在 worker 进程内部的行为（插话、压缩、工具注册、QueueOutboundAttachment 回给模型的文字、`/cancel` 之后的中断标记），以及飞书适配器的会话键、@ 过滤、访问策略、`/setup` 卡片、进度卡、表情回应、语音和流式卡片，都核对自这两个文件里的字符串字面量。证据文档把这些字面量写成普通引号文字并注明出处，构建检查不核对它们。飞书适配器经 CLI 启动时能收到哪些环境变量，另外对照了 npm 上已发布的 `@openduo/channel-feishu` 包声明的变量名单。

## 附录 E · 对本仓库长期目标的启示

本仓库的长期目标是做一个会做金融预测、并用预测结果持续修正自己判断的 agent（细节见 [`AGENT_FRAMEWORKS_COMPARISON.md`](./AGENT_FRAMEWORKS_COMPARISON.md)）；对这个目标，duoduo 最值得复用的是 6.1 表的第 3、9、10 条，第 7 条也有直接对应，而 duoduo 缺少的修改后验证（6.2 第 2 条）正是金融场景必须自建的部分。

第 3 条（先写事件日志再执行）可以用来记录预测：把"作出预测"和"预测结算"做成事件日志里的两类事件，预测在结果出现之前就已写入，运行时对日志只追加、不改写，复盘时可以逐条对照。第 10 条（记忆分层与预算）可以用来组织信念库，即显式记录每条判断及其概率的一组文件：每条信念是一份档案，常用的结论以一行的形式放在记忆板上，并像效果记录那样统计它被后续结果支持或推翻的次数。第 9 条（运行时测量、模型决定修改内容的流水线）可以用来做校准复盘：由代码计算预测概率与实际结果的偏差、写成任务单，交给一个后台分区，由模型决定修改哪条信念。第 7 条（每个文件有唯一的写者）对应预测记录的分工：模型写预测，代码写结算，双方都不改对方的文件。

duoduo 的后台分区改完记忆就生效，没有检验修改是否让判断变好。金融预测的错误有直接的代价，所以信念修改之后需要一个验证步骤，例如在历史数据上回测，或在之后若干次预测上比较修改前后的得分，确认变好之后再让修改进入前台使用的记忆。
